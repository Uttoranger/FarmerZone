# ARCHITECTURE

## 1. Schichten

```
UI            src/app/**/page.tsx, src/components/**
                 ↓ ruft auf, kennt keine DB
DOMAIN        src/lib/<fachregel>.ts        ← rein, ohne I/O, direkt testbar
SERVERGRENZE  src/server/actions/**  src/server/queries/**  src/app/api/**
                 ↓ einzige Schicht mit DB-Zugriff
DATEN         Prisma über @/lib/prisma
```

**Die eine Regel, aus der alle anderen folgen:** Fachliche Entscheidungen gehören in eine reine Funktion in `src/lib/`, die ohne Datenbank testbar ist. Die Servergrenze beschafft Daten, ruft die Entscheidung auf, schreibt das Ergebnis.

Vorbild: `src/lib/reservierung.ts` entscheidet (rein, 174 Tests ohne DB), `src/server/warenkorb.ts` wendet an, `src/app/api/checkout/route.ts` schreibt.

### Verboten
- **Keine** Prisma-Aufrufe in `src/components/**`.
- **Keine** Prisma-Aufrufe in `src/lib/<fachregel>.ts` (Ausnahmen: `prisma.ts`, `auth.ts` selbst).
- **Keine** Geschäftsentscheidung in einer React-Komponente (Rabatt, Frist, Verfügbarkeit, Preis).
- **Keine** Geschäftsentscheidung in einem API-Route-Handler. Handler = Eingang, Validierung, Aufruf, Antwort.
- **Kein** direkter Aufruf einer Server Action aus einer anderen Server Action, wenn die gemeinsame Logik in `lib/` gehört.

### `src/lib/` ist voll — Regel beim Hinzufügen
94 Dateien (Stand 2026-09-29), gemischter Zweck. Bevor eine neue entsteht:
1. Passt es in eine bestehende Datei? Dann dorthin.
2. Ist es eine **Fachregel**? → eigene Datei, rein, ohne Import von `prisma`/`auth`/`stripe`.
3. Ist es eine **Infrastrukturkapsel** (externer Dienst)? → `server-only` importieren.
4. Ist es ein **React-Hook**? → Präfix `use-` (`use-cart.ts`).

## 3. Server Action oder API-Route?

**Standard ist die Server Action.** API-Route nur bei einem dieser Gründe:

| Grund | Beispiel |
|---|---|
| Externer Aufrufer | Stripe-Webhook, Vercel Cron |
| Aufruf per Link (GET) — nur lesen oder weiterleiten, nie einen Zustand ändern; einzige Ausnahme Fristfreigabe beim Lesen (§5) | Bestätigungslink älterer E-Mails |
| Aufruf aus `fetch()` im Browser mit eigener Fehlerbehandlung | `/api/reserve`, `/api/checkout` |
| Nicht-JSON-Antwort | Export, Datei |

Sonst: Server Action. **Keine** API-Route bauen, nur weil das Muster vertraut ist.

### Pflichten jeder API-Route
1. Rate-Limit (`enforceRateLimit`) bei allem, was schreibt oder Bestand hält; auf den Wegen aus Register R1 zusätzlich die zweite Stufe über alle Instanzen (§5 „Zweistufige Bremse“).
2. Zod-Validierung des Bodys **und** der URL-Parameter.
3. Auth- bzw. Token-Prüfung, **fail-closed**: fehlt das Geheimnis, wird gesperrt, nicht geöffnet.
4. Antwortform nach `CODING_STANDARDS.md`.
5. Langsames über `nachDerAntwort()`.

### Triage-Routen: ein Token je Recht
Der Briefkasten hat zwei API-Routen, weil ihre Aufrufer extern sind (CLI, GitHub Action):

| Route | Token | Darf |
|---|---|---|
| `GET /api/triage/export` | `TRIAGE_TOKEN` | nur lesen |
| `POST /api/triage/status` | `TRIAGE_WRITE_TOKEN` (Rechner des Entwicklers) | `VERMUTLICH_WUNSCH`, `GEPLANT` — nur Art FEHLER |
| `POST /api/triage/status` | `TRIAGE_MERGE_TOKEN` (nur GitHub Actions) | `ERLEDIGT`, Wiederöffnen (`ERLEDIGT → GEPRUEFT`) |

- Ein Token je Recht, alle drei verschieden — sind zwei gleich, lehnt die Route alles ab. Ein Token, der für den Status nicht gilt → 403.
- Welcher Übergang erlaubt ist und was er schreibt, entscheidet `src/lib/triage-status.ts`; die Route liest, fragt dort und schreibt per `updateMany` auf genau den gelesenen Stand (sonst 409).
- Die Schreibroute schreibt nie Text, den ein Melder sieht, außer ihren festen Sätzen, und nie die Art. Body strikt: ein unbekanntes Feld ist 400.
- Den Merge-Token gibt es nie auf einem Rechner mit Agenten — abschließen kann nur das Deployment.

### Pflichten jeder Server Action
1. `'use server'` als erste Zeile.
2. Auth prüfen — **nie** der Eingabe vertrauen, wer der Aufrufer ist.
3. **Besitz prüfen:** Gehört der Datensatz zum Hof des eingeloggten Nutzers? Jedes Mal.
4. Zod-Validierung des Arguments.
5. `revalidatePath()` für jede betroffene Route.

**Öffentliche Server Action (ohne Anmeldung)** — Punkte 2 und 3 entfallen, dafür: Argument als `unknown` annehmen und mit Zod prüfen (Längengrenzen aus `src/lib/eingabegrenzen.ts`), Bremse je IP mit einer modulweiten `createRateLimiter`-Instanz und `getClientIp(await headers())` (`src/lib/rate-limit.ts`), wie `enforceRateLimit` nur bei `NODE_ENV === 'production'` (auf den Wegen aus R1 danach die zweite Stufe, §5 „Zweistufige Bremse“); das Limit als Konstante in einem reinen Modul, damit der Test es importieren kann (eine `'use server'`-Datei exportiert nur asynchrone Funktionen). Über dem Limit eine Antwort, die die Oberfläche ruhig behandelt — eine neutrale (`null`, leere Liste) bei reinen Hinweisen, `{ error, code: 'ZU_VIELE' }` bei Aktionen, auf die jemand wartet. Die Antwort verrät nichts, was der Aufrufer nicht schon weiß (keine Unterscheidung nach Freischaltung, Rolle, Bestand). Vorbilder: `checkSlugAvailability` (`src/server/actions/onboarding.ts`, neutral `null`, Antwort nur frei/vergeben), `loeseOrtAuf` (`hoefe.ts`, nur für die leere Liste als ruhige Antwort; Argument über `ortssucheSchema`), „Bestellungen finden" (`ZU_VIELE`).

### Die Admin-Prüfung: `src/server/admin-wache.ts`

Für den Betreiber-Bereich gibt es **eine** Antwort auf „darf dieser Mensch die
Plattform verwalten?", mit zwei Ausgängen:

| Wo | Aufruf | Verhalten |
|---|---|---|
| Admin-**Seite** (`src/app/admin/**/page.tsx`) | `await verlangeAdminSeite()` | nicht angemeldet → `redirect('/login')`, angemeldet ohne Recht → `notFound()` |
| Admin-**Aktion** (`'use server'`) | `await verlangeAdminAktion()` | `{ ok: true, userId } \| { error }` — die Antwortform der Actions |

- Beide lesen das Recht über `isAdminUser` **frisch aus der Datenbank**, nie aus
  der Session: `isAdmin` steckt bewusst nicht in den
  Better-Auth-additionalFields, damit ein zurückgenommenes Recht sofort greift.
- `notFound()` statt 403: Der Bereich gibt sich Unbefugten nicht zu erkennen.
- Die Prüfung steht in **jeder** Aktion, nicht nur in der Seite. Eine Seite
  schützt die Ansicht, eine Aktion schützt die Wirkung.
- **Layout `src/app/admin/layout.tsx` (seit Nr. 22f):** trägt die AdminShell und
  lädt Name und Zähler nur über `ladeAdminbereich` (`src/server/adminbereich.ts`),
  das als erste Anweisung `verlangeAdminSeite()` ruft — ein Layout rendert
  parallel zur Seite und darf Unbefugten keine Zähler zeigen. Die Seiten prüfen
  trotzdem selbst (`tests/admin-seiten-wache.test.ts`: jede `page.tsx` unter
  `src/app/admin`, Layout und Lader, AST mit Gegenproben).
- Im Admin gibt es keine Hofzugehörigkeit — das Admin-Recht **ist** die
  Besitzprüfung. Keine eigene Fassung daneben bauen: Vorher lag die Frage an
  vier Stellen und in zwei Implementierungen.

## 4. Datenfluss

### Lesen
```
Server Component → src/server/queries/*  → Prisma → Props → Komponente
```
- Standard ist die Server Component.
- `'use client'` nur bei Interaktivität (State, Event-Handler, Browser-API).
- `'use client'` so tief wie möglich im Baum — nie ein ganzes Layout zur Client-Komponente machen.
- Serialisierbarkeit beachten: `Decimal` und `Date` nicht roh in Client-Komponenten reichen (→ `CODING_STANDARDS.md`).

### Schreiben
```
Client-Komponente → Server Action → Zod → Fachregel (lib) → Prisma → revalidatePath
```

### State-Regeln
| Art | Wo | Nicht |
|---|---|---|
| Server-Daten | Server Component, per Props | Nicht in Client-State spiegeln |
| Formular | `react-hook-form` | Kein `useState` je Feld |
| UI-lokal (offen/zu) | `useState` | Nicht global |
| Warenkorb | `use-cart.ts` (localStorage) + serverseitige Reservierung; der Speicher nur über `src/lib/warenkorb-speicher.ts` (ein Schlüssel, Zod, Ereignis `WARENKORB_EREIGNIS` nach jedem Schreiben) | Warenkorb ist **nie** die Wahrheit über Verfügbarkeit. ### Schwere Module nur dynamisch (seit Nr. 31)
- **Kein Seitenmodul zieht E-Mail-Versand oder Stripe statisch mit** — auch nicht über eine Server Action, die eine Client-Komponente der Seite einbindet (sie landet in den Server-Chunks der Seite). Resend, `@react-email/*`, `src/emails/*`, das Stripe-SDK und die Sammelmodule `src/lib/email.ts` und `src/lib/stripe.ts` kommen per `await import()` erst dort, wo gesendet bzw. Stripe gefragt wird: in der Versandfunktion, der Action, dem Zweig. Vorlage: `const { sendOrderReady } = await import('@/lib/email')` im Nachlauf, `const { stripe } = await import('@/lib/stripe')` direkt vor dem Aufruf (in `teilerstattung.ts` über `stripeSdk()`).
- **`email.ts` ist selbst leicht:** Es importiert statisch nur Formatierer und Fachregeln; Resend-Client, `render` und jede Vorlage lädt die Versandfunktion. Kein Log und keine Arbeit auf Modulebene (früher „[E-Mail] Init" bei jedem Kaltstart).
- **Der dynamische Import gehört in dieselbe Fehlerbehandlung wie der Aufruf** (im `try` bzw. im Nachlauf), damit ein gescheitertes Laden wie ein gescheiterter Versand behandelt wird — ein Nachlauf rollt nie etwas zurück.
- **Kein `await import()` innerhalb einer Transaktion:** Das erste Laden hielte eine Zeilensperre (FOR UPDATE) fest. Wer in der Transaktion Stripe braucht, ruft vorher `stripeVorladen()` (`src/server/teilerstattung.ts`, Vorbild `meldeFehlendenArtikel`); in der Transaktion nutzt `stripeSdk()` das gemerkte SDK.
- **Versandfunktionen mit Ergebnis werfen nicht:** Anmeldecode, Bestell-Code und E-Mail-Bestätigung laden und rendern ihre Vorlage über `htmlOderFehler` und liefern beim Scheitern `{ error }`.
- Ausnahme: API-Routen, die das Modul in jedem Aufruf brauchen (Webhook, Kasse, Cron), dürfen statisch importieren.
- `tests/schwere-module.test.ts` läuft den statischen Import-Graphen jeder `page`/`layout`/`loading` unter `src/app` ab (ohne `api`) und nennt die Kette, über die ein schweres Modul hereinkam. Tests, die „keine Mail" prüfen, warten vorher `await vi.dynamicImportSettled()` ab (`TESTING_GUIDELINES.md` §3).

### Jede Route hat ihre Ladeansicht (seit Nr. 31)
- **Im Hofbereich (`(hof)`, `(farmer)`) hat jede Route mit `page.tsx` ihre eigene `loading.tsx`** in der Form ihrer Seite (Regeln: `DESIGN_SYSTEM.md` „Ladeansicht einer Route"); die Gruppen haben zusätzlich einen Rückfall (`(hof)/loading.tsx`, `(farmer)/loading.tsx`) für neue Routen. Ausnahme bis zum Umzug nach `(hof)` (Nr. 22c): die Auswertung unter `(farmer)/analytics` — sie bringt ihre Ladeansicht dort mit. Der Admin bekommt seine mit der AdminShell (Nr. 24). Ohne sie gab es beim Tab-Wechsel weder sofortige Rückmeldung noch Vorladen bis zur Grenze. `tests/ladeansichten.test.ts` prüft beides.
- **Zugang gehört ins Layout ÜBER der Grenze.** Mit `loading.tsx` streamt Next.js: Was erst die Seite prüft (`redirect`, `notFound`), kommt nach dem Skelett mit Status 200 im Datenstrom. Deshalb prüft das Layout der Gruppe vorher — `ladeHofbereich` in `(hof)`/`(farmer)`; wer Ladeansichten unter `/admin` anlegt, braucht dort ein Layout mit `verlangeAdminSeite` (sonst gäbe sich der Admin-Bereich Unbefugten mit einem Skelett zu erkennen). Eine fremde ID in einer Seite (`notFound()` hinter der Grenze) ergibt die 404-Ansicht mit Status 200 und `noindex` — kein Inhalt geht hinaus.
- Eine Route, die nur umleitet (`/status`), zeigt die Ladeansicht ihres Ziels.

### Kundenseiten: Kopfzeile und Rückweg
- Jede Seite unter `src/app/(public)/` rendert `KundenKopf` (`src/components/shared/kunden-kopf.tsx`) mit ihrer `KundenSeite`, bis ihr Gate sie in die `KundeShell` umstellt; die Startseite trägt seit Nr. 07 die `KundeShell` (Sitzung über `istKundensitzung`: nur die Kunden-Anmeldung zählt als angemeldet), `/hoefe` seit Nr. 09 (bleibt `force-dynamic` wegen der Filter im Server-HTML, liest die Sitzung aber ebenfalls über `KundeShellMitSitzung`). Die Hofseite seit Nr. 10 ebenso (dynamisch wegen Suchparametern und Fristfreigabe beim Lesen; die Sitzung liest der Server nur für `?vorschau=1`); ihr Rückweg „‹ Alle Höfe" steht als Zeile über dem Titelbild und nutzt `rueckweg`/`useRueckwegKlick` wie bisher. Eine Seite, die sonst statisch sein kann, liest die Sitzung **nicht** auf dem Server (`headers()`, `cookies()`, `auth.api` machen sie dynamisch), sondern nimmt `KundeShellMitSitzung` (`useSession` im Browser) und `export const revalidate`; Vorbild ist die Startseite (`tests/startseite.test.ts`). Die öffentliche Hofliste kommt immer aus `ladeOeffentlicheHoefe` (`src/server/queries/oeffentliche-hoefe.ts`) — ein Cache-Eintrag unter `HOEFE_CACHE_TAG`, nie ein eigener `unstable_cache` je Seite. `tests/kunden-kopf.test.ts` kennt jede Seite — eine neue fällt dort auf.
- **„Für Höfe"** (`/fuer-hoefe`, seit Nr. 15) ist statisch (`revalidate`, `KundeShellMitSitzung`), liest weder Anfrage noch Datenbank; Preise nennt sie wie `/konditionen` (statisch mit `revalidate = 3600`, stündlich neu gebaut seit Nr. 28, Register F6 „19a": die Bar-Ausnahme bis zum Stichtag entscheidet sich je Bau) nur aus `src/lib/konditionen.ts` (E6) — eine Zahl in einer dieser Seiten ist ein Fehler (`tests/konditionen-seiten.test.ts`).
- **Die Bestätigungsseite** (`/[farmSlug]/confirm/[orderId]`, seit Nr. 13) trägt `KundeShellMitSitzung` ohne Unterleiste. Zugang, Fristfreigabe und Zustand bleiben, wie §5 sie beschreibt; Kopf, Blöcke und Status-Schritte kommen aus `src/lib/bestaetigung.ts`, die Bausteine aus `src/components/bestaetigung/`. Der Kalenderlink entsteht nur über `kalenderPfad` (`bestell-link.ts`); Knopf und ICS-Route fragen dieselbe Regel `kalenderTerminGilt` (`bestaetigung.ts`). Die Karte „Neuigkeiten vom Hof per E-Mail" (`NeuigkeitenKarte`, seit Nr. 46) bekommt nur Kennung, Signatur (beides steht ohnehin in der Adresse), Hofname und die Adresse der Bestellung zur Anzeige; zurück an den Server gehen nur Kennung und Signatur.
- **„Meine Bestellungen"** (`/bestellungen`, seit Nr. 14) trägt `KundeShellMitSitzung` mit Unterleiste, ist dynamisch (liest den Cookie), `noindex`, `Referrer-Policy: no-referrer` (Metadaten und Header in `next.config.ts`). Ohne bewiesene Adresse das Formular, danach die Liste — Regeln siehe §5. Die Seiten unter `/account` (`login`, `profile`, `unsubscribe`) tragen dieselbe Shell; ihr Inhalt ist unverändert (E8).
- **Die Produktseite** (`/[farmSlug]/produkt/[id]`, seit Nr. 11) lädt über denselben Lader wie die Hofseite (`ladeHofseiteGeteilt`: öffentliche Höfe, Fristfreigabe, Vorschau nur für den Besitzer) und zeigt das Produkt nur, wenn es in der Produktliste DIESES Hofs steht und im Shop ist (`sichtbaresProdukt`) — sonst 404; eine ID allein öffnet nie etwas. ## 5. Domänen-Invarianten

Diese Regeln sind fachlich, nicht technisch. Verletzung kostet Geld oder Vertrauen.

- **Reservierung bucht keinen Bestand ab.** `Product.stock` sinkt erst beim Kauf. `StockReservation` ist ein weicher Halt, der die Menge nur vor **anderen** Sitzungen verbirgt. Verfällt er, gibt es nichts zurückzubuchen.
- **Die 15-Minuten-Frist gilt beim Lesen.** Jede Abfrage fremder Halte filtert auf `expiresAt > jetzt`. Nie einem Cron vertrauen.
- **Eine offene Bestellung hat eine Frist, und auch sie gilt beim Lesen.** Der Checkout bucht den Bestand vor Zahlung bzw. Bestätigung. Wie lange eine Bestellung in PENDING_CONFIRMATION ihre Ware hält, steht nur in `src/lib/fristen.ts`: online 30 Minuten; vor Ort 2 Stunden, höchstens bis zum Beginn des gewählten Abholfensters. Wer Bestand oder offene Bestellungen liest, gibt vorher frei, was darüber ist: `gibVerwaisteFreiOhneRisiko(farmId)` bzw. `gibVerwaisteFreiFuerProdukte(productIds)` (`src/server/verwaiste-bestellungen.ts`). Die Hofseite gibt über `gibVerwaisteFreiFuerSlug` frei, in `ladeHofseite`. Ein neuer Lesepfad ruft eine der drei am Anfang auf; Fehler darin werden gemeldet, nie an den Request weitergegeben. Nicht nach der Antwort (`after()`/`nachDerAntwort`), solange die Seite Bestellungen oder Vorrat zeigt — sie zeigte sonst Verfallenes. Was die Freigabe nicht ändern kann, darf neben ihr laufen (Vorbild `getHeute`, Nr. 31): Die Abfrage bekommt die laufende Freigabe als Promise und startet nur die abhängigen Abfragen in `freigabe.then(...)`, beides in EINEM `Promise.all`. Online wird zuerst der PaymentIntent abgebrochen — **Ausnahme** von „Stripe und Mail kommen danach", weil die Kundin die verfallene Bestellung sonst noch bezahlen könnte; ist er bezahlt oder in Bearbeitung, bleibt die Bestellung stehen und Stripe wird höchstens alle fünf Minuten erneut gefragt. Der tägliche Cron `/api/cron/verwaiste-bestellungen` ist nur das Netz und meldet stehen gebliebene Bestellungen an Sentry.
- **Cron-Routen prüfen `CRON_SECRET` mit `cronBerechtigt`** (`src/lib/geheimnis.ts`): fail-closed, in konstanter Zeit — nie mit `!==`.
- **Bestandsabzug ist bedingt.** `updateMany` mit `stock >= Menge`; bei Teilfehlschlag die bereits gebuchten Positionen gutschreiben.
- **Vorrat setzen ist bedingt (seit Nr. 18).** Ändert der Hof den Vorrat (Produkttabelle `setzeVorrat`, Bearbeiten-Dialog `updateProduct`), ist das ein Setzen auf den Wert, den er meint — aber nur, wenn die Zeile noch den Vorrat hält, den er gesehen hat: `updateMany` mit `{ id, farmId, stock: vorher }`. Trifft die Bedingung nicht (eine Bestellung oder ein Storno hat inzwischen gebucht), wird nichts geschrieben, und die Antwort trägt den aktuellen Stand (`code: 'GEAENDERT'`). So überschreibt ein Setzen nie eine Buchung, die der Hof nicht gesehen hat; ein Setzen nutzt nie `increment`/`decrement` und nie einen Wert ohne erwarteten alten Stand. Abziehen (Checkout, `bucheVorrat`) geht nur bedingt: `updateMany` mit `stock >= n` und `decrement: n` — nie ein blindes `decrement`. Nur `bucheVorrat` hat einen zweiten Schritt: reicht der Vorrat nicht, bedingt `stock < n` → 0 (Abschnitt „Verkäufe" in §4). `updateProduct` schreibt einen unveränderten Vorrat gar nicht. Reservierungen sind davon unberührt: Setzt der Hof unter das, was in Warenkörben liegt, scheitert der Checkout an `stock >= Menge`. Der Browser schickt je Produkt eine Änderung nach der anderen mit dem zuletzt bestätigten Stand (`VorratFeld`). Bewiesen in `tests/integration/vorrat-setzen.int.test.ts` mit erzwungener Reihenfolge (eine offene Buchung hält die Zeile, `setzeVorrat` wartet nachweislich darauf und setzt danach nicht) samt Gegenprobe (dieselbe Abfolge mit blindem Setzen verliert die Buchung).
- **Ein Statuswechsel mit Wirkung auf Bestand oder Geld ist die Sperre.** Er läuft als `updateMany` mit Statusbedingung (Vorlage: `cancelOrder`), `count === 0` heißt „schon erledigt" — nie eine Leseprüfung mit anschließendem blindem `update`. Bestandsbuchungen gehören in DIESELBE Transaktion; Stripe und Mail kommen danach. Auch ein Rückweg (Undo) schreibt bedingt: Er darf eine stornierte Bestellung nie zurückholen. Zahlstatus und Zahlzeitpunkt bleiben dabei stimmig (`paymentStatus` PAID genau mit `paidAt`): Was ein Rückweg an der Zahlung ändert — das Rückgängig im Hinweis (`revertOrderStatus`) wie der Dialog „Abholung rückgängig" (`revertPickedUp`, seit Nr. 32) —, entscheidet nur `zahlungNachRueckweg` (`hof-bestellungen.ts`) — online nie, bar nur das Kassieren genau des zurückgenommenen Schritts —, geschrieben bedingt auf den gelesenen Zahlstand.
- **Seiten mit Daten einer Bestellung nur mit signiertem Link.** Bestätigungsseite (`/{hof}/confirm/{id}?sig=`) und Bestellseite (`/{hof}/bestellung/{id}?s=`) prüfen `bestellLinkGilt` (`src/lib/bestell-link.ts`) VOR jeder Datenbankabfrage; ohne gültige Signatur zeigt die Bestätigungsseite nur „eingegangen", ohne Name, E-Mail, Artikel oder Beträge. Die Bestell-ID ist ratbar. Pfade dorthin baut nur der Server (`bestaetigungsPfad`, `bestellungPfad`) — das Geheimnis gehört nie in den Browser; `/api/checkout` liefert den signierten Pfad mit (`bestaetigung`). `tests/bestaetigung-zugang.test.ts` sucht nach selbst gebauten `/confirm/${…}`. **Der Link liest — mit genau einer Ausnahme (seit Nr. 46):** Dieselbe Signatur (Zweck `bestellung-ansehen`, auch in Bestellmail und ICS-Seite) erlaubt eine Abo-Anfrage über `meldeNeuigkeitenAn` („Neuigkeiten vom Hof per E-Mail"). Wer den Link hält — auch wer eine Bestellung mit fremder Adresse angelegt hat —, kann damit nur Folgendes auslösen: eine Bestätigungsmail an die Adresse DER Bestellung (nie eine andere), angemeldet erst mit dem Klick darin (Double-Opt-in, S11); nur für eine laufende Bestellung (`neuigkeitenErlaubt`: nicht storniert, verfallen, nicht abgeholt oder unbezahlt, bar offen nur bis zur Frist); höchstens drei Anfragen je Bestellung und Tag (Datenbank-Bremse `neuigkeitenBestellung`), ein Link je Abo und zehn Minuten, in Produktion zehn je IP und Minute; immer dieselbe Antwort; an der Bestellung ändert sich nichts. Ein weiterer Schreibweg über diese Signatur braucht ein eigenes Token mit eigenem Zweck.
- **Kein signierter Link an Orten, die wir nicht schützen.** Ein Kalendereintrag (ICS, `/{hof}/bestellung/{id}/kalender`) wird synchronisiert, geteilt und weitergereicht — seine `DESCRIPTION` nennt nur die Bestellnummer, nie `bestellungPfad`/`bestaetigungsPfad`. Einen Termin gibt es nur, solange die Bestellung steht und die Abholung aussteht (`kalenderTerminGilt`, beim Lesen: offen — vor der Frist unbestätigt, danach verfallen —, storniert, abgeholt → dieselbe 404 wie jede Ablehnung). Signierte Links stehen nur in Mails an die Kundin und auf ihren eigenen Seiten.
- **Eine gespeicherte Bild-Adresse kommt nur aus unserem Blob-Speicher und dem Ordner des eigenen Hofes.** Jede Aktion, die eine Bild-URL schreibt (Galerie, Titelbild, Logo, Produktbild, Beitragsfoto, Screenshot einer Meldung), prüft über `bildUrlErlaubt` bzw. `istEigenesBild` (`src/server/bild-url.ts` → `istEigeneBildUrl` in `upload-pfade.ts`): https, Host `<speicher>.public.blob.vercel-storage.com` mit dem Speicher aus `BLOB_READ_WRITE_TOKEN` (das Host-Muster allein trifft jeden Vercel-Speicher, auch einen fremden), Pfad unter `farms/<hofId>/` ohne Punkt-Segmente, ohne Anmeldedaten, Abfrage und Anker. Ohne Schlüssel ist nichts erlaubt. Leer (Bild entfernen) geht immer; eine fremde Adresse nur, wenn sie unverändert schon gespeichert ist (Altbestand bleibt speicherbar). Nie eine Bild-URL aus dem Browser ungeprüft speichern (`tests/bild-url-pruefung.test.ts`).
- **Ein Link aus einer Mail ändert nie einen Zustand.** Link-Scanner und Vorschauen der Mailprogramme rufen Links ungefragt auf. Ein GET liest oder leitet weiter; bestätigt, storniert oder bucht wird nur per Knopf (Server Action, POST). **Einzige Ausnahme ist die Fristfreigabe beim Lesen** (`gibVerwaisteFreiOhneRisiko`, wie auf `/{hof}/confirm/{id}` und `/orders`): Sie setzt nur durch, was die Frist ohnehin schon entschieden hat (über der Frist ist die Bestellung verfallen, ob jemand aufräumt oder nicht). Nie löst ein GET eine Bestätigung oder einen anderen Übergang aus, den die Kundin oder der Hof wollen muss. Der Knopf prüft die Frist mit der Zeit NACH seiner eigenen Freigabe (die kann bei Stripe Sekunden dauern), und `confirmedAt` ist genau diese Zeit. Bar-Bestätigung: Die Mail verlinkt `/{hof}/bestaetigen/{token}` (Pfad nur über `barBestaetigungsPfad`), `/api/orders/confirm/{token}` alter Mails leitet nur dorthin weiter. Der Knopf (`src/server/actions/bar-bestaetigung.ts`) bestätigt per `updateMany` auf PENDING_CONFIRMATION **und** den Token, nur solange `barBestaetigungsAnsicht` (`src/lib/bar-bestaetigung.ts`) „offen" sagt (Frist aus `fristVon`), und löscht den Token im selben Schreiben; Mails über `nachDerAntwort`. „Doch nicht" storniert über `storniereUnbezahlteBestellung`. Die Seite zeigt nie Name oder E-Mail der Kundin, `noindex`, `Referrer-Policy: no-referrer`; Sentry entfernt den Token (`sentry-hygiene.ts`).
- **Werbliche Mails nur mit Double-Opt-in (S11, seit Nr. 38).** Werblich sind Mails an Abonnentinnen eines Hofes (heute: Beiträge per Mail aus `publishStatusPost`); Bestellbestätigung, Abholung, Storno, Anmeldecode sind es nicht. Empfänger nur über `WERBEMAIL_EMPFAENGER` (`src/server/abo-anmeldung.ts`: `optInEmail` UND — nie angefragt [Bestand] ODER bestätigt), nie über `optInEmail: true` allein (`tests/abo-bestaetigung-quelltext.test.ts`). Im Checkout sitzt die zweite Stufe (`bremseCheckout`) nach `enforceRateLimit` mit Sitzung und vor jedem Schreiben; bei der Code-Anmeldung (`anmeldecodeGebremst`) im `before`-Hook von `auth.ts`, beim Anfordern nach der Speicher-Bremse je Adresse und vor der Rollenprüfung. Abgelaufene Zähler räumt der bestehende Cron `cleanup-reservations` in eigenem `try` (kein neuer Cron-Eintrag); gelesen wird eine Zeile nach ihrem Fenster nie mehr. Ein neuer Weg bekommt einen Eintrag in `DB_BREMSEN` mit festem Zweck-Wort (`tests/bremse-datenbank.test.ts`, `tests/bremse-verdrahtung.test.ts`, `tests/integration/bremse-datenbank.int.test.ts`). **Eine Ausnahme ohne erste Stufe:** `neuigkeitenBestellung` (Nr. 46, Runde 1) zählt je Bestellung und Tag (`NEUIGKEITEN_JE_BESTELLUNG_UND_TAG`) und gilt in allen Umgebungen (`neuigkeitenGebremst`) — sie schützt das Postfach hinter einer Bestellung vor Wiederholungen, nicht den Server vor Last; das Merkmal ist die Bestell-Kennung, nie die Adresse.
- **Eine Expand-Migration ist nur hinzufügend und wiederholbar.** Neue Spalten an bestehenden Tabellen sind nullable oder haben einen Default (`ADD COLUMN IF NOT EXISTS … DEFAULT …`), dazu `SET lock_timeout`; kein `DROP`, `RENAME`, `ALTER TYPE`, `ALTER COLUMN`, kein `UPDATE` auf Bestandszeilen. Erzeugt wird sie mit `prisma migrate diff` gegen das Schema von `main` (Regel 3 in `docs/nachtlauf.md`), geprüft mit `pnpm test:integration`. Jede solche Migration bekommt eine Datei-Wache (Muster: `tests/schema-expand.test.ts`, `tests/migration-teilen-momente.test.ts` — Anweisungen ohne Kommentare gegen eine Verbotsliste, mit Gegenprobe) und einen Integrationstest, der Default, Deploy-Fenster (rohes INSERT ohne die Spalte) und einen zweiten Lauf auf einem bestehenden Hof prüft (`tests/integration/teilen-momente.int.test.ts`). Ein Schalter mit Default `false` wird so benannt, dass der Default den bisherigen Zustand bedeutet (`Farm.teilenMomenteAus`: false = Momente an wie bisher).

### Zahlungen

- **Vollerstattung bei Destination Charges immer mit `reverse_transfer` — und mit `refund_application_fee`, sobald die Zahlung eine `application_fee` trägt; Gebühren-Teilerstattung ohne beides.** Das gilt auch für eine Erstattung von Hand im Stripe-Dashboard. Vorlage: `cancelOrder`; Teilerstattung: `lasseServicegebuehrEntfallen`. Warum: `DEVELOPMENT.md`, „Vollstorno ohne reverse_transfer". **Ausnahme nach „Artikel fehlt":** Hat eine Bestellung schon eine Teilerstattung oder eine fehlende Position (`nachTeilerstattung`, `src/lib/storno.ts`), holt der Storno den Rest mit FESTEN Beträgen (nächster Punkt) — Stripe kehrte Überweisung und Gebühr sonst anteilig um.
- **Erstattung mit festen Beträgen = zwei Buchungen, nie zweimal** (`src/server/teilerstattung.ts`): erst lesen, was Stripe schon gebucht hat (`ladeStripeStand`: Überweisung über `latest_charge.transfer`, Erstattungen der Zahlung, Rückbuchungen der Überweisung). Jede Buchung trägt `metadata` `orderId`, `anlass` (`teilstorno`/`reststorno`), `positionId`, `art` (`kunde`/`hof`); gibt es für dieselbe Bestellung, denselben Anlass und dieselbe Position schon eine, wird ihr Betrag übernommen und nichts neu gebucht — das schützt auch nach Ablauf des Idempotenz-Schlüssels (rund 24 h) und bei inzwischen anderem Betrag; der Schlüssel bleibt die Sicherung gegen gleichzeitiges Buchen. **Im Zweifel nicht buchen** (`StripeStandUnklar`): hat eine Liste mehr als eine Seite (100), gibt es eine Erstattung oder Rückbuchung ohne zuordenbare Merkmale (von Hand im Dashboard, Teilstorno im alten Format ohne Position, fremder Anlass) oder geht ein Nachtrag fachlich nicht auf bzw. sind es mehr als `NACHTRAGEN_HOECHSTENS`, wird nichts gebucht — Sentry (`stripe_unklar_<grund>`), der Hof bekommt „bitte melde dich bei uns". Eine Erstattung mit Status `failed`/`canceled` zählt nie als erstattet, auch nicht, wenn derselbe Schlüssel sie zurückgibt (`pending` zählt). Sonst die Erstattung an die Kundin über den Betrag OHNE `reverse_transfer` und ohne `refund_application_fee` (geht vom Plattformsaldo, wo die einbehaltene Gebühr liegt), zuletzt die Rückbuchung (`transfers.createReversal`) mit festem Betrag vom Hof. Scheitert nur die Rückbuchung, ist die Kundin bedient; Sentry (`rueckbuchung_offen`) nennt Betrag und Bestellung für die Handbuchung. Nie `reverse_transfer` mit einem Teilbetrag, wenn der Hof einen anderen Betrag zurückgeben soll, als die Kundin bekommt.
- **Storno nach Teilerstattung rechnet aus Stripes Buchungen** (`restNachTeilerstattung`, `src/lib/storno.ts`): Kundin = bezahlt − alle Teilstorno-Erstattungen, Hof = Warenpreis der Bestellung − Provision − alle Teil-Rückbuchungen. **Bezahlt kommt aus Stripe** (`latest_charge.amount`, `StripeStand.bezahltCents`), nie aus der Datenbank; weicht es von Warenpreis + Gebühr + `erstattetCents` ab oder fehlt es, wird nichts gebucht (`StripeStandUnklar` `bezahlt_abweichend`). Der Storno fragt deshalb vor der Vollerstattung mit `reverse_transfer`, ob Stripe schon Erstattungen kennt (`hatErstattungen`, eine Seite) — auch solche, die die Datenbank nach einer verlorenen Antwort nicht hat; dann feste Beträge, `erstattetCents` = alles, was Stripe erstattet hat. Eine gescheiterte Teil-Rückbuchung holt der Rest damit nach.
- **Keine Servicegebühr bei Barzahlung bis zum SEPA-Start (Register B1, Nr. 19a).** Der Stichtag ist `BAR_SERVICEGEBUEHR_AB` in `src/lib/konditionen.ts` (Standard `TARIFE_AB`, Wiener Mitternacht); maßgeblich ist der Bestellzeitpunkt (Server-Uhr von `/api/checkout`), nicht der Abholtag. Entschieden wird nur in `barOhneServicegebuehr` (`src/lib/servicegebuehr.ts`), gerechnet nur in `berechneServicegebuehr(…, zahlungsart)`: bar davor → Snapshot `serviceFeeCents` 0, `serviceFeePercentApplied` und `serviceFeeMinCentsApplied` null (wie ein gebührenfreier Hof, damit „Artikel fehlt" bei 0 bleibt). Online unverändert; `ONSITE_CARD` nennt B1 nicht. Die Kasse rechnet mit der gewählten Zahlart neu, verbindlich ist der Server, Stripe bekommt nur den Betrag der gespeicherten Bestellung. Finanzseite (`topfVonBestellung`) und Admin-Hofliste (rohes SQL, Spalte „bar") zählen Barbestellungen vor dem Stichtag nirgends — auch ältere mit Gebühr nicht, eingezogen wird sie nicht. Gespeicherte Beträge alter Bestellungen bleiben; „Artikel fehlt" rechnet eine ältere Barbestellung mit Gebühr mit IHRER Regel weiter. Texte nur aus `konditionen.ts` (`BAR_OHNE_GEBUEHR_HINWEIS`, `BAR_OHNE_GEBUEHR_SATZ`), angehängt nur vor dem Stichtag (`mitBarAusnahme`, `servicegebuehrZahltKunde`; der eine Datumsvergleich ist `vorBarStichtag`). Hof-Sätze „… holt/nimmt die Monatsabrechnung“ nur nach `gebuehrFuerMonatsabrechnung` (Bestellansicht, Dialog „Artikel fehlt“); der Gebührenhinweis vor dem Bestellen (Hofseite, Produktseite, Mini-Warenkorb) nur über `gebuehrHinweisFuerHof` — vor dem Stichtag mit Bar-Ausnahme bzw. gar nicht, wenn der Hof nur bar anbietet. `konditionen.ts` bindet `servicegebuehr.ts` nicht ein (umgekehrt schon) — Wiener Tage stehen deshalb in `src/lib/wiener-tag.ts`, `centsAlsEuro` in `format.ts`, der Satz für neue Höfe in `konditionen.ts`; `servicegebuehr.ts` reicht alles weiter.
- **„Artikel fehlt" (E14, seit Nr. 19).** Was gerechnet wird, entscheidet `artikelFehltRechnung` (`src/lib/artikel-fehlt.ts`): Gebühr auf den verbleibenden Warenwert mit Satz und Mindestgebühr DER BESTELLUNG (`serviceFeePercentApplied`, `serviceFeeMinCentsApplied`, den der Checkout seit Nr. 19 schreibt; Altbestellungen ohne Snapshot: lag die Gebühr über dem Prozentanteil, war sie die Mindestgebühr, sonst € 0,50) über `berechneServicegebuehr`, nie über der bisherigen Gebühr; bar neuer Betrag = Rest + neue Gebühr, online Erstattung = Artikelpreis + Gebührendifferenz, vom Hof genau der Artikelpreis. Die Bestellung trägt danach den AKTUELLEN Stand: `totalAmount` = verbleibender Warenpreis, `serviceFeeCents` = neue Gebühr (Monatsabrechnung, Umsatz, Mails und Storno lesen ihn ohne Sonderweg), `erstattetCents` = Summe der von Stripe BESTÄTIGTEN Teilerstattungen, `OrderItem.fehltSeit` an der Position (ihre Snapshots bleiben). Nach dem Überschreiben gilt rechnerisch bezahlt = `totalAmount` + `serviceFeeCents` + `erstattetCents` — die Datenbank erzwingt das nicht; es folgt daraus, dass jede Rechnung vom gesperrten aktuellen Stand ausgeht und die neue Gebühr nie über der alten liegt. Einzige Ausnahme: Eine nachgetragene Erstattung, die Stripe von einem älteren Stand aus gebucht hat, wird mit ihrem gebuchten Betrag eingetragen (Sentry `erstattung_abweichend` nennt den Unterschied). Der Schema-Kommentar zu `erstattetCents` nennt noch die alte Grenze (`totalAmount + serviceFeeCents`). Fehlt der letzte Artikel, ist es ein normaler Storno. Ein fehlender Artikel geht NICHT zurück in den Vorrat, auch nicht beim Storno danach (er war nie da); Heute, Packliste und Papier zeigen ihn nicht, Kundenseiten mit „fehlt leider · nicht berechnet". **Reihenfolge (Ausnahme von „erst bedingt schreiben, dann Stripe"):** `meldeFehlendenArtikel` (`src/server/artikel-fehlt.ts`) sperrt die Bestellzeile (`SELECT … FOR UPDATE`, `farmId` in der Bedingung), liest, ruft Stripe INNERHALB der Sperre (Schlüssel `teilstorno-<orderId>-<itemId>` bzw. `teilstorno-hof-<orderId>-<itemId>`) und schreibt erst danach bedingt auf den gelesenen Stand. Vorher trägt sie Erstattungen nach, die Stripe gebucht hat, die Datenbank aber nicht kennt (verlorene Antwort, abgelaufene Transaktion; höchstens `NACHTRAGEN_HOECHSTENS` je Meldung) — mit dem gebuchten Betrag, die gemeldete Position danach vom berichtigten Stand. So vermerkt die Datenbank nie eine Erstattung, die Stripe nicht bestätigt hat, und keine Position wird zweimal erstattet; ein Stripe-Fehler rollt alles zurück (derselbe Knopf versucht es erneut und findet eine schon erfolgte Erstattung). **Zeitgrenze, Pflicht für jeden Stripe-Aufruf in einer Sperre:** Request-Optionen `STRIPE_OPTIONEN` (`maxNetworkRetries: 0` — sonst wiederholt das SDK still zweimal —, `timeout` 4 s), höchstens `STRIPE_AUFRUFE_HOECHSTENS` Aufrufe; die Transaktion (`TRANSAKTION_MS`) ist deren Summe plus 10 s für die Datenbank, dazu höchstens `VERBINDUNG_WARTEN_MS` Warten auf eine Verbindung. Die Seiten, deren Server Actions solche Transaktionen halten (`/orders`, `/orders/[orderId]`), setzen `export const maxDuration` über diese Summe (60 s; `tests/teilerstattung.test.ts` prüft die Rechnung). Läuft sie trotzdem ab, trägt der nächste Versuch nach, und zwei gleichzeitige Meldungen rechnen nacheinander vom jeweils aktuellen Stand — ohne Sperre erstattete die zweite die Gebührendifferenz doppelt (Gegenprobe in `tests/integration/artikel-fehlt.int.test.ts`). Die Mail an die Kundin (`sendArtikelFehlt`) geht nach dem Schreiben über `nachDerAntwort`. Der Storno liest Beträge und Positionen frisch UNTER der Sperre seines Statuswechsels (`tx.order.findFirst` nach dem `updateMany`).
- **Der PaymentIntent entsteht mit festem Stripe-Schlüssel `pi-<Bestell-ID>` und Parametern aus der GESPEICHERTEN Bestellung** (`intentParameter` in `src/app/api/checkout/route.ts`) — nie ungeschützt: Bestellung und Bestand stehen dann schon. Scheitert Stripe, wird die Bestellung über `storniereUnbezahlteBestellung` beendet und der Checkout antwortet 503 `ZAHLUNG_NICHT_MOEGLICH`; ein Stripe-409 (derselbe Schlüssel läuft gerade) ist kein Ausfall. Die Intent-ID wird nur an eine noch offene Bestellung gehängt (`haengeIntentAn`), sonst wird der Intent abgebrochen. Eine Wiederholung ohne gespeicherte Intent-ID holt mit demselben Schlüssel denselben Intent; nach zwei Minuten gilt sie als gescheitert — die Stripe-Aufrufe bleiben mit kurzem Timeout darunter.
- **Stripe ist Pflicht für jeden Hof (Register Z1).** Kein Server-Weg schreibt `Farm.acceptsOnline` auf etwas anderes als true (alles unter `src/server`, API-Routen, `src/lib`, die Einstellungs-Formulare; `tests/stripe-pflicht.test.ts` wacht am Quelltext) — eine Wahl „nur bar" gibt es nicht. Auf true setzen es nur `createConnectAccount`, `createOnboardingLink` (wer Stripe einrichtet, will online kassieren) und `schalteOnlineZahlungEin` (Bestandshof mit fertigem Stripe, `/settings/payments`; Zod `onlineZahlungEinschaltenSchema`, Besitz in der WHERE-Klausel), immer nur für den eigenen Hof. Gelesen wird das Feld weiter (Checkout, Notbremse `onlineZahlungPausiert`, Admin-Kennzeichen „Online-Zahlung aus"). Freischalten verlangt Stripe (`freischaltSperre`). Texte zur Pflicht nur aus `konditionen.ts` (`ONLINE_ZAHLUNG_EINRICHTEN_SATZ`, `ONLINE_ZAHLUNG_START_SCHRITT`).
- **`Farm.stripeAccountReady` schreibt nur `stripeKontoBereit`** (`src/lib/stripe-konto.ts`: Zahlungen UND Auszahlungen frei) — beim Onboarding, bei „Status prüfen" und bei `account.updated`. Connect-Events kommen über einen eigenen Stripe-Endpunkt mit eigenem Secret an dieselbe Webhook-Route; sie prüft gegen `STRIPE_WEBHOOK_SECRET` und `STRIPE_CONNECT_WEBHOOK_SECRET`. Ereignisse mit `event.account` laufen nur durch `account.updated`, und das liest den aktuellen Kontostand bei Stripe nach (Ereignisse kommen nicht garantiert in Reihenfolge).
- **Jede Erstattung trägt einen festen Idempotenz-Schlüssel je Bestellung und Anlass** (`storno-<id>`, `storno-hof-<id>` für die Rückbuchung des Reststornos, `teilstorno-<id>-<positionId>` und `teilstorno-hof-<id>-<positionId>`, `servicegebuehr-nicht-abgeholt-<id>`, `spaet-bezahlt-<id>`): Erreicht ein zweiter Aufruf Stripe, kommt dieselbe Erstattung zurück, keine zweite.
- **Ein Stripe-Ereignis ändert eine Bestellung nur aus dem Zustand, für den es gilt** — bedingtes `updateMany` wie oben, nie Lesen und blind Schreiben (`src/app/api/stripe/webhook/route.ts`).
  - `payment_intent.payment_failed` ist kein Endzustand, der PaymentIntent bleibt bezahlbar: nur `paymentStatus` FAILED vermerken, nie stornieren, nie Bestand.
  - Endgültig ist `payment_intent.canceled`. Ohne den Hof (Webhook, Aufräumrunde) beendet eine unbezahlte Bestellung nur `storniereUnbezahlteBestellung` (`src/server/unbezahlte-bestellung.ts`): Storno aus PENDING_CONFIRMATION, Gebühren-Vermerk und Rückbuchung in einer Transaktion. Der Hof storniert über `cancelOrder`.
  - `payment_intent.succeeded` setzt PAID nur aus PENDING_CONFIRMATION. Trifft es eine Bestellung, die storniert wurde, ohne je bezahlt gewesen zu sein: sofort voll erstatten (Regel oben), Sentry-Alarm, Mail an die Kundin — nie wiederbeleben. Einzige Ausnahme von „erst bedingt schreiben, dann Stripe": Hier kommt die Erstattung vor dem bedingten Vermerk REFUNDED, weil der Vermerk erst stehen darf, wenn das Geld zurück ist. Vor doppelter Erstattung schützt der Schlüssel, der Vermerk sperrt die Mail.
- **Scheitert die Erstattung eines Stornos, bekommt der Hof nie eine Anweisung, die er nicht ausführen kann** (er hat keinen Zugang zum Plattformkonto): Text „Rückerstattung fehlgeschlagen. Wir kümmern uns um die Erstattung und melden uns.", dazu Sentry und eine Mail an den Betreiber (`sendErstattungOffen` an `SUPPORT_EMAIL`, nach der Antwort, ohne Daten der Kundin). Die Handanweisung folgt dem Weg, der wirklich genommen wurde (`handbuchungFuer`: Rest mit festen Beträgen aus `rest`, Vollerstattung oder „Stand unbekannt"), nie pauschal der Vollerstattung.
- **Auch die Vollerstattung des Stornos trägt Merkmale** (seit Nr. 27): `metadata` aus `vollstornoMerkmal` (`orderId`, `anlass: 'vollstorno'`, `art: 'kunde'`), Schlüssel weiter `storno-<id>`. Sie zählt nie als Teil- oder Rest-Storno (`ordneZu` gibt null — taucht sie daneben auf, bleibt das Bild „unklar"). Gibt `refunds.create` eine Erstattung mit Status `failed`/`canceled` zurück, gilt sie wie bei der Teilerstattung nicht als erstattet (kein REFUNDED, Weg „Erstattung offen"); der Storno setzt dann den Meldevermerk `<refundId>#gescheitert-gemeldet` (Voll- und Rest-Storno), damit ein späteres `refund.failed` derselben Erstattung nicht ein zweites Mal meldet. Sie läuft ohne `STRIPE_OPTIONEN`, weil sie in keiner Sperre steht (die SDK-Wiederholung mit demselben Schlüssel ist dort erwünscht).
- **Eine später gescheiterte Erstattung** (`refund.failed`, `charge.refund.updated`; `src/server/erstattung-gescheitert.ts`) wird nur zurückgenommen, wenn sie nachweislich unsere ist: Merkmale in `metadata` (`ordneZu`) UND die Bestellung gehört zur Zahlung der Erstattung. **Eine gescheiterte Vollerstattung** (`anlass: 'vollstorno'`) nimmt den Zahlstand zurück, nie einen Betrag: REFUNDED → PAID bedingt auf storniert, REFUNDED und `erstattetCents` 0, nur wenn ihr Betrag genau Warenpreis + Gebühr ist und Stripe (eine Seite `refunds.list`, `STRIPE_OPTIONEN`) keine weitere zählende Erstattung kennt (`zuruecknahmeNachGescheiterterVollerstattung`); Vermerk und Meldung wie unten. Eine Vollerstattung ohne Merkmale (vor Nr. 27) bleibt „fremd": nur gemeldet. Zurückgenommen wird nicht durch Senken um den Betrag, sondern bedingt auf Stripes Summe der zählenden, zugeordneten Erstattungen, und nur wenn die Datenbank genau um die gescheiterte darüber liegt (`zuruecknahmeNachGescheiterterErstattung`) — so ist es je Erstattung idempotent, auch bei beiden Ereignissen und erneuter Zustellung. `paymentStatus` REFUNDED → PAID bedingt. Die Erstattung des Ereignisses zählt dabei nie mit, auch wenn `refunds.list` sie noch als `pending` führt (`ladeStripeStand(…, { gescheitert })`) — das Ereignis ist verbindlich. Jeder Ausgang außer „nicht gescheitert“ wird genau einmal je Erstattung gemeldet, auch „schon erledigt“ (nie gezählt, das Geld steht trotzdem aus); Vermerk `<refundId>#gescheitert-gemeldet` in `WebhookEvent` — die Zurücknahme legt ihn in derselben Transaktion an (`createMany` mit `skipDuplicates`) und meldet immer, alle anderen Ausgänge melden nur, wenn sie den Vermerk als Erste anlegen. Ein unklares Bild (auch eine Zahlung ohne Überweisung, `ohne_ueberweisung`) antwortet 200 mit Meldung, nie 500 ohne Meldung.
- **Im Webhook kein Mailversand im Antwortpfad.** Mails laufen über `nachDerAntwort`, jede einzeln abgefangen. Eine 500 heißt für Stripe „erneut zustellen" — sie ist nur erlaubt, wenn Daten oder Geld nicht verarbeitet sind, sonst gehen die Mails doppelt raus.
- **Was ein Storno an Geld bewegt, rechnet `src/lib/storno.ts`** — dieselbe Funktion für den Storno-Dialog und für `cancelOrder`. Wer den Ladungstyp im Checkout ändert, ändert den Storno mit; `tests/storno-erstattung.test.ts` (Ladungstyp-Wache) schlägt sonst an.

### Taxonomie (Kategorien, Unterkategorien, Siegel)

`src/lib/taxonomie.ts` ist die **einzige** Quelle für Werte und Labels. Kein zweites Label-Verzeichnis, kein Hof-Sonderfall anderswo. Anzeige nur über `formatKategorie` in `format.ts`.

- **Jede Unterkategorie (L2) gehört zu genau einer Kategorie (L1).** `gehoertZu(l1, l2)` entscheidet; das Zod-Schema lehnt jede andere Kombination ab. Einzige Ausnahme: `VORBEREITETE_UNTERKATEGORIEN` — Werte, die schon im Prisma-Enum stehen (Expand), aber noch zu keiner L1 gehören (seit Nr. 20 leer). `gehoertZu` sagt für sie immer false, damit lehnt Zod sie ab und nichts bietet sie an. Wer sie wählbar macht, verschiebt sie in `TAXONOMIE` und leert die Liste. Fisch, Brot, Getränke, Sonstiges, Mischfutter und Ergänzungsfutter haben keine L2; Brennholz hat seit Nr. 20 die Arten Brennholz (Scheite), Anzündholz, Hackschnitzel (E11). Keine dritte Ebene, keine Freitext-Kategorien. Der Enum-Wert `BRENNHOLZ` heißt in der Oberfläche „Brennmaterial" (`KATEGORIE_LABEL`, E11 Label seit Nr. 23) — Chips, Abschnitte und Filter nehmen das Label, nie ein eigenes Wort.
- **Eine fehlende L2 ist kein Fehler.** Bestandsprodukte dürfen ohne bleiben; das Formular zeigt nur einen Hinweis. Einzige Ausnahme: Futter-Kategorien mit Sorten (Heu & Stroh, Getreide & Körner).
- **Siegel sind orthogonal zur Kategorie.** `labels` ist eine Menge (BIO, GENTECHNIKFREI, AMA_GUETESIEGEL), mehrere je Produkt, keines Pflicht, keines doppelt. `isOrganic` ist Altlast: wird nur noch gelesen, nie mehr geschrieben; Bio ist `labels` enthält BIO.
- **Neue Produkte brauchen eine Kategorie** (`productAnlegenSchema`) — ohne landen sie im Bereich Sonstiges zwischen den Lebensmitteln. Bestandsprodukte ohne Kategorie bleiben speicherbar; die Produktliste zeigt einen Chip. Nachtragen aus der Liste nur über `setzeKategorie` (schreibt Kategorie, Unterkategorie, MwSt-Vorbelegung, nur solange die Kategorie leer ist) — nie über `updateProduct` mit Listendaten, das schriebe einen veralteten Bestand zurück.
- **Kategorie-Vorschlag ist nie eine Wahl.** `kategorieVorschlag(name)` in `taxonomie.ts` liefert nur bei genau einem eindeutigen Treffer etwas; Wörter aus `DUAL_USE` nie. Übernommen wird erst mit einem Tipp; Futtermittel nie mit einem Tipp aus der Liste (Kennzeichnung fehlt).
- **Futter-Kennzeichnung nur im Bereich Futtermittel.** Dort Pflicht (Futtermittelart passend zur Kategorie, Nettomenge, Tierarten, Zusammensetzung, analytische Bestandteile, Bestätigung), sonst verboten. Ein Kategoriewechsel aus dem Bereich heraus löscht sie in derselben Transaktion wie das Produkt-Update.
- **Pflicht-Bestätigung des Hofs (E10a, seit Nr. 23).** Wortlaut `FUTTER_BESTAETIGUNG_TEXT`, Zeitpunkt in `FutterKennzeichnung.bestaetigtAm`. Beim Anlegen verlangt das Schema den Haken (`futterKennzeichnungSchema`, Futter-Formular). Beim Bearbeiten entscheidet der Server mit dem gespeicherten Stand: `updateProduct` vergleicht, was es schreiben würde (`produktDaten`, `futterDaten`), mit genau diesen Spalten aus der Datenbank (`brauchtNeueBestaetigung` in `src/lib/futter-registrierung.ts`); ändert sich etwas außer `OHNE_NEUE_BESTAETIGUNG` (Preis, Vorrat, Sichtbarkeit, Foto) und fehlt der Haken, antwortet es mit Code `BESTAETIGUNG` und schreibt nichts. Ohne Änderung bleibt der alte `bestaetigtAm`. Der Haken wird beim Bearbeiten nie vorbelegt. Ein neuer Schreibweg auf Futter-Angaben fragt dieselbe Funktion.
- **Futter-Texte für Hof und Kundin aus EINER Quelle** (`src/lib/futter-registrierung.ts`): Haken, Kopfhinweis „zur Orientierung" samt BAES-Adresse (`BAES_FUTTERMITTEL_URL`, nur dort), Verantwortungs-Hinweis für Kundinnen (`futterVerantwortung`, im Korb `futterVerantwortungImKorb` — reine Anzeige, ändert nie die Warenkorb-Prüfung). `tests/futter-bestaetigung.test.ts` sucht die Wortlaute im Quelltext.

### Bereiche (Lebensmittel, Futtermittel, Sonstiges)

Konzept: `docs/konzepte/bereiche.md`.

- **Bereich ist abgeleitet.** `bereichVon(category)` in `taxonomie.ts` entscheidet. Nie als Spalte, nie in `localStorage`, nie `category === '…'` vergleichen, wo der Bereich gemeint ist. Im Browser nur zur Anzeige und Formularführung (dieselbe Funktion) — verbindlich prüfen Zod und die Servergrenze.
- **Angezeigt werden zwei Bereiche: „Hofladen" und „Futtermittel".** `anzeigeBereichVon` und `ANZEIGE_BEREICHE` in `taxonomie.ts` (Hofladen = Lebensmittel + Sonstiges). Das Label steht nur dort — nie „Lebensmittel" als Bereichsname in der Oberfläche, keine zweite Label-Tabelle.
- **Kaufbar heißt: sichtbar UND freier Bestand > 0** — `istKaufbar` in `src/lib/bereiche-anzeige.ts`. Chips, Suche, Facetten, Karte und Kilopreis-Sortierung fragen nur dort.
- **Verkaufsgrößen sind eine Produktfamilie (E3, seit Nr. 20).** Je Größe ein Produkt mit eigenem Preis, `stock` und eigener Kennzeichnung (Nettomenge je Gebinde); zusammengehalten von `Product.familieId` (vom Server vergeben, kein Fremdschlüssel). Angelegt wird eine Familie in EINER Transaktion über `legeFutterFamilieAn` bzw. `legeBrennmaterialFamilieAn` (`src/server/actions/produktfamilie.ts`, Schemas `src/schemas/produktfamilie.ts`); der Name je Größe ist `groessenProduktname` (Familie + Größe), bearbeitet wird je Größe im Produktdialog. Neue Futtermittel entstehen nur so — `createProduct` lehnt Futter ab, `updateProduct` den Wechsel eines Nicht-Futter-Produkts auf eine Futter-Kategorie (beide `FUTTER_NUR_UEBER_FORMULAR`); der Produktdialog bietet die Futter-Kategorien dann gar nicht an. Ein Futtermittel ohne Verpackung ist damit immer Altbestand.
- **Sperre je Gebinde (E10, S7, seit Nr. 20).** Welche Registrierung ein Gebinde braucht und ob der Hof sie hat, entscheidet nur `gebindeSperre` (`src/lib/futter-registrierung.ts`): Verpackung `LOSE_BALLEN` → LFBIS (eine Nummer am Hof), `ABGEPACKT_ETIKETT` sowie Mischfutter und Ergänzungsfutter → BAES (Status Registriert/Zugelassen). Produkte ohne Verpackung (Bestand) sperrt sie nie. Durchgesetzt mit dem Stand des Hofs FRISCH aus der Datenbank (`ladeHofRegistrierung`) an allen Wegen in den Shop: beim Anlegen (gesperrte Größen entstehen als Entwurf), am Schalter „Sichtbar" (`produktSichtbarkeitSetzen`, Code `GESPERRT`), beim Bearbeiten (`updateProduct` speichert gesperrt als Entwurf, `hinweis`), nach einem Wechsel von Nummer oder Status im Hofprofil (`nimmGesperrteAusDemShop`) und vor dem Checkout im Warenkorb-Abgleich (`pruefeSitzungsWarenkorb`: gesperrt = nicht verkäuflich). Die Plattform prüft die Nummer nicht (E9).
- **Behördenkontakt BAES — einzige freigegebene Ausnahme** zu „keine echten E-Mails oder Telefonnummern im Code" (CLAUDE.md; Freigabe Lauf 7 §11, Nr. 36): E-Mail und Telefon des BAES stehen nur in `BAES_KONTAKT` in `src/lib/futter-registrierung.ts`, Links und Vorlese-Texte werden daraus gebaut; `tests/futter-bestaetigung.test.ts` zählt die Vorkommen in `src/`, Tests prüfen nur über den Import. Jede weitere Ausnahme braucht eine eigene Freigabe des Menschen.
- **Ein Produkt gehört zu genau einem Bereich.** Dual-Use (Mais als Lebensmittel und als Futter) = zwei Produkte mit zwei Beständen, ohne Verknüpfung im Schema.
- **`OrderItem.vatRate` ist ein Snapshot.** Der Checkout-Handler schreibt ihn aus `Product.vatRate` im selben `create` wie die Bestellung. Nie nachlesen, nie rückwirkend ändern. `mwstStandard` ist nur die Vorbelegung im Formular.

Fachkonzepte liegen unter docs/konzepte/. Ein Sprint verweist auf sein Konzept, statt es zu wiederholen.
