# ARCHITECTURE

---

## 1. Schichten

```
UI            src/app/**/page.tsx, src/components/**
                 ↓ ruft auf, kennt keine DB
DOMAIN        src/lib/<fachregel>.ts        ← rein, ohne I/O, direkt testbar
SERVERGRENZE  src/server/actions/**  src/server/queries/**  src/app/api/**
                 ↓ einzige Schicht mit DB-Zugriff
DATEN         Prisma über @/lib/prisma
```

**Die eine Regel, aus der alle anderen folgen:** Fachliche Entscheidungen gehören in eine reine Funktion in `src/lib/`, die ohne Datenbank testbar ist. Die Servergrenze beschafft Daten, ruft die Entscheidung auf, schreibt das Ergebnis.

Vorbild: `src/lib/reservierung.ts` entscheidet (rein, 174 Tests ohne DB), `src/server/warenkorb.ts` wendet an, `src/app/api/checkout/route.ts` schreibt.

### Verboten
- **Keine** Prisma-Aufrufe in `src/components/**`.
- **Keine** Prisma-Aufrufe in `src/lib/<fachregel>.ts` (Ausnahmen: `prisma.ts`, `auth.ts` selbst).
- **Keine** Geschäftsentscheidung in einer React-Komponente (Rabatt, Frist, Verfügbarkeit, Preis).
- **Keine** Geschäftsentscheidung in einem API-Route-Handler. Handler = Eingang, Validierung, Aufruf, Antwort.
- **Kein** direkter Aufruf einer Server Action aus einer anderen Server Action, wenn die gemeinsame Logik in `lib/` gehört.

### `src/lib/` ist voll — Regel beim Hinzufügen
Zuerst `docs/ai/BAUSTEINE.md` (erzeugt mit `pnpm bausteine`) nach dem Stichwort durchsuchen: Gibt es die Datei, den Baustein oder die Funktion schon, wird sie benutzt oder erweitert, nicht neu geschrieben.

94 Dateien (Stand 2026-09-29), gemischter Zweck. Bevor eine neue entsteht:
1. Passt es in eine bestehende Datei? Dann dorthin.
2. Ist es eine **Fachregel**? → eigene Datei, rein, ohne Import von `prisma`/`auth`/`stripe`.
3. Ist es eine **Infrastrukturkapsel** (externer Dienst)? → `server-only` importieren.
4. Ist es ein **React-Hook**? → Präfix `use-` (`use-cart.ts`).

## 3. Server Action oder API-Route?

**Standard ist die Server Action.** API-Route nur bei einem dieser Gründe:

| Grund | Beispiel |
|---|---|
| Externer Aufrufer | Stripe-Webhook, Vercel Cron |
| Aufruf per Link (GET) — nur lesen oder weiterleiten, nie einen Zustand ändern; einzige Ausnahme Fristfreigabe beim Lesen (§5) | Bestätigungslink älterer E-Mails |
| Aufruf aus `fetch()` im Browser mit eigener Fehlerbehandlung | `/api/reserve`, `/api/checkout` |
| Nicht-JSON-Antwort | Export, Datei |

Sonst: Server Action. **Keine** API-Route bauen, nur weil das Muster vertraut ist.

### Pflichten jeder API-Route
1. Rate-Limit (`enforceRateLimit`) bei allem, was schreibt oder Bestand hält; auf den Wegen aus Register R1 zusätzlich die zweite Stufe über alle Instanzen (§5 „Zweistufige Bremse“). Eine eigene Grenze (`{ max }`, als Konstante mit Begründung) nur, wo der Aufrufer kein Mensch ist und die Vorgabe (20 je Minute und IP) echte Aufrufe abwiese — heute nur die Ein-Klick-Abmeldung (`EIN_KLICK_JE_MINUTE`).
2. Zod-Validierung des Bodys **und** der URL-Parameter.
3. Auth- bzw. Token-Prüfung, **fail-closed**: fehlt das Geheimnis, wird gesperrt, nicht geöffnet.
4. Antwortform nach `CODING_STANDARDS.md`.
5. Langsames über `nachDerAntwort()`.

### Triage-Routen: ein Token je Recht
Der Briefkasten hat zwei API-Routen, weil ihre Aufrufer extern sind (CLI, GitHub Action):

| Route | Token | Darf |
|---|---|---|
| `GET /api/triage/export` | `TRIAGE_TOKEN` | nur lesen |
| `POST /api/triage/status` | `TRIAGE_WRITE_TOKEN` (Rechner des Entwicklers) | `VERMUTLICH_WUNSCH`, `GEPLANT` — nur Art FEHLER |
| `POST /api/triage/status` | `TRIAGE_MERGE_TOKEN` (nur GitHub Actions) | `ERLEDIGT`, Wiederöffnen (`ERLEDIGT → GEPRUEFT`) |

- Ein Token je Recht, alle drei verschieden — sind zwei gleich, lehnt die Route alles ab. Ein Token, der für den Status nicht gilt → 403.
- Welcher Übergang erlaubt ist und was er schreibt, entscheidet `src/lib/triage-status.ts`; die Route liest, fragt dort und schreibt per `updateMany` auf genau den gelesenen Stand (sonst 409).
- Die Schreibroute schreibt nie Text, den ein Melder sieht, außer ihren festen Sätzen, und nie die Art. Body strikt: ein unbekanntes Feld ist 400.
- Den Merge-Token gibt es nie auf einem Rechner mit Agenten — abschließen kann nur das Deployment.

### Pflichten jeder Server Action
1. `'use server'` als erste Zeile.
2. Auth prüfen — **nie** der Eingabe vertrauen, wer der Aufrufer ist. Das Ergebnis gleich in der nächsten Anweisung auswerten: `if (!sitzung?.user) return …` bzw. `if ('error' in wache) return …` (oder `throw`), auch beim Ergebnis eines Helfers, der ohne Sitzung `null` gibt; wer bewusst ohne Sitzung weiterläuft, steht mit Grund in `SITZUNG_FREIWILLIG` (`tests/actions-sitzung-wache.test.ts`, seit Nr. 125).
3. **Besitz prüfen:** Gehört der Datensatz zum Hof des eingeloggten Nutzers? Jedes Mal.
4. Zod-Validierung des Arguments.
5. `revalidatePath()` für jede betroffene Route.

**Jeder Export einer `'use server'`-Datei ist ein öffentlicher Endpunkt** (eigene Aktions-ID), auch wenn ihn heute nur eine Route aufruft. Ein Weg, den nur ein Route Handler braucht (z. B. einen Link-Token ohne Sitzung einlösen), liegt in einem Server-Modul ohne `'use server'` — Vorbild `src/server/zustellung-bestaetigen.ts`; `tests/actions-sitzung-wache.test.ts` verlangt von jedem Export unter `src/server/actions/` eine erreichbare Sitzungsprüfung; öffentliche Wege (Token, Code, Bremse) stehen dort mit Grund in `OEFFENTLICH`.

**Öffentliche Server Action (ohne Anmeldung)** — Punkte 2 und 3 entfallen, dafür: Argument als `unknown` annehmen und mit Zod prüfen (Längengrenzen aus `src/lib/eingabegrenzen.ts`), Bremse je IP mit einer modulweiten `createRateLimiter`-Instanz und `getClientIp(await headers())` (`src/lib/rate-limit.ts`), wie `enforceRateLimit` nur bei `NODE_ENV === 'production'` (auf den Wegen aus R1 danach die zweite Stufe, §5 „Zweistufige Bremse“); das Limit als Konstante in einem reinen Modul, damit der Test es importieren kann (eine `'use server'`-Datei exportiert nur asynchrone Funktionen). Über dem Limit eine Antwort, die die Oberfläche ruhig behandelt — eine neutrale (`null`, leere Liste) bei reinen Hinweisen, `{ error, code: 'ZU_VIELE' }` bei Aktionen, auf die jemand wartet. Die Antwort verrät nichts, was der Aufrufer nicht schon weiß (keine Unterscheidung nach Freischaltung, Rolle, Bestand). Vorbilder: `checkSlugAvailability` (`src/server/actions/onboarding.ts`, neutral `null`, Antwort nur frei/vergeben), `loeseOrtAuf` (`hoefe.ts`, nur für die leere Liste als ruhige Antwort; Argument über `ortssucheSchema`), „Bestellungen finden" (`ZU_VIELE`).

### Die Admin-Prüfung: `src/server/admin-wache.ts`

Für den Betreiber-Bereich gibt es **eine** Antwort auf „darf dieser Mensch die
Plattform verwalten?", mit zwei Ausgängen:

| Wo | Aufruf | Verhalten |
|---|---|---|
| Admin-**Seite** (`src/app/admin/**/page.tsx`) | `await verlangeAdminSeite()` | nicht angemeldet → `redirect('/login')`, angemeldet ohne Recht → `notFound()`, Sitzung ≥ 12 h → abgemeldet und `/login/admin`, ohne Passkey → `/admin/einrichten`, Sitzung ohne Passkey (`passkeyAm` leer) → `/login/admin`, nicht abgemeldet |
| **Pflichtseite** `/admin/einrichten` | `await verlangeEinrichtenSeite()` | wie die Seite, aber die offene Pflicht öffnet sie (kein Passkey, nach Ersatzcode ohne neuen); bei erledigter Pflicht nur mit `passkeyAm`, sonst `/login/admin`; gibt `{ userId, pflicht }` zurück |
| Admin-**Aktion** (`'use server'`) | `await verlangeAdminAktion()` | `{ ok: true, userId } \| { error }` — die Antwortform der Actions |
| **Heikle** Admin-Aktion | `await verlangeFrischeBestaetigung()` als erste Anweisung, vor der Prüfung der Eingabe; im Browser nur über `useFrischBestaetigt(<Action>)` | alles von `verlangeAdminAktion`, dazu `passkeyAm` ≤ 5 min, sonst `{ error: 'frisch' }`. Welche: Zurücknehmen, Ablehnen, Gründung ausnehmen/wieder aufnehmen, Zusagen festschreiben, Testhof, Erstattung erledigt, Passkeys und Ersatzcodes; seit Nr. 154 (N20, Ergänzung 23.10.2026) auch Freischalten, Servicegebühr, „Gründungshof bis“, Rundschreiben senden, Startseite veröffentlichen und Empfänger der Zustellung hinzufügen — die Liste führt `HEIKLE_AKTIONEN` in `tests/frisch-bestaetigung-wache.test.ts`. Ruft eine Aktion mit eigener Wache denselben Weg (Bescheid an die Höfe in `setzeBuendelStandAction`), liegt der Weg ohne Wache in einem Server-Modul ohne `'use server'` (`verschickeRundschreiben`, `src/server/rundschreiben.ts`) |

- Beide lesen das Recht über `isAdminUser` **frisch aus der Datenbank**, nie aus
  der Session: `isAdmin` steckt bewusst nicht in den
  Better-Auth-additionalFields, damit ein zurückgenommenes Recht sofort greift.
- `notFound()` statt 403: Der Bereich gibt sich Unbefugten nicht zu erkennen.
- Die Prüfung steht in **jeder** Aktion, nicht nur in der Seite. Eine Seite
  schützt die Ansicht, eine Aktion schützt die Wirkung.
- **Layout `src/app/admin/layout.tsx` (seit Nr. 22f):** trägt die AdminShell und
  lädt Name und Zähler nur über `ladeAdminbereich` (`src/server/adminbereich.ts`),
  das als erste Anweisung `verlangeAdminSeite()` ruft — ein Layout rendert
  parallel zur Seite und darf Unbefugten keine Zähler zeigen. Die Seiten prüfen
  trotzdem selbst (`tests/admin-seiten-wache.test.ts`: jede `page.tsx` unter
  `src/app/admin`, Layout und Lader, AST mit Gegenproben); jede `route.ts` dort
  prüft als erste Anweisung oder steht mit Grund in `ROUTEN_OHNE_WACHE`, und
  nur `page` und `route` liefern unter `/admin` eine Adresse aus.
- Im Admin gibt es keine Hofzugehörigkeit — das Admin-Recht **ist** die
  Besitzprüfung. Keine eigene Fassung daneben bauen: Vorher lag die Frage an
  vier Stellen und in zwei Implementierungen.

### Admin-Anmeldung: nur mit Passkey (Register N20, seit Nr. 115)

- **Plugin** `@better-auth/passkey` in `src/lib/auth.ts`, Client NUR in `src/lib/auth-client-passkey.ts` (Admin-Seiten und der Dialog „Mit Passkey bestätigen"). `rpID`/`origin` kommen geschützt aus `UMGEBUNG.appUrl` (`passkeyAdresse`): unlesbar → `hooks.before` antwortet auf `/passkey/*` und die Ersatzcode-Anmeldung mit 503, alles andere läuft. Ein Passkey gilt nur unter der Adresse, unter der er entstand (Vorschau: Branch-Adresse).
- **Nutzerprüfung** (Fingerabdruck, Gesicht, PIN) erzwingen die beiden `afterVerification` (`userVerified`), nicht das Plugin — es prüft mit `requireUserVerification: false` und fragt beim Anmelden nur „preferred".
- **Registrierung** nur in den Fällen a–c (`registrierungsFall`, `src/lib/admin-anmeldung.ts`), geprüft in `hooks.before` auf BEIDEN Pfaden (`generate-register-options`, `verify-registration`): (a) erster Passkey — kein Passkey, `adminSeit` ≤ 24 h, Sitzung ≤ 15 min mit Passwort, E-Mail-Code dieser Sitzung bestätigt (`EinmalLink`, Zweck `admin-einrichten:<Sitzung>`, Hash über Zweck, Konto und Code); (b) nach Ersatzcode genau EINER — `afterVerification` verbraucht den Anspruch per bedingtem `updateMany` auf der Sitzung (`anmeldeart` `ersatzcode` → `ersatzcode-eingeloest`); (c) weiterer — `passkeyAm` ≤ 5 min, nie in einer Sitzung aus einem Ersatzcode. Jede Registrierung setzt `passkeyAm`. `delete-passkey`/`update-passkey` stehen in `disabledPaths`; Entfernen nur über `entfernePasskey` (frisch, Kontozeile per UPDATE gesperrt, nie der letzte).
- **Anmeldeart und `passkeyAm`** entstehen atomar mit der Sitzung in `databaseHooks.session.create.before` — der Hook bekommt den Endpunkt-Kontext mit `path` (`anmeldeartFuerPfad`); die Felder stehen in `session.additionalFields` mit `input: false` (sonst setzte `/update-session` sie).
- **Frische Bestätigung = erneute Anmeldung mit Passkey.** `hooks.before` auf `/passkey/verify-authentication`: Gibt es eine Sitzung, muss `response.id` ein Passkey DIESES Kontos sein, sonst 401 vor dem Endpunkt (keine Sitzung, kein Cookie). Nach Erfolg löscht `hooks.after` die alte Sitzung — nur wenn sie demselben Konto gehört. Oberfläche: `useFrischBestaetigt(aktion)` (`src/components/admin/frisch-bestaetigen.tsx`) öffnet bei `{ error: 'frisch' }` den Dialog und wiederholt die Aktion genau einmal; die CSV-Exporte antworten mit 303 auf `/admin/bestaetigen?weiter=` (`frischOderBestaetigen`, nur Pfade unter `/admin`).
- **Pflicht „erst Passkey"** prüft jede Seite selbst (`verlangeAdminSeite()` ohne Argument); nur `/admin/einrichten` ruft `verlangeEinrichtenSeite()` (`verlangeAdminSeite` nimmt keine Optionen), ihre Actions `{ ohnePasskey: true }`, `ladeAdminbereich` ruft `verlangeAdminShell()` (scheitert gleich, sagt `inhaltOffen`) — im Pflicht-Zustand und in einer Sitzung ohne Passkey ohne Zähler. Pflicht = kein Passkey oder der zuletzt benutzte Ersatzcode ist jünger als der jüngste Passkey.
- **Sitzung mit Passkey:** Ohne `ohnePasskey` verlangt die Wache nach der Pflicht auch `passkeyAm` dieser Sitzung (gesetzt nur durch Anmeldung mit Passkey und Einrichten in der Sitzung); sonst Seite → `/login/admin` ohne Löschen, Aktion → `ADMIN_AKTION_FEHLER.ohnePasskey`. Das gilt auch für die Pflichtseite, sobald die Pflicht erledigt ist: Kein Admin-Kopf und kein Zustand „eingerichtet" in einer Sitzung ohne Passkey.
- **Sperren** für ein Admin-Konto mit Passkey (auch für seinen Hof): `/sign-in/email` antwortet und zählt wie ein falsches Passwort, `/request-password-reset` antwortet wie bei einer unbekannten Adresse ohne Link, „Das war ich nicht" ruft keinen Passwort-Link. Ersatzcodes: 10 je Konto, nur als HMAC (`src/lib/ersatzcodes.ts`), Anmeldung über den eigenen Endpunkt `/admin-ersatzcode/anmelden` (Bremse 5 je Adresse und Stunde, fail-closed, bedingt verbraucht). Mails: `src/emails/admin-sicherheit.tsx`, ohne Link zum Anmelden.

## 4. Datenfluss

### Lesen
```
Server Component → src/server/queries/*  → Prisma → Props → Komponente
```
- Standard ist die Server Component.
- `'use client'` nur bei Interaktivität (State, Event-Handler, Browser-API).
- `'use client'` so tief wie möglich im Baum — nie ein ganzes Layout zur Client-Komponente machen.
- Serialisierbarkeit beachten: `Decimal` und `Date` nicht roh in Client-Komponenten reichen (→ `CODING_STANDARDS.md`).

### Schreiben
```
Client-Komponente → Server Action → Zod → Fachregel (lib) → Prisma → revalidatePath
```

### State-Regeln
| Art | Wo | Nicht |
|---|---|---|
| Server-Daten | Server Component, per Props | Nicht in Client-State spiegeln |
| Formular | `react-hook-form` | Kein `useState` je Feld |
| UI-lokal (offen/zu) | `useState` | Nicht global |
| Warenkorb | `use-cart.ts` (localStorage) + serverseitige Reservierung; der Speicher nur über `src/lib/warenkorb-speicher.ts` (ein Schlüssel, Zod, Ereignis `WARENKORB_EREIGNIS` nach jedem Schreiben) | Warenkorb ist **nie** die Wahrheit über Verfügbarkeit. Kein zweiter Zugriff auf den Schlüssel (`tests/warenkorb-speicher.test.ts`). Keine Änderung auf `items` des Renders: Jeder Schreibweg geht über `persist((vorher) => …)` auf dem Stand der letzten Änderung — sonst überschreiben sich Aufrufe hintereinander aus demselben Render (Nachbestell-Link, seit Nr. 71, `tests/use-cart.test.ts`). `useCart` nur in der Produktliste der Hofseite und auf der Produktseite; Kasse und Kopfzeile lesen ohne useCart (`leseWarenkorb`, `useWarenkorbKopf`) – ein zweiter `useCart` führte still einen zweiten Korb (Regelvorschlag 128, 21.10.2026; tests/use-cart-wache.test.ts). |
| Filter/Suche in URL | `useSearchParams` lesen, Zod-Schema in `src/schemas/` parst und verwirft Ungültiges still; schreiben mit `window.history.replaceState(null, …)` (Next gleicht `useSearchParams` ab, kein Server-Roundtrip je Tipp — mit `window.history.state` als Zustand gleicht Next NICHT ab) oder `router.replace`, wenn der Server neu rendern soll. Filter sind echte Links (`FilterChip`); wendet die Seite sie selbst an, schreibt der `onNavigate` des Links per `replaceState` und ruft `preventDefault()`, `prefetch` ist dann aus (Vorbild `/hoefe`, `beimNavigieren` in `src/components/hoefe/entdecken-teile.tsx`). **Auf einer statischen Seite nie `useSearchParams`** — es zeichnete alles bis zur nächsten Suspense-Grenze nur im Browser; dort liest ein Speicher über `useSyncExternalStore` die Adresse (Server-Wert `null` = leerer Filter); `replaceState` geht nur über ihn, damit er die Änderung meldet, Zurück/Vor meldet `popstate`, Nexts eigenes `pushState` die Navigation API (`currententrychange`, wo vorhanden) (Vorbild `src/components/hoefe/use-hoefe-adresse.ts`, Register N19). Ergeben die Filter einer öffentlichen Seite beliebig viele Adressen, tragen ihre Links `rel="nofollow"` (`FilterChip` mit `nofollow`), und die Seite ist statisch oder die Adressen mit Parametern stehen in robots.txt | Nicht nur im State — Ergebnisse müssen teilbar sein. **Nie** Standort/Koordinaten in die URL |
| Ansicht von Mein Hof unter lg („Bearbeiten · So sieht’s die Kundin", seit Nr. 49) | Adresse `?ansicht=kundin` (Zod `src/schemas/mein-hof-ansicht.ts`, Regeln `src/lib/mein-hof-ansicht.ts`), gelesen über `useSearchParams` in `MeinHofAnsicht`, geschrieben per `replaceState(null, …)` über `ansichtAdresse`; „Ansehen" von einer anderen Seite über `kundinAdresse`; das iframe hängt nur ein, wo der Umschalter zu sehen ist (`useSchmalerAls`, `src/lib/use-mindestbreite.ts`: `useSyncExternalStore` mit `matchMedia`, Server und Hydrieren sagen „nein") | Nicht nur im State: „Ansehen" nach dem Veröffentlichen eines Beitrags führt von `/status/new` direkt in die Kundenansicht. Die Reiter-Links tragen die Ansicht nicht weiter — jeder Reiter beginnt mit „Bearbeiten" |
| Auftrag in der URL (Dialog öffnen) | `?neu=1` / `?edit=<id>` über `useUrlAuftrag` (`src/lib/use-url-auftrag.ts`): liest `useSearchParams` (Zod: `src/schemas/url-auftrag.ts`), führt den Auftrag einmal aus und nimmt ihn per `replaceState` aus der Adresse | Nicht die `searchParams` der Seite als Startwert — ein zweiter Auftrag auf derselben Seite (Plus bei offenem `/products`) käme nie an. Nie einen Dialog nur für die URL bauen: der vorhandene öffnet |
| Theme | `next-themes`, `ThemeProvider` in `src/app/layout.tsx` (`attribute="data-theme"`, `defaultTheme="system"`; Inline-Skript vor der Hydration, Regeln in `docs/ai/DESIGN_SYSTEM.md`) | Kein eigener Provider, keine Spalte in der Datenbank — die Wahl gehört dem Gerät |
| Gemerkter Foto-Weg | localStorage, nur über `src/lib/foto-weg-speicher.ts` (ein Schlüssel, Zod: `src/schemas/foto-weg.ts`, nichts wirft); ob gesetzt oder gelöscht wird, entscheidet `merkerNachErgebnis` in `src/lib/foto-wege.ts` | Kein zweiter Zugriff auf den Schlüssel, keine Spalte in der Datenbank — der Weg gehört dem Gerät |

Seit Nr. 30 verlangt jede dieser drei Regeln `teilenMomenteAus` als Pflichtfeld — der Schalter `Farm.teilenMomenteAus` kommt aus der Seitenabfrage (`getHeute`, `getProdukteSeite`; ohne Hof „aus“), geschrieben nur über `setzeTeilenMomente` (`/settings/teilen`). Der Browser beantwortet nur noch „schon gezeigt?“. Ohne lesbaren Speicher kommt er nicht (höchstens einmal) | Kein Cookie: Der Moment ist ein Overlay nach der Hydration, nichts rutscht nach. **Ein Client mit automatischem Speichern (Admin › Startseite, `useStartseitenEntwurf`) übernimmt neue Props nach dem ersten Rendern nie still in seinen Zustand**, nur die Antwort der eigenen Action — ein `revalidatePath` auf die eigene Seite setzte sonst offene Eingaben mitten im Speichern zurück; der Prüfstand-Test „neue Props → Liste bleibt“ in `tests/startseite-entwurf.test.ts` hält es fest.

**Ein Fehlerzustand beim automatischen Speichern wird durch jede Aktion verlassen, die den Entwurf wieder gültig macht** (Verwerfen eines neuen Blocks, Löschen, Übernehmen einer Fassung, eine neue Speicherung): „Speichern vor dem nächsten Schritt“ (`speichereSofort`) speichert nach einem Fehler neu, statt den alten Fehler zurückzugeben, und gibt den Grund dieses Laufs zurück (`{ ok, fehler }`), nie den Stand aus dem Render davor. **Vor jeder Action, die den Entwurf ersetzt oder einen Block entfernt, wird gewartet:** Uhr löschen bzw. das Wartende speichern und eine laufende Speicherung abwarten (`halteAn`, `entferneBlock`) — sonst legt sie danach einen verworfenen Block an oder überschreibt den übernommenen Stand. Listen, in die nach einer Speicherung etwas eingefügt wird, baut der Hook aus seiner Ref (nur die Einfügestelle kommt von außen). Beim Aushängen geht eine wartende Änderung sofort hinaus; solange „Speichert …“ steht oder ein nie gespeicherter neuer Block offen ist, fragt `beforeunload` nach (Nr. 183, Prüfstand `tests/startseite-entwurf.test.ts`).

### Schwere Module nur dynamisch (seit Nr. 31)
- **Kein Seitenmodul zieht E-Mail-Versand oder Stripe statisch mit** — auch nicht über eine Server Action, die eine Client-Komponente der Seite einbindet (sie landet in den Server-Chunks der Seite). Resend, `@react-email/*`, `src/emails/*`, das Stripe-SDK und die Sammelmodule `src/lib/email.ts` und `src/lib/stripe.ts` kommen per `await import()` erst dort, wo gesendet bzw. Stripe gefragt wird: in der Versandfunktion, der Action, dem Zweig. Vorlage: `const { sendOrderReady } = await import('@/lib/email')` im Nachlauf, `const { stripe } = await import('@/lib/stripe')` direkt vor dem Aufruf (in `teilerstattung.ts` über `stripeSdk()`).
- **`email.ts` ist selbst leicht:** Es importiert statisch nur Formatierer und Fachregeln; Resend-Client, `render` und jede Vorlage lädt die Versandfunktion. Kein Log und keine Arbeit auf Modulebene (früher „[E-Mail] Init" bei jedem Kaltstart). **Eine Ausnahme (Register N18, seit Nr. 103):** Nach einem erfolgreichen Versand ruft `sendRaw` den Mail-Zähler per `await import('@/server/betrieb-zaehler')` — nur dynamisch, fail-open (ein Fehler beim Zählen stoppt nie eine Mail), nur Schreiben einer Zahl, kein Lesen; Log-Modus und gesperrte Post (Z3) zählen nicht. `email.ts` bindet weiter weder Prisma noch den Zähler statisch ein (Wache `tests/betrieb.test.ts`). **Ebenso das Protokoll (Register N26, seit Nr. 158):** Nach jedem Versuch schreibt `sendRaw` per `await import('@/server/mail-warteschlange')` eine Zeile (`protokolliereSofortMail`), fail-open — ein Fehler im Protokoll hält keine Mail auf.
- **Der dynamische Import gehört in dieselbe Fehlerbehandlung wie der Aufruf** (im `try` bzw. im Nachlauf), damit ein gescheitertes Laden wie ein gescheiterter Versand behandelt wird — ein Nachlauf rollt nie etwas zurück.
- **Kein `await import()` innerhalb einer Transaktion:** Das erste Laden hielte eine Zeilensperre (FOR UPDATE) fest. Wer in der Transaktion Stripe braucht, ruft vorher `stripeVorladen()` (`src/server/teilerstattung.ts`, Vorbild `meldeFehlendenArtikel`); in der Transaktion nutzt `stripeSdk()` das gemerkte SDK.
- **Versandfunktionen mit Ergebnis werfen nicht:** Anmeldecode, Bestell-Code und E-Mail-Bestätigung laden und rendern ihre Vorlage über `htmlOderFehler` und liefern beim Scheitern `{ error }`.
- Ausnahme: API-Routen, die das Modul in jedem Aufruf brauchen (Webhook, Kasse, Cron), dürfen statisch importieren.
- **Der Stripe-Client entsteht erst beim ersten Gebrauch** (seit Nr. 42): `src/lib/stripe.ts` exportiert `stripeClient()` und den Stellvertreter `stripe`, dessen Eigenschaften den Client holen. Der Import allein erzeugt nichts und wirft nie — so laufen Bar-Bestellung, Webhook-Annahme und Seiten ohne Stripe auch dann, wenn die Modus-Wache sperrt (§5 „Zahlungen“). `then` und Symbole beantwortet der Stellvertreter selbst (ein async-Rückgabewert wird auf `then` geprüft). Unter `src/` holt nur `src/lib/stripe.ts` das Paket `stripe` als Wert und ruft `Stripe(…)` auf — alle anderen importieren `import type` (Quelltext-Wache in `tests/stripe-client-wache.test.ts`, auch gegen Umbenennung, `require`/`import()`, Weiterexport und Aufruf ohne `new`). Ausnahmen außerhalb von `src/`: Integrationstests für Fehlerklassen und Signaturen, die Altskripte unter `scripts/`.
- `tests/schwere-module.test.ts` läuft den statischen Import-Graphen jeder `page`/`layout`/`loading` unter `src/app` ab (ohne `api`) und nennt die Kette, über die ein schweres Modul hereinkam. Tests, die „keine Mail" prüfen, warten vorher `await vi.dynamicImportSettled()` ab (`TESTING_GUIDELINES.md` §3).

## 5. Domänen-Invarianten

Diese Regeln sind fachlich, nicht technisch. Verletzung kostet Geld oder Vertrauen.

- **Reservierung bucht keinen Bestand ab.** `Product.stock` sinkt erst beim Kauf. `StockReservation` ist ein weicher Halt, der die Menge nur vor **anderen** Sitzungen verbirgt. Verfällt er, gibt es nichts zurückzubuchen.
- **Die 15-Minuten-Frist gilt beim Lesen** (Einzeiler in `CLAUDE.md` §2): Jede Abfrage fremder Halte filtert auf `expiresAt > jetzt`.
- **Eine offene Bestellung hat eine Frist, und auch sie gilt beim Lesen.** Der Checkout bucht den Bestand vor Zahlung bzw. Bestätigung. Wie lange eine Bestellung in PENDING_CONFIRMATION ihre Ware hält, steht nur in `src/lib/fristen.ts`: online 30 Minuten; vor Ort 2 Stunden, höchstens bis zum Beginn des gewählten Abholfensters. Wer Bestand oder offene Bestellungen liest, gibt vorher frei, was darüber ist: `gibVerwaisteFreiOhneRisiko(farmId)` bzw. `gibVerwaisteFreiFuerProdukte(productIds)` (`src/server/verwaiste-bestellungen.ts`). Die Hofseite gibt über `gibVerwaisteFreiFuerSlug` frei, in `ladeHofseite`. Ein neuer Lesepfad ruft eine der drei am Anfang auf; Fehler darin werden gemeldet, nie an den Request weitergegeben. Nicht nach der Antwort (`after()`/`nachDerAntwort`), solange die Seite Bestellungen oder Vorrat zeigt — sie zeigte sonst Verfallenes. Was die Freigabe nicht ändern kann, darf neben ihr laufen (Vorbild `getHeute`, Nr. 31): Die Abfrage bekommt die laufende Freigabe als Promise und startet nur die abhängigen Abfragen in `freigabe.then(...)`, beides in EINEM `Promise.all`. Online wird zuerst der PaymentIntent abgebrochen — **Ausnahme** von „Stripe und Mail kommen danach", weil die Kundin die verfallene Bestellung sonst noch bezahlen könnte; ist er bezahlt oder in Bearbeitung, bleibt die Bestellung stehen und Stripe wird höchstens alle fünf Minuten erneut gefragt. Der tägliche Cron `/api/cron/verwaiste-bestellungen` ist nur das Netz und meldet stehen gebliebene Bestellungen an Sentry.
- **Cron-Routen prüfen `CRON_SECRET` mit `cronBerechtigt`** (`src/lib/geheimnis.ts`): fail-closed, in konstanter Zeit — nie mit `!==`.
- **Bestandsabzug ist bedingt.** `updateMany` mit `stock >= Menge`; bei Teilfehlschlag die bereits gebuchten Positionen gutschreiben.
- **Vorrat setzen ist bedingt (seit Nr. 18).** Ändert der Hof den Vorrat (Produkttabelle `setzeVorrat`, Bearbeiten-Dialog `updateProduct`), ist das ein Setzen auf den Wert, den er meint — aber nur, wenn die Zeile noch den Vorrat hält, den er gesehen hat: `updateMany` mit `{ id, farmId, stock: vorher }`. Trifft die Bedingung nicht (eine Bestellung oder ein Storno hat inzwischen gebucht), wird nichts geschrieben, und die Antwort trägt den aktuellen Stand (`code: 'GEAENDERT'`). So überschreibt ein Setzen nie eine Buchung, die der Hof nicht gesehen hat; ein Setzen nutzt nie `increment`/`decrement` und nie einen Wert ohne erwarteten alten Stand. Abziehen (Checkout, `bucheVorrat`) geht nur bedingt: `updateMany` mit `stock >= n` und `decrement: n` — nie ein blindes `decrement`. Nur `bucheVorrat` hat einen zweiten Schritt: reicht der Vorrat nicht, bedingt `stock < n` → 0 (Abschnitt „Verkäufe" in §4). `updateProduct` schreibt einen unveränderten Vorrat gar nicht. Reservierungen sind davon unberührt: Setzt der Hof unter das, was in Warenkörben liegt, scheitert der Checkout an `stock >= Menge`. Der Browser schickt je Produkt eine Änderung nach der anderen mit dem zuletzt bestätigten Stand (`VorratFeld`). Bewiesen in `tests/integration/vorrat-setzen.int.test.ts` mit erzwungener Reihenfolge (eine offene Buchung hält die Zeile, `setzeVorrat` wartet nachweislich darauf und setzt danach nicht) samt Gegenprobe (dieselbe Abfolge mit blindem Setzen verliert die Buchung).
- **Ein Statuswechsel mit Wirkung auf Bestand oder Geld ist die Sperre.** Er läuft als `updateMany` mit Statusbedingung (Vorlage: `cancelOrder`), `count === 0` heißt „schon erledigt" — nie eine Leseprüfung mit anschließendem blindem `update`. Bestandsbuchungen gehören in DIESELBE Transaktion; Stripe und Mail kommen danach. Auch ein Rückweg (Undo) schreibt bedingt: Er darf eine stornierte Bestellung nie zurückholen. Zahlstatus und Zahlzeitpunkt bleiben dabei stimmig (`paymentStatus` PAID genau mit `paidAt`): Was ein Rückweg an der Zahlung ändert — das Rückgängig im Hinweis (`revertOrderStatus`) wie der Dialog „Abholung rückgängig" (`revertPickedUp`, seit Nr. 32) —, entscheidet nur `zahlungNachRueckweg` (`hof-bestellungen.ts`) — online nie, bar nur das Kassieren genau des zurückgenommenen Schritts —, geschrieben bedingt auf den gelesenen Zahlstand.
- **Seiten mit Daten einer Bestellung nur mit signiertem Link.** Bestätigungsseite (`/{hof}/confirm/{id}?sig=`) und Bestellseite (`/{hof}/bestellung/{id}?s=`) prüfen `bestellLinkGilt` (`src/lib/bestell-link.ts`) VOR jeder Datenbankabfrage; ohne gültige Signatur zeigt die Bestätigungsseite nur „eingegangen", ohne Name, E-Mail, Artikel oder Beträge. Die Bestell-ID ist ratbar. Pfade dorthin baut nur der Server (`bestaetigungsPfad`, `bestellungPfad`) — das Geheimnis gehört nie in den Browser; `/api/checkout` liefert den signierten Pfad mit (`bestaetigung`). `tests/bestaetigung-zugang.test.ts` sucht nach selbst gebauten `/confirm/${…}`. **Der Link liest — mit genau zwei Ausnahmen (Nr. 46 und Nr. 151, Freigabe §27):** Dieselbe Signatur (Zweck `bestellung-ansehen`, auch in Bestellmail und ICS-Seite) erlaubt zwei Schreibwege: `sendeBarLinkErneut` („Mail nicht bekommen? Erneut senden", nur für eine offene Barbestellung, höchstens drei Mails je Bestellung und Tag, immer dieselbe Antwort) und eine Abo-Anfrage über `meldeNeuigkeitenAn` („Neuigkeiten vom Hof per E-Mail"). Für die Abo-Anfrage gilt: Wer den Link hält — auch wer eine Bestellung mit fremder Adresse angelegt hat —, kann damit nur Folgendes auslösen: eine Bestätigungsmail an die Adresse DER Bestellung (nie eine andere), angemeldet erst mit dem Klick darin (Double-Opt-in, S11); nur für eine laufende Bestellung (`neuigkeitenErlaubt`: nicht storniert, verfallen, nicht abgeholt oder unbezahlt, bar offen nur bis zur Frist); höchstens drei Anfragen je Bestellung und UTC-Tag (Datenbank-Bremse `neuigkeitenBestellung`; festes Fenster ohne erste Stufe, an der Tagesgrenze also bis zu doppelt so viele — die Mails bremst daneben „ein Link je Abo und zehn Minuten"), ein Link je Abo und zehn Minuten, in Produktion zehn je IP und Minute; immer dieselbe Antwort; an der Bestellung ändert sich nichts. Ein dritter Schreibweg über diese Signatur braucht ein eigenes Token mit eigenem Zweck oder eine ausdrückliche Freigabe.
- **Signierte Links: zwei Geheimnisse, eine Kennung (Register S17, Ergänzung 24.10.2026, seit Nr. 166).** Bestell-Link (`bestell-link.ts`), Nachbestell-Token (`reorder-token.ts`) und Abmeldelink (`unsubscribe.ts`) signieren nur über `signiereLink`/`pruefeLink` (`src/lib/link-signatur.ts`); keiner dieser drei Links baut sein HMAC selbst. Offener Rest: der Double-Opt-in-Link (`src/lib/abo-bestaetigung-token.ts`) signiert noch mit `BETTER_AUTH_SECRET`. Ist `LINK_SECRET` gesetzt, trägt jede neue Signatur die Kennung `2.` vor dem Hex (HMAC über `<zweck>:<inhalt>`); eine Signatur ohne Kennung prüft `pruefeLink` mit `BETTER_AUTH_SECRET` im alten Format — sie liegt in Postfächern und gilt weiter. Eine unbekannte Kennung gilt nie, die `2` ohne `LINK_SECRET` auch nicht. Vergleich in konstanter Zeit (`geheimnisGleich`). Ein Token trennt Inhalt und Signatur am **ersten** Punkt; eine Formprüfung von `sig`/`s` lässt `2.` vor 64 Hex zu (`src/schemas/bestaetigung.ts`, `src/schemas/abo.ts`). **Tausch mit Kennung 3:** (1) eine neue optionale Variable für das neue Geheimnis anlegen (Freigabe nötig, wie jede Variable) und in `geheimnisFuer` der Kennung `3` zuordnen, `LINK_KENNUNG` auf `3`; (2) die Formprüfung der beiden Schemas um `3.` erweitern; (3) Kennung `2` weiter prüfen, solange ihre Links gelten sollen — Bestell- und Abmeldelinks laufen nie ab, also erst entfernen, wenn alte Links bewusst ungültig werden dürfen; (4) mit Tests: alte `2.`- und kennungslose Signaturen gelten, neue tragen `3.`. Nur nach einem Leck die alte Kennung sofort entfernen. Bremsen-Schlüssel (`bremsSchluessel`) und Bar-Token-Hash sind keine Links und hängen nicht daran.
- **Kein signierter Link an Orten, die wir nicht schützen.** Ein Kalendereintrag (ICS, `/{hof}/bestellung/{id}/kalender`) wird synchronisiert, geteilt und weitergereicht — seine `DESCRIPTION` nennt nur die Bestellnummer, nie `bestellungPfad`/`bestaetigungsPfad`. Einen Termin gibt es nur, solange die Bestellung steht und die Abholung aussteht (`kalenderTerminGilt`, beim Lesen: offen — vor der Frist unbestätigt, danach verfallen —, storniert, abgeholt → dieselbe 404 wie jede Ablehnung). Signierte Links stehen nur in Mails an die Kundin und auf ihren eigenen Seiten.

Ohne Schlüssel ist nichts erlaubt. Leer (Bild entfernen) geht immer; eine fremde Adresse nur, wenn sie unverändert schon gespeichert ist (Altbestand bleibt speicherbar). Nie eine Bild-URL aus dem Browser ungeprüft speichern (`tests/bild-url-pruefung.test.ts`).
- **Ein Link aus einer Mail ändert nie einen Zustand.** Link-Scanner und Vorschauen der Mailprogramme rufen Links ungefragt auf. Ein GET liest oder leitet weiter; bestätigt, storniert oder bucht wird nur per Knopf (Server Action, POST). **Einzige Ausnahme ist die Fristfreigabe beim Lesen** (`gibVerwaisteFreiOhneRisiko`, wie auf `/{hof}/confirm/{id}` und `/orders`): Sie setzt nur durch, was die Frist ohnehin schon entschieden hat (über der Frist ist die Bestellung verfallen, ob jemand aufräumt oder nicht). Nie löst ein GET eine Bestätigung oder einen anderen Übergang aus, den die Kundin oder der Hof wollen muss. Der Knopf prüft die Frist mit der Zeit NACH seiner eigenen Freigabe (die kann bei Stripe Sekunden dauern), und `confirmedAt` ist genau diese Zeit. Bar-Bestätigung: Die Mail verlinkt `/{hof}/bestaetigen/{token}` (Pfad nur über `barBestaetigungsPfad`), `/api/orders/confirm/{token}` alter Mails leitet nur dorthin weiter. Die Seite zeigt nie Name oder E-Mail der Kundin, `noindex`, `Referrer-Policy: no-referrer`; Sentry entfernt den Token (`sentry-hygiene.ts`). **In `Order.confirmationToken` steht nur der Hash** (Register S17 Punkt 2, seit Nr. 151): `barTokenHash` (`'h1:'` + SHA-256 über `'bar-bestaetigung:'` + Token; der Doppelpunkt besteht das Token-Schema nie, ein gespeicherter Wert taugt nie als Token). Der Checkout speichert den Hash, die Mail trägt den Token. Jeder Leser sucht mit `findFirst({ where: { confirmationToken: { in: tokenKandidaten(token) } } })` — nie `findUnique` auf den Token, nie ein eigener Vergleich; das bedingte Schreiben nimmt denselben Filter. Der Klartext-Kandidat hält Bestellungen von vor dem Deploy gültig und fällt mit einem eigenen Auftrag weg. **„Mail nicht bekommen? Erneut senden"** steht auf der Bestätigungsseite genau dann, wenn `barLinkErneutMoeglich` ja sagt (offen, bar oder Karte beim Hof, Hof nicht stillgelegt); die Action `sendeBarLinkErneut` ist — neben `meldeNeuigkeitenAn` — der zweite Schreibweg über die Signatur der Bestätigungsseite (`bestellLinkGilt`, vor jeder Abfrage): dieselbe Bedingung wie der Knopf, Bremse `barLinkBestellung` (3 je Bestellung und Tag, nach Signatur und Stand gezählt), dann `updateMany` mit dem gelesenen Wert in der WHERE-Klausel und dem Hash eines neuen Tokens (der Wechsel ist die Sperre: von zwei Anforderungen schickt genau eine eine Mail, der alte Link gilt danach nicht mehr). Die Mail geht nur bei `count === 1`, über `nachDerAntwort`, an die Adresse DER Bestellung (`barMailBestellung`, dieselbe Hilfe wie beim Bestätigen); nach Sentry nur die Bestell-ID; die Antwort ist immer `BAR_LINK_ERNEUT_ANTWORT`. Ein ungültiger Link sagt auf Seite und in den Knöpfen denselben Satz (`LINK_UNGUELTIG_TITEL`, `LINK_UNGUELTIG_SATZ`).

Regeln und Texte in `src/lib/abo-bestaetigung.ts` (ohne env, auch im Browser ladbar), das Geheimnis nur in `abo-bestaetigung-token.ts`. WhatsApp ist davon (noch) nicht erfasst.

Codes zählen über beide Wege zusammen (`/sign-in/email-otp` und `pruefeBestellCode`), sonst hätte jeder Weg seine eigenen 10. **Gezählt wird VOR dem Code bzw. Passwort, atomar** (`zaehleVersuchVorab` über `zaehleVersuche`, im `before`-Hook von `auth.ts`, bei der Code-Anmeldung vor der Rollenprüfung; in `pruefeBestellCode` vor der Code-Zeile), erst dann entscheidet der Stand — nie erst lesen, dann prüfen, dann zählen: Dann kämen alle gleichzeitigen Versuche (Hash und Datenbankwege, 100–300 ms) an einem Stand unter der Grenze vorbei. Der Versuch bleibt nur bei einem Fehlversuch gezählt (`hooks.after`, Fehler als APIError in `ctx.context.returned`, welche Codes zählen sagt `istFehlversuch`); ein Erfolg oder ein anderer Fehler gibt ihn zurück (`gibVersuchZurueck`, im Fenster der Zählung, nie unter 0), eine Ablehnung wegen Pause sofort — sonst füllten Ablehnungen das Tagesfenster. Wirft der `before`-Hook oder der Endpunkt etwas anderes als einen APIError, läuft `hooks.after` nicht, der Versuch bleibt gezählt. Zusage: je Fenster höchstens `max` geprüfte Versuche, die nicht zurückgegeben wurden. Die Ablehnung eines Hofs bei der Code-Anmeldung zählt im `before`-Hook wie ein falscher Code — Antwort, Status und Zählung sind für Kundin, Hof und unbekannte Adresse gleich. Dazu antwortet ein abgelaufener oder zu oft probierter Code (`OTP_EXPIRED`, `TOO_MANY_ATTEMPTS` des Plugins) im `after`-Hook wie ein falscher (`alsFalscherCode`, 400 `INVALID_OTP`): Ein Hof bekommt nie einen Code, sonst verriete der 6. Versuch auf denselben Code die Rolle. **Better Auth:** Ein in `hooks.after` geworfener APIError ersetzt nur den Körper, den Status behält Better Auth vom Endpunkt (`dispatchAuthEndpoint` → `toResponse`) — wer den Status ändern muss, gibt über HTTP eine fertige `Response` zurück (ohne Request, also bei `auth.api`, wird geworfen). Voll ist eine Bremse beim `max`-ten Fehlversuch (`fehlversuchSperreBis`; abgelehnt wird, wessen Stand VOR dem Versuch `max` erreichte); danach 429 mit `code` (`ZU_VIELE_FALSCHE_CODES` / `…_PASSWOERTER`), `pauseBis` (Wiener Uhrzeit) und dem Satz aus `zuVieleFehlversucheAntwort`, ohne dass Better Auth prüft. **Fail-closed, als einzige Bremsen:** Fehler oder Zeitlimit der Datenbank → pausiert (`bis: null`, 429 ohne Uhrzeit) — sie schützen ein Konto vor dem Raten, und ohne Datenbank meldet ohnehin niemand an; alle übrigen Bremsen bleiben fail-open. Sie gelten in jeder Umgebung (Merkmal Adresse, keine IP — wie `neuigkeitenGebremst`), so prüft die Integrationsschicht die echte Bremse ohne Schalter. **Eine Mail je Pause:** Nur der gescheiterte Versuch, dessen Stand genau `max` ist (`pauseBeginntBis` in `zaehleAlsFehlversuch`), stellt die Mail in `nachDerAntwort` — nur an eine Adresse mit Konto, nie mit Code oder Link. Der atomare Stand allein reicht nicht (gibt ein gleichzeitiger richtiger Versuch zurück, sieht der nächste Fehlversuch wieder `max`): Jede Mail geht zusätzlich durch eine Drossel in der Datenbank (`warnMailDrosseln`, `max: 1` je Fenster der Bremse, die voll wurde — `code-fehler-mail-stunde` / `-tag`; beim Passwort `passwort-fehler-mail`, eine am Tag); antwortet die Drossel nicht, geht im Zweifel keine Mail. Pausiert, sagt „Bestellungen finden“ denselben Satz mit Uhrzeit wie die Code-Anmeldung (`bestellCodePauseText` → `zuVieleCodesText`), ohne Ende (fail-closed) den Satz ohne Uhrzeit. Ein erfolgreiches `/reset-password` löscht die Zeilen von `passwort-fehler` dieser Adresse (die Adresse merkt sich der `before`-Hook je Aufruf an `ctx.context`, `WeakMap`); „Passwort vergessen“ bleibt offen und verschickt über `nachDerAntwort`. Grenze: Wer eine Adresse kennt, kann ihre Anmeldung je Stunde neu pausieren — keine Sperre auf Dauer.

Das Feld ist Pflicht in `HofFuerPlatz`; jede Hofliste der Vergabe kommt aus `HOF_FUER_GRUENDUNG` (über `ladeHoefeFuerGruendung`) oder dem Select von `getAdminFarms` — keine dritte Abfrage, keine zweite Zählung (Wache `tests/gruendung-ausgenommen-wache.test.ts`). Geschrieben wird nur in `nimmAusGruendung`/`nimmWiederAuf` (`src/server/actions/gruendung.ts`: frische Bestätigung mit Passkey als heikle Aktion (N20, seit Nr. 115) und Admin-Wache, Zod `src/schemas/gruendung.ts`, bedingtes `updateMany` auf den alten Wert der Spalte, dazu `gruendungGeaendertAm`/`-VonUserId`): Ausnehmen eines Hofs mit Platz nur mit `bestaetigt` (K1), Wiederaufnehmen nur bei `wiederAufnahmeMoeglich` (danach höchstens `gruendungPlaetze` der Einstellung im Rennen, nie die feste 12). Was die Bestätigung zeigt, rechnet `folgenDerAenderung` mit derselben Regel. **Wer Plätze vergibt oder Höfe ins Rennen bringt, nimmt die Sperre:** in `prisma.$transaction(async (tx) => …)` zuerst ``tx.$executeRaw`SELECT pg_advisory_xact_lock(${GRUENDUNGSPLAETZE_SPERRE})` `` (Kennung an EINER Stelle in `gruendungshof.ts`; `$executeRaw`, weil die Funktion `void` liefert), danach die Höfe mit `ladeHoefeFuerGruendung(tx)` lesen und bedingt schreiben — so `approveFarmAction` (bedingtes Freischalten, Zeitpunkt nach der Sperre, Platz und Zusage in derselben Transaktion; Nachricht und Mail danach) und beide Actions oben. Einen Platz freigeben (Zurücknehmen, Stilllegen, Ausnehmen ohne Platz) braucht keine Sperre — dabei verliert niemand eine Zusage. Admin › Höfe liest die Zahl der Plätze seit Nr. 109 aus der Einstellung; das wirksame Ende in der Spalte rechnet weiter `bestimmeGruendungBis` mit denselben Plätzen (`plaetzeDerVergabe`, Nr. 116).
- **Testhof (Register N21, seit Nr. 119).** `Farm.istTesthof` (Default false, dazu `testhofGeaendertAm`/`-VonUserId`) wird nur in `markiereAlsTesthof`/`nimmTesthofZurueck` (`src/server/actions/gruendung.ts`) geschrieben — frische Bestätigung mit Passkey als heikle Aktion (N20, seit Sammel-PR Lauf 18) und Admin-Wache, Zod, EINE Transaktion unter `GRUENDUNGSPLAETZE_SPERRE`, bedingtes `updateMany` auf den alten Wert. Danach `revalidiereGruendung()` samt `HOEFE_CACHE_TAG`, dazu `/sitemap.xml`, `STARTSEITE_CACHE_TAG` und die Hofseite. Die Hofseite liest `istTesthof` über `getPublicFarm`/`getOwnerFarm` (`PublicFarm`) für ihren Hinweis; Bestellen bleibt möglich.
- **Festgeschriebene Gründungsplätze und die Aktion „100 Gründungshöfe“ (Register K2, Änderung 19.10.2026, seit Nr. 116).** Platz und Ende stehen je Hof in `Farm.gruendungPlatz` (eindeutig) und `Farm.gruendungBis`; `PlattformEinstellung.gruendungFestAm` sagt, ob festgeschrieben ist. Vorher gilt alles oben unverändert (Reihenfolge, bisheriges Ende). Die Lader liefern dafür auch stillgelegte und zurückgenommene Höfe mit Platz (sie halten ihn); wer „freigeschaltet und nicht stillgelegt“ meint, prüft das am Hof selbst. Platz und Ende werden nur in vier Wegen geschrieben, alle unter `GRUENDUNGSPLAETZE_SPERRE` mit Einstellung und Höfen NACH der Sperre gelesen: „Zusagen festschreiben“ (`schreibeZusagenFest`, einmal: `gruendungFestAm` bedingt setzen, dann je Hof aus `festschreibenListe` — auch stillgelegte, nie kürzer), Freischalten (`zusageBeiFreischaltung`: vorhandener Platz und Ende bleiben — ohne gespeichertes Ende nennt die Nachricht den Standard wie `bestimmeGruendungBis` —, sonst kleinste freie Nummer und `zusageEnde` ab heute, solange `aktionLaeuft`), Ausnehmen (Platz frei) und Wiederaufnahme (wie Freischalten). Auch `reactivateFarm` und `speichereGruendungEinstellung` nehmen die Sperre; Stilllegen und Freigabe entziehen ändern keinen Platz (Wache `tests/gruendung-sperre-wache.test.ts`). Der eindeutige Index fängt den Rest: P2002 → fester Satz, die Transaktion rollt ganz zurück. Der Schalter `gruendungAnzeige` steuert nur die Sätze (`zeigen`), nie die Vergabe. Öffentliche Abfragen geben nur `gruendungshof` (Ja/Nein, `zeigtAbzeichen`) und den Monat der Freischaltung weiter, nie die Nummer (`ABZEICHEN_SELECT` in `src/server/queries/farm.ts`, Test `tests/abzeichen.test.ts`); nach dem Schalter „Abzeichen zeigen“, dem Festschreiben, jeder Freischaltung und jeder Platzänderung `updateTag(HOEFE_CACHE_TAG)` (Höfe-Liste und Startseite hängen am selben Eintrag). Die Zahlen des Erklär-Blatts liest die Hofseite über `ladeAbzeichenBlatt` (`unstable_cache` unter `HOEFE_CACHE_TAG` und `PLATTFORM_EINSTELLUNG_TAG`, fünf Minuten wegen des Stichtags), nie bei jedem Aufruf frisch gezählt. Das Teilen-Bild liest `ABZEICHEN_SELECT` in `ladeTeilenBildQuelle` und gibt nur `gruendungshof` weiter; das Feld steht nur bei Gründungshöfen in den Bilddaten, damit ändert der Schalter die Prüfsumme und die Bildadresse (`?v=`).
- **Plattform-Einstellungen (Register K2-Ergänzung und N15, seit Nr. 93)** stehen in EINER Zeile `PlattformEinstellung` (Kennung `plattform`, angelegt von der Migration): Plätze gesamt, Standard-Ende (DATE), Anzeige an/aus, dazu wer zuletzt gespeichert hat; `zustellRegeln` gehört Nr. 95. Gelesen wird nur — fehlt die Zeile, gelten `PLATTFORM_EINSTELLUNG_STANDARD` (= die Konstanten aus `gruendungshof.ts`); kein Lesepfad schreibt (kein upsert beim Lesen). Öffentliche Seiten lesen über `ladePlattformEinstellung` (`unstable_cache`, Etikett `plattform-einstellung`, Form nur JSON: Kalendertag statt Date, der Eintrag entsteht erst beim Aufruf), Admin › Einstellungen und die Freischaltung frisch über `lesePlattformEinstellung` (`src/server/queries/plattform-einstellung.ts`). Geschrieben wird nur in `speichereGruendungEinstellung` (`src/server/actions/plattform-einstellung.ts`: Admin-Wache, Zod strikt, unter `GRUENDUNGSPLAETZE_SPERRE` `pruefeGruendungEingabe` — Plätze nie unter die vergebenen und nie weniger als bisher, Monate nur höher (und nur, solange die Aktion nicht vorbei ist), „Aktion bis“ einmal gesetzt nur früher und nie vor heute; das Standard-Ende ist nicht mehr änderbar —, upsert nur der Felder der Gruppe, danach `updateTag` und `revalidatePath` für `/`, `/fuer-hoefe`, `/register`, `/admin/einstellungen`). Was die Seiten zeigen, rechnet `gruendungSeitenDaten` aus Einstellung, Platzvergabe und Warteliste; die Seiten holen es über `gruendungFuerSeiten()` (fängt Ladefehler, dann zeigt die Seite nichts davon). Seit Nr. 116 lesen alle Aufrufer (Admin-Liste, Freischalt-Dialog, `ladeGruendungBis`, `setzeGruendungBisAction`) die Plätze aus der Einstellung bzw. von `plaetzeDerVergabe` an den Zeilen — eine Zusage mit Geldwert hat nie zwei Quellen; `pruefeGruendungEingabe` ersetzt die frühere Sperre der Felder.
- **Eine Expand-Migration ist nur hinzufügend und wiederholbar.** Neue Spalten an bestehenden Tabellen sind nullable oder haben einen Default (`ADD COLUMN IF NOT EXISTS … DEFAULT …`), dazu `SET lock_timeout`; kein `DROP`, `RENAME`, `ALTER TYPE`, `ALTER COLUMN`, kein `UPDATE` auf Bestandszeilen. Erzeugt wird sie mit `prisma migrate diff` gegen das Schema von `main` (Regel 3 in `docs/nachtlauf.md`), geprüft mit `pnpm test:integration`. Jede solche Migration bekommt eine Datei-Wache (Muster: `tests/schema-expand.test.ts`, `tests/migration-teilen-momente.test.ts` — Anweisungen ohne Kommentare gegen eine Verbotsliste, mit Gegenprobe) und einen Integrationstest, der Default, Deploy-Fenster (rohes INSERT ohne die Spalte) und einen zweiten Lauf auf einem bestehenden Hof prüft (`tests/integration/teilen-momente.int.test.ts`; eine nullable Spalte ohne Default prüft statt des Defaults, dass null als Standard wirkt: `tests/integration/gruendung-bis.int.test.ts`). Ein Schalter mit Default `false` wird so benannt, dass der Default den bisherigen Zustand bedeutet (`Farm.teilenMomenteAus`: false = Momente an wie bisher).

### Mails (Register N26, seit Nr. 158)

- **Drei Wege.** *Sofort* (`vorrang` 0): Mails mit Code, Einmal-Link oder Bestätigungslink (Anmeldecode, Bestellcode, Login-Link, Passwort-Link, E-Mail bestätigen, Registrierungs-Hinweis, Bar-Bestätigungslink, Admin-Sicherheit, Neue Anmeldung, Zu viele Versuche, Betriebs-Warnung, Testmail, Bestätigung einer weiteren Betreiber-Adresse — ihr Token liegt nur als Hash vor) gehen direkt über `sendRaw` und stehen nur im Protokoll — ein Token oder Code wird nie gespeichert. *Wichtig* (1): Mails zu Bestellungen und an Höfe und Betreiber. *Kann warten* (2): Beiträge, Rundschreiben, Bescheide. Die Arten stehen in `MAIL_ARTEN`, ihr Weg in `MAIL_WEG` (`src/schemas/mail-auftrag.ts`, seit Nr. 159 die eine Liste); auf Admin-Seiten heißen die Wege „Sofort“, „Wichtig“, „Kann warten“, nie Zahlen.
- **Eine Tabelle, keine Personendaten.** `MailAuftrag` ist Warteschlange und Protokoll zugleich. Sie trägt Art, Weg, Stand, Versuche, Fehlercode (kurzer Code von Resend, nie dessen Text), `bestellungId`/`farmId` (ohne Fremdschlüssel) und in `bezug` nur Kennungen (`bezugSchemaFuer`: je eingestellter Art ein festes, striktes Schema; Werte ohne @ und Leerzeichen). Wo eine Mail einen Betrag zeigt, der beim Ereignis feststand (Storno, „Artikel fehlt", Zahlung zu spät), trägt der Bezug ihn als Ziffern in Cent (`…Cents`) — nie neu gerechnet; „Erstattung offen" trägt statt Text einen festen Fall (`ERSTATTUNG_OFFEN_FAELLE`, Sätze in `src/lib/erstattung-offen.ts`). Nie Adresse, Name, Text oder Token. Für die Suche per Adresse nur `empfaengerHash` aus `empfaengerFingerabdruck` (`src/lib/mail-empfaenger.ts`), gesetzt beim Versand, verglichen nur über diese Funktion. Nach 90 Tagen löscht das Aufräumen die Zeile (`MAIL_PROTOKOLL_AUFBEWAHREN_TAGE`).
- **Einstellen.** `stelleMailEin(auftraege, db?)`: EIN `createMany` mit `skipDuplicates` über den fachlichen `schluessel` (`beitrag:<postId>:<aboId>`, `<art>:<orderId>` …) — doppelt eingestellt heißt einmal verschickt. Gibt es eine fachliche Änderung, läuft das Einstellen mit dem Transaktions-Client in derselben Transaktion. Danach startet der Worker über `nachDerAntwort`. Keine Schleife über Mails in Actions oder Routen (CODING_STANDARDS §4).
- **Worker.** `arbeiteWarteschlange` — nur einer zur Zeit (`pg_try_advisory_xact_lock` in einer offenen Transaktion), Seiten zu 100 per `WITH … FOR UPDATE SKIP LOCKED` + `UPDATE … RETURNING` mit `belegtBis` = jetzt + 2 min (abgelaufen gilt wieder als offen), Wichtig zuerst. Der eigene `belegtBis` ist die Kennung des Laufs: Jedes Schreiben danach verlangt ihn in der WHERE-Klausel, und eine Anfrage an Resend geht nur, solange noch 30 s Belegung übrig sind (`BELEGUNG_REST_MS`, sonst Freigabe). Versand je Seite als `versendeStapel` (`batch.send`, src/lib/email.ts), Aufträge eines abgebrochenen Laufs als eigene Anfrage mit dem Idempotenz-Schlüssel aus sortierten Kennungen und Versuchen (`stapelSchluessel`), zwischen zwei Anfragen an Resend mindestens 200 ms. 429/5xx/Netz: neuer Versuch nach 1, 5, 15, 60, 240 Minuten, danach `gescheitert`; anderer 4xx sofort `gescheitert`. Ohne Schlüssel `ohne_schluessel`, kein neuer Versuch. Cron `/api/cron/mails` jede Minute (Ablauf `mails`, überfällig nach 10 Minuten), dazu der Lauf nach jedem Einstellen.
- **Kontingent.** Kann warten wird nicht geholt ab 70 % der Tagesgrenze (nur mit Tagesgrenze) oder 90 % der Grenze des Abrechnungszeitraums (`kannWartenPausiert`). Wichtig geht immer.
- **Renderer.** Je Art eine Funktion in `src/server/mail-arten/` (Tabelle `RENDERER`): lädt Adresse und Inhalt frisch und baut die Mail mit der Vorlage aus `src/lib/email.ts` (`baue…`, z. B. `baueBeitragMail`) — keine zweite Vorlage. Darf die Mail nicht mehr hinaus (Abo abgemeldet, Double-Opt-in fehlt — `WERBEMAIL_EMPFAENGER`, Bezug gelöscht, Empfänger entfernt, Anfrage erledigt), liefert er `{ verworfen: <code> }`.
- **Wege je Art (Nr. 159).** In `src/lib/email.ts` verschickt nur eine Sofort-Funktion selbst (`send…` über `sendRaw`); jede Mail der Warteschlange hat eine `baue…`-Funktion, die nur baut. Die Aufträge baut der Aufrufer über die Helfer neben den Renderern (`bestellMailAuftrag`, `stornoMailAuftrag`, `betreiberAuftraege`, `beitragAuftraege` …). Betreiber-Mails: je Adresse der Liste ein Auftrag mit `empfaengerId` (`support` = die feste Adresse, sonst die Zeile in `BetreiberEmpfaenger`; `betreiberKennungen` nimmt die Liste aus `ladeBetreiberEmpfaenger`). Ein Statuswechsel stellt in seiner Transaktion ein (Webhook bezahlt, Bar-Bestätigung, Storno, abholbereit, nicht abholbereit, Rundschreiben, Beitrag, Zahlung zu spät) — scheitert das Einstellen, ist auch der Wechsel nicht gespeichert und die Action meldet das. Steht der Betrag erst nach Stripe fest (Online-Storno), trägt der Auftrag `erstattung: 'ausstehend'`; danach setzt `trageStornoErstattungEin` den gebuchten Betrag oder `offen` (Renderer verwirft, keine Storno-Mail). Solange `ausstehend` steht, wirft der Renderer und der Worker versucht es nach Plan wieder. „Artikel fehlt" stellt noch nach dem Schreiben ein (die Transaktion liegt in `src/server/artikel-fehlt.ts`). „n per E-Mail" eines Beitrags zählt `gesendeteBeitragsMails` aus der Warteschlange (Beiträge ohne Aufträge: die alte Zahl am Beitrag); `emailRecipientCount` ist die Zahl der Aufträge und hält die 7-Tage-Sperre. Die Wache `tests/mail-wege-wache.test.ts` hält Funktionen, `MAIL_WEG` und `RENDERER` zusammen und meldet Versand in einer Schleife unter `src/server` und `src/app`.
- **Zustellmeldungen (seit Nr. 160).** `POST /api/webhooks/resend`: Reihenfolge Geheimnis → Größe (`RESEND_EREIGNIS_MAX_BYTES`, begrenzt gelesen wie /api/csp-bericht) → Svix-Signatur über den Rohtext (`svix-id`, `svix-timestamp`, `svix-signature`; HMAC-SHA256 über `<id>.<timestamp>.<Rohtext>` mit dem Base64-Teil von `RESEND_WEBHOOK_SECRET` nach `whsec_`, mehrere `v1,…` erlaubt, Vergleich mit `geheimnisGleich`, Zeitstempel höchstens 5 Minuten daneben) → Zod (`src/schemas/resend-ereignis.ts`, nur `type`, `created_at`, `data.email_id`) → Wirkung. Ohne Geheimnis oder mit leerem Schlüssel 503, falsche Signatur 401, andere Ereignisse und unbekannte `resendId` 200 ohne Wirkung. `vermerkeZustellung` setzt `zugestelltAm`/`bounceAm`/`beschwerdeAm` per `updateMany` mit leerer Spalte als Bedingung (doppelte Meldung → nichts); bei Bounce oder Spam-Meldung mit `aboId` im Bezug meldet sie VORHER über `meldeAboAb` (`src/server/abo-anmeldung.ts`, dieselbe Funktion wie der Abmeldelink) ab. Wer künftig eine `resendId` schreibt, schreibt sie in `MailAuftrag` — sonst findet der Webhook die Mail nicht.
- **Post-Sperre (Z3) bleibt die eine Stelle:** `postSperreLaesstDurch` in `src/lib/email.ts` — `sendRaw` und Worker fragen beide dort (`gesperrt`).
- **Mails nochmal schicken (Register N27, seit Nr. 167).** Nur der Support in Admin › Betrieb › Alle Mails, nur Arten aus `NOCHMAL_ERLAUBT` (`src/lib/betrieb-mails.ts`; jede Art steht in genau einer der Listen `NOCHMAL_ERLAUBT`/`NOCHMAL_NIE`, `tests/mails-nochmal.test.ts` wacht). `schickeMailNochmalAction` (frische Bestätigung, N20) prüft der Reihe nach Art, Stand (nicht mehr unterwegs), höchstens 3-mal je ursprünglicher Mail in 24 Stunden (`nochmalVon`, `zaehleNochmalHeute`) und den heutigen Stand (`passtNochmal`, rein) und stellt dann über `stelleMailEin` EINEN neuen Auftrag ein: dieselbe Art und derselbe Bezug, Weg Wichtig, `ausloeser: 'support'`, `nochmalVon` auf die ursprüngliche, Schlüssel `nochmal:<id>:<n>` (zwei gleichzeitige Klicks ergeben denselben Schlüssel). Der Empfänger ist nie eine Eingabe — der Renderer lädt die heute hinterlegte Adresse; Post-Sperre und Abmeldung gelten wie für jede Zeile (der Worker liest `ausloeser`/`nochmalVon` nie). Der Bar-Bestätigungslink ist der Sonderfall: neuer Token über `neuerBarToken` (src/lib/bar-bestaetigung.ts), gespeichert nur der Hash und nur per bedingtem Wechsel (gelesener Wert, unbestätigt), dann direkt über `sendOnsiteConfirmation(…, { nochmalVon })` — der Token steht nie in `MailAuftrag`, die Frist bleibt. Die Vorschau (`baueMailVorschau`, src/server/mail-arten/vorschau.ts) baut mit demselben Renderer und gibt die Mail nur durch `entschaerfeLinks` heraus; sie wird nicht gespeichert und nicht protokolliert. Adressen erscheinen nur gekürzt (`maskiereAdresse`) und werden je Anzeige frisch geladen (`ladeNochmalStand`).

### Zahlungen

- **Vollerstattung bei Destination Charges immer mit `reverse_transfer` — und mit `refund_application_fee`, sobald die Zahlung eine `application_fee` trägt; Gebühren-Teilerstattung ohne beides.** Das gilt auch für eine Erstattung von Hand im Stripe-Dashboard. Vorlage: `cancelOrder`; Teilerstattung: `lasseServicegebuehrEntfallen`. Warum: `DEVELOPMENT.md`, „Vollstorno ohne reverse_transfer". **Ausnahme nach „Artikel fehlt":** Hat eine Bestellung schon eine Teilerstattung oder eine fehlende Position (`nachTeilerstattung`, `src/lib/storno.ts`), holt der Storno den Rest mit FESTEN Beträgen (nächster Punkt) — Stripe kehrte Überweisung und Gebühr sonst anteilig um.
- **Erstattung mit festen Beträgen = zwei Buchungen, nie zweimal** (`src/server/teilerstattung.ts`): erst lesen, was Stripe schon gebucht hat (`ladeStripeStand`: Überweisung über `latest_charge.transfer`, Erstattungen der Zahlung, Rückbuchungen der Überweisung). Jede Buchung trägt `metadata` `orderId`, `anlass` (`teilstorno`/`reststorno`), `positionId`, `art` (`kunde`/`hof`); gibt es für dieselbe Bestellung, denselben Anlass und dieselbe Position schon eine, wird ihr Betrag übernommen und nichts neu gebucht — das schützt auch nach Ablauf des Idempotenz-Schlüssels (rund 24 h) und bei inzwischen anderem Betrag; der Schlüssel bleibt die Sicherung gegen gleichzeitiges Buchen. **Im Zweifel nicht buchen** (`StripeStandUnklar`): hat eine Liste mehr als eine Seite (100), gibt es eine Erstattung oder Rückbuchung ohne zuordenbare Merkmale (von Hand im Dashboard, Teilstorno im alten Format ohne Position, fremder Anlass) oder geht ein Nachtrag fachlich nicht auf bzw. sind es mehr als `NACHTRAGEN_HOECHSTENS`, wird nichts gebucht — Sentry (`stripe_unklar_<grund>`), der Hof bekommt „bitte melde dich bei uns". Eine Erstattung mit Status `failed`/`canceled` zählt nie als erstattet, auch nicht, wenn derselbe Schlüssel sie zurückgibt (`pending` zählt). Sonst die Erstattung an die Kundin über den Betrag OHNE `reverse_transfer` und ohne `refund_application_fee` (geht vom Plattformsaldo, wo die einbehaltene Gebühr liegt), zuletzt die Rückbuchung (`transfers.createReversal`) mit festem Betrag vom Hof. Scheitert nur die Rückbuchung, ist die Kundin bedient; Sentry (`rueckbuchung_offen`) nennt Betrag und Bestellung für die Handbuchung. Nie `reverse_transfer` mit einem Teilbetrag, wenn der Hof einen anderen Betrag zurückgeben soll, als die Kundin bekommt.
- **Storno nach Teilerstattung rechnet aus Stripes Buchungen** (`restNachTeilerstattung`, `src/lib/storno.ts`): Kundin = bezahlt − alle Teilstorno-Erstattungen, Hof = Warenpreis der Bestellung − Provision − alle Teil-Rückbuchungen. **Bezahlt kommt aus Stripe** (`latest_charge.amount`, `StripeStand.bezahltCents`), nie aus der Datenbank; weicht es von Warenpreis + Gebühr + `erstattetCents` ab oder fehlt es, wird nichts gebucht (`StripeStandUnklar` `bezahlt_abweichend`). Der Storno fragt deshalb vor der Vollerstattung mit `reverse_transfer`, ob Stripe schon Erstattungen kennt (`hatErstattungen`, eine Seite) — auch solche, die die Datenbank nach einer verlorenen Antwort nicht hat; dann feste Beträge, `erstattetCents` = alles, was Stripe erstattet hat. Eine gescheiterte Teil-Rückbuchung holt der Rest damit nach.
- **Keine Servicegebühr bei Barzahlung bis zum SEPA-Start (Register B1, Nr. 19a).** Der Stichtag ist `BAR_SERVICEGEBUEHR_AB` in `src/lib/konditionen.ts` (Standard `TARIFE_AB`, Wiener Mitternacht); maßgeblich ist der Bestellzeitpunkt (Server-Uhr von `/api/checkout`), nicht der Abholtag. Entschieden wird nur in `barOhneServicegebuehr` (`src/lib/servicegebuehr.ts`), gerechnet nur in `berechneServicegebuehr(…, zahlungsart)`: bar davor → Snapshot `serviceFeeCents` 0, `serviceFeePercentApplied` und `serviceFeeMinCentsApplied` null (wie ein gebührenfreier Hof, damit „Artikel fehlt" bei 0 bleibt). Online unverändert; `ONSITE_CARD` nennt B1 nicht. Die Kasse rechnet mit der gewählten Zahlart neu, verbindlich ist der Server, Stripe bekommt nur den Betrag der gespeicherten Bestellung. Finanzseite (`topfVonBestellung`) und Admin-Hofliste (rohes SQL, Spalte „bar") zählen Barbestellungen vor dem Stichtag nirgends — auch ältere mit Gebühr nicht, eingezogen wird sie nicht. - **„Artikel fehlt" (E14, seit Nr. 19).** Was gerechnet wird, entscheidet `artikelFehltRechnung` (`src/lib/artikel-fehlt.ts`): Gebühr auf den verbleibenden Warenwert mit Satz und Mindestgebühr DER BESTELLUNG (`serviceFeePercentApplied`, `serviceFeeMinCentsApplied`, den der Checkout seit Nr. 19 schreibt; Altbestellungen ohne Snapshot: lag die Gebühr über dem Prozentanteil, war sie die Mindestgebühr, sonst € 0,50) über `berechneServicegebuehr`, nie über der bisherigen Gebühr; bar neuer Betrag = Rest + neue Gebühr, online Erstattung = Artikelpreis + Gebührendifferenz, vom Hof genau der Artikelpreis. Die Bestellung trägt danach den AKTUELLEN Stand: `totalAmount` = verbleibender Warenpreis, `serviceFeeCents` = neue Gebühr (Monatsabrechnung, Umsatz, Mails und Storno lesen ihn ohne Sonderweg), `erstattetCents` = Summe der von Stripe BESTÄTIGTEN Teilerstattungen, `OrderItem.fehltSeit` an der Position (ihre Snapshots bleiben). Nach dem Überschreiben gilt rechnerisch bezahlt = `totalAmount` + `serviceFeeCents` + `erstattetCents` — die Datenbank erzwingt das nicht; es folgt daraus, dass jede Rechnung vom gesperrten aktuellen Stand ausgeht und die neue Gebühr nie über der alten liegt. Einzige Ausnahme: Eine nachgetragene Erstattung, die Stripe von einem älteren Stand aus gebucht hat, wird mit ihrem gebuchten Betrag eingetragen (Sentry `erstattung_abweichend` nennt den Unterschied). Der Schema-Kommentar zu `erstattetCents` nennt noch die alte Grenze (`totalAmount + serviceFeeCents`). Fehlt der letzte Artikel, ist es ein normaler Storno. Ein fehlender Artikel geht NICHT zurück in den Vorrat, auch nicht beim Storno danach (er war nie da); Heute, Packliste und Papier zeigen ihn nicht, Kundenseiten mit „fehlt leider · nicht berechnet". **Reihenfolge (Ausnahme von „erst bedingt schreiben, dann Stripe"):** `meldeFehlendenArtikel` (`src/server/artikel-fehlt.ts`) sperrt die Bestellzeile (`SELECT … FOR UPDATE`, `farmId` in der Bedingung), liest, ruft Stripe INNERHALB der Sperre (Schlüssel `teilstorno-<orderId>-<itemId>` bzw. `teilstorno-hof-<orderId>-<itemId>`) und schreibt erst danach bedingt auf den gelesenen Stand. Vorher trägt sie Erstattungen nach, die Stripe gebucht hat, die Datenbank aber nicht kennt (verlorene Antwort, abgelaufene Transaktion; höchstens `NACHTRAGEN_HOECHSTENS` je Meldung) — mit dem gebuchten Betrag, die gemeldete Position danach vom berichtigten Stand. So vermerkt die Datenbank nie eine Erstattung, die Stripe nicht bestätigt hat, und keine Position wird zweimal erstattet; ein Stripe-Fehler rollt alles zurück (derselbe Knopf versucht es erneut und findet eine schon erfolgte Erstattung). **Zeitgrenze, Pflicht für jeden Stripe-Aufruf in einer Sperre:** Request-Optionen `STRIPE_OPTIONEN` (`maxNetworkRetries: 0` — sonst wiederholt das SDK still zweimal —, `timeout` 4 s), höchstens `STRIPE_AUFRUFE_HOECHSTENS` Aufrufe; die Transaktion (`TRANSAKTION_MS`) ist deren Summe plus 10 s für die Datenbank, dazu höchstens `VERBINDUNG_WARTEN_MS` Warten auf eine Verbindung. Die Seiten, deren Server Actions solche Transaktionen halten (`/orders`, `/orders/[orderId]`), setzen `export const maxDuration` über diese Summe (60 s; `tests/teilerstattung.test.ts` prüft die Rechnung). Läuft sie trotzdem ab, trägt der nächste Versuch nach, und zwei gleichzeitige Meldungen rechnen nacheinander vom jeweils aktuellen Stand — ohne Sperre erstattete die zweite die Gebührendifferenz doppelt (Gegenprobe in `tests/integration/artikel-fehlt.int.test.ts`). Die Mail an die Kundin (`sendArtikelFehlt`) geht nach dem Schreiben über `nachDerAntwort`. Der Storno liest Beträge und Positionen frisch UNTER der Sperre seines Statuswechsels (`tx.order.findFirst` nach dem `updateMany`).
- **Der PaymentIntent entsteht mit festem Stripe-Schlüssel `pi-<Bestell-ID>` und Parametern aus der GESPEICHERTEN Bestellung** (`intentParameter` in `src/app/api/checkout/route.ts`) — nie ungeschützt: Bestellung und Bestand stehen dann schon. Scheitert Stripe, wird die Bestellung über `storniereUnbezahlteBestellung` beendet und der Checkout antwortet 503 `ZAHLUNG_NICHT_MOEGLICH`; ein Stripe-409 (derselbe Schlüssel läuft gerade) ist kein Ausfall. Die Intent-ID wird nur an eine noch offene Bestellung gehängt (`haengeIntentAn`), sonst wird der Intent abgebrochen. Eine Wiederholung ohne gespeicherte Intent-ID holt mit demselben Schlüssel denselben Intent; nach zwei Minuten gilt sie als gescheitert — die Stripe-Aufrufe bleiben mit kurzem Timeout darunter.
- **Stripe ist Pflicht für jeden Hof (Register Z1).** Kein Server-Weg schreibt `Farm.acceptsOnline` auf etwas anderes als true (alles unter `src/server`, API-Routen, `src/lib`, die Einstellungs-Formulare; `tests/stripe-pflicht.test.ts` wacht am Quelltext) — eine Wahl „nur bar" gibt es nicht. Auf true setzen es nur `createConnectAccount`, `createOnboardingLink` (wer Stripe einrichtet, will online kassieren) und `schalteOnlineZahlungEin` (Bestandshof mit fertigem Stripe, `/settings/payments`; Zod `onlineZahlungEinschaltenSchema`, Besitz in der WHERE-Klausel), immer nur für den eigenen Hof. Gelesen wird das Feld weiter (Checkout, Notbremse `onlineZahlungPausiert`, Admin-Kennzeichen „Online-Zahlung aus"). Freischalten verlangt Stripe (`freischaltSperre`). Texte zur Pflicht nur aus `konditionen.ts` (`ONLINE_ZAHLUNG_EINRICHTEN_SATZ`, `ONLINE_ZAHLUNG_START_SCHRITT`).
- **`Farm.stripeAccountReady` schreibt nur `stripeKontoBereit`** (`src/lib/stripe-konto.ts`: Zahlungen UND Auszahlungen frei) — beim Onboarding, bei „Status prüfen" und bei `account.updated`. Einzige Ausnahme: Kennt Stripe das Konto nicht, setzt `vermerkeUnbekanntesHofKonto` false (nächster Punkt). Connect-Events kommen über einen eigenen Stripe-Endpunkt mit eigenem Secret an dieselbe Webhook-Route; sie prüft gegen `STRIPE_WEBHOOK_SECRET` und `STRIPE_CONNECT_WEBHOOK_SECRET`. Ereignisse mit `event.account` laufen nur durch `account.updated`, und das liest den aktuellen Kontostand bei Stripe nach (Ereignisse kommen nicht garantiert in Reihenfolge).
- **Modus-Wache und Testbetrieb (Register Z2, seit Nr. 42).** Den Stripe-Modus kennt nur `bestimmeUmgebung` (Präfix des Schlüssels, nie der Schlüssel; `sk_`/`rk_` gleich behandelt). Zwei Regeln in `src/lib/stripe-modus.ts`, rein: `stripeStartGesperrt` — **fail-closed**: Ein Live-Schlüssel (`sk_live_`, `rk_live_`) startet den Client NUR im Produktions-Deployment bei Vercel (`art` produktion UND `VERCEL_ENV === 'production'`, Feld `vercelProduktion`); in jeder anderen Lage (Vorschau, `next dev`, `next start`, Vitest/CI, test:integration, Unbekanntes) wirft `stripeClient()` `StripeModusGesperrt` (deutsche Meldung ohne Schlüssel), Sentry einmal je Instanz nur mit Umgebung und „live“. Test-Schlüssel starten überall. Die Wache vertraut `VERCEL_ENV`: Lokal gezogenes `VERCEL_ENV=production` lässt `next start` mit Live-Schlüssel starten, und ohne die Vercel-Systemvariablen („Automatically expose System Environment Variables“) sperrt sie auch die Produktion — die Meldung für „produktion“ nennt deshalb beide Auswege. Wer die Sperre erkennen muss, fragt `istModusSperre` (am Namen, ohne SDK-Modul): Der Webhook antwortet dann 503 „Zahlungsdienst vorübergehend nicht verfügbar.“ statt 400 „Signatur ungültig“ — nach außen neutral, weil die Antwort vor der Signaturprüfung kommt; die Einzelheiten nur ins Protokoll. `istTestbetrieb` — Produktion mit Test-Schlüssel. Der Wahrheitswert steht als `TESTBETRIEB` in `src/lib/umgebung-server.ts`; Kasse (Seite → `CheckoutForm` → `kassenZahlarten`), Admin-Layout (→ `AdminShell`) und `/settings/payments` lesen nur ihn, an Client-Komponenten geht er als Prop. Die drei Sätze nur aus `TESTBETRIEB_TEXT`. Mit Live-Schlüssel verschwinden sie von selbst — kein Schalter, keine Spalte (Register Z3: kein Umschalter in der Produktion). Beträge und Zahlarten ändert der Testbetrieb nicht.
- **Ein Hof-Konto, das Stripe nicht kennt (Register Z2, seit Nr. 42)** — erkannt in `src/lib/stripe-konto.ts` NUR dort, wo das Hof-Konto die einzige Kennung im Aufruf ist. Kasse (Zielkonto des PaymentIntents, auch die Wiederholung): `istUnbekanntesStripeKonto`, streng — „No such account/destination“ oder `resource_missing` an einem Konto-Parameter (`transfer_data[destination]`, `destination`, `account`); `resource_missing` allein (etwa an `intent`) zählt nicht. Reine Konto-Aufrufe mit der gespeicherten Kennung (Kontostatus, Einrichtungs- und Login-Link, Rückkehr aus dem Onboarding, die Prüfung in `createConnectAccount`): `istUnzugaenglichesStripeKonto` — zusätzlich der Zugriffsfehler `account_invalid` bzw. „does not have access to account“, denn gespeicherte Kennungen stammen immer aus dem eigenen `accounts.create` (Grenze: derselbe Fehler kommt bei einem Plattform-Schlüssel aus dem falschen Stripe-Konto — dann gilt jeder Hof als unbekannt; das Betriebsdokument lässt den Menschen das vor dem Umschalten prüfen). Dann `vermerkeUnbekanntesHofKonto(farmId, kennung)` (`src/server/hofkonto-unbekannt.ts`, wirft nie): `stripeAccountReady` per `updateMany` mit `id`, DERSELBEN `stripeAccountId` und `stripeAccountReady: true` auf false; Sentry höchstens einmal je Hof und Tag über `DB_BREMSEN.stripeKontoUnbekannt` (Bremse in der Datenbank, Merkmal Hof-ID, fail-open), nur mit Hof-ID. Die Kennung wird **nie automatisch** gelöscht oder ersetzt. Die Kasse storniert (Bestand zurück), lässt die Halte der Sitzung stehen und antwortet 503 `ZAHLUNG_NICHT_MOEGLICH` mit `hofKontoUnbekanntText` und `onlineAus` (Formular stellt auf bar); danach bietet sie Online wie ohne Konto nicht an. Der Hof landet auf `/settings/payments?stripe=neu` („Online-Zahlung neu einrichten“, `zahlungHinweis`). Nach dem Vermerk rendern die Actions Zahlung, Einstellungen, Heute, Verkäufe und Hofseite neu (`revalidatePath`); eine Meldung, die das überleben muss, hängt an einer Komponente, die eingehängt bleibt. Ersetzen darf die Kennung nur `createConnectAccount` auf den Knopf des Hofs, wenn Stripe das gespeicherte Konto in diesem Moment nachweislich nicht kennt oder den Zugriff verweigert — `accounts.create` mit Idempotenz-Schlüssel aus Hof-ID, alter Kennung und 15-Minuten-Fenster (`neuEinrichtenSchluessel`; Doppelklick, sofortiger Neuversuch → dasselbe Konto; das Fenster, weil Stripe unter einem Schlüssel 24 Stunden auch Fehler festhält), bedingt auf die alte Kennung (`updateMany`, `count` 0 → Satz, nichts überschrieben), alte und neue Kennung mit Hof-ID ins Server-Protokoll (`console.info`); kennt Stripe es, bleibt alles. Der Webhook (`account.updated`) ist davon unberührt.
- **Jede Erstattung trägt einen festen Idempotenz-Schlüssel je Bestellung und Anlass** (`storno-<id>`, `storno-hof-<id>` für die Rückbuchung des Reststornos, `teilstorno-<id>-<positionId>` und `teilstorno-hof-<id>-<positionId>`, `servicegebuehr-nicht-abgeholt-<id>`, `spaet-bezahlt-<id>`): Erreicht ein zweiter Aufruf Stripe, kommt dieselbe Erstattung zurück, keine zweite.
- **Ein Stripe-Ereignis ändert eine Bestellung nur aus dem Zustand, für den es gilt** — bedingtes `updateMany` wie oben, nie Lesen und blind Schreiben (`src/app/api/stripe/webhook/route.ts`).
  - `payment_intent.payment_failed` ist kein Endzustand, der PaymentIntent bleibt bezahlbar: nur `paymentStatus` FAILED vermerken, nie stornieren, nie Bestand.
  - Endgültig ist `payment_intent.canceled`. Ohne den Hof (Webhook, Aufräumrunde) beendet eine unbezahlte Bestellung nur `storniereUnbezahlteBestellung` (`src/server/unbezahlte-bestellung.ts`): Storno aus PENDING_CONFIRMATION, Gebühren-Vermerk und Rückbuchung in einer Transaktion. Der Hof storniert über `cancelOrder`.
  - `payment_intent.succeeded` setzt PAID nur aus PENDING_CONFIRMATION. Trifft es eine Bestellung, die storniert wurde, ohne je bezahlt gewesen zu sein: sofort voll erstatten (Regel oben), Sentry-Alarm, Mail an die Kundin — nie wiederbeleben. Einzige Ausnahme von „erst bedingt schreiben, dann Stripe": Hier kommt die Erstattung vor dem bedingten Vermerk REFUNDED, weil der Vermerk erst stehen darf, wenn das Geld zurück ist. Vor doppelter Erstattung schützt der Schlüssel, der Vermerk sperrt die Mail.
- **Scheitert die Erstattung eines Stornos, bekommt der Hof nie eine Anweisung, die er nicht ausführen kann** (er hat keinen Zugang zum Plattformkonto): Text „Rückerstattung fehlgeschlagen. Wir kümmern uns um die Erstattung und melden uns.", dazu Sentry und eine Mail an den Betreiber (`sendErstattungOffen` an `SUPPORT_EMAIL`, nach der Antwort, ohne Daten der Kundin). Die Handanweisung folgt dem Weg, der wirklich genommen wurde (`handbuchungFuer`: Rest mit festen Beträgen aus `rest`, Vollerstattung oder „Stand unbekannt"), nie pauschal der Vollerstattung.
- **Auch die Vollerstattung des Stornos trägt Merkmale** (seit Nr. 27): `metadata` aus `vollstornoMerkmal` (`orderId`, `anlass: 'vollstorno'`, `art: 'kunde'`), Schlüssel weiter `storno-<id>`. Sie zählt nie als Teil- oder Rest-Storno (`ordneZu` gibt null — taucht sie daneben auf, bleibt das Bild „unklar"). Gibt `refunds.create` eine Erstattung mit Status `failed`/`canceled` zurück, gilt sie wie bei der Teilerstattung nicht als erstattet (kein REFUNDED, Weg „Erstattung offen"); der Storno setzt dann den Meldevermerk `<refundId>#gescheitert-gemeldet` (Voll- und Rest-Storno), damit ein späteres `refund.failed` derselben Erstattung nicht ein zweites Mal meldet. Sie läuft ohne `STRIPE_OPTIONEN`, weil sie in keiner Sperre steht (die SDK-Wiederholung mit demselben Schlüssel ist dort erwünscht).
- **Eine später gescheiterte Erstattung** (`refund.failed`, `charge.refund.updated`; `src/server/erstattung-gescheitert.ts`) wird nur zurückgenommen, wenn sie nachweislich unsere ist: Merkmale in `metadata` (`ordneZu`) UND die Bestellung gehört zur Zahlung der Erstattung. **Eine gescheiterte Vollerstattung** (`anlass: 'vollstorno'`) nimmt den Zahlstand zurück, nie einen Betrag: REFUNDED → PAID bedingt auf storniert, REFUNDED und `erstattetCents` 0, nur wenn ihr Betrag genau Warenpreis + Gebühr ist und Stripe (eine Seite `refunds.list`, `STRIPE_OPTIONEN`) keine weitere zählende Erstattung kennt (`zuruecknahmeNachGescheiterterVollerstattung`); Vermerk und Meldung wie unten. Eine Vollerstattung ohne Merkmale (vor Nr. 27) bleibt „fremd": nur gemeldet. Zurückgenommen wird nicht durch Senken um den Betrag, sondern bedingt auf Stripes Summe der zählenden, zugeordneten Erstattungen, und nur wenn die Datenbank genau um die gescheiterte darüber liegt (`zuruecknahmeNachGescheiterterErstattung`) — so ist es je Erstattung idempotent, auch bei beiden Ereignissen und erneuter Zustellung. `paymentStatus` REFUNDED → PAID bedingt. Die Erstattung des Ereignisses zählt dabei nie mit, auch wenn `refunds.list` sie noch als `pending` führt (`ladeStripeStand(…, { gescheitert })`) — das Ereignis ist verbindlich. Jeder Ausgang außer „nicht gescheitert“ wird genau einmal je Erstattung gemeldet, auch „schon erledigt“ (nie gezählt, das Geld steht trotzdem aus); Vermerk `<refundId>#gescheitert-gemeldet` in `WebhookEvent` — die Zurücknahme legt ihn in derselben Transaktion an (`createMany` mit `skipDuplicates`) und meldet immer, alle anderen Ausgänge melden nur, wenn sie den Vermerk als Erste anlegen. Ein unklares Bild (auch eine Zahlung ohne Überweisung, `ohne_ueberweisung`) antwortet 200 mit Meldung, nie 500 ohne Meldung.
- **Im Webhook kein Mailversand im Antwortpfad.** Mails laufen über `nachDerAntwort`, jede einzeln abgefangen. Eine 500 heißt für Stripe „erneut zustellen" — sie ist nur erlaubt, wenn Daten oder Geld nicht verarbeitet sind, sonst gehen die Mails doppelt raus.
- **Was ein Storno an Geld bewegt, rechnet `src/lib/storno.ts`** — dieselbe Funktion für den Storno-Dialog und für `cancelOrder`. Wer den Ladungstyp im Checkout ändert, ändert den Storno mit; `tests/storno-erstattung.test.ts` (Ladungstyp-Wache) schlägt sonst an.

### Taxonomie (Kategorien, Unterkategorien, Siegel)

`src/lib/taxonomie.ts` ist die **einzige** Quelle für Werte und Labels. Kein zweites Label-Verzeichnis, kein Hof-Sonderfall anderswo. Anzeige nur über `formatKategorie` in `format.ts`.

- **Jede Unterkategorie (L2) gehört zu genau einer Kategorie (L1).** `gehoertZu(l1, l2)` entscheidet; das Zod-Schema lehnt jede andere Kombination ab. Einzige Ausnahme: `VORBEREITETE_UNTERKATEGORIEN` — Werte, die schon im Prisma-Enum stehen (Expand), aber noch zu keiner L1 gehören (seit Nr. 20 leer). `gehoertZu` sagt für sie immer false, damit lehnt Zod sie ab und nichts bietet sie an. Wer sie wählbar macht, verschiebt sie in `TAXONOMIE` und leert die Liste. Fisch, Brot, Getränke, Sonstiges, Mischfutter und Ergänzungsfutter haben keine L2; Brennholz hat seit Nr. 20 die Arten Brennholz (Scheite), Anzündholz, Hackschnitzel (E11). Keine dritte Ebene, keine Freitext-Kategorien. Der Enum-Wert `BRENNHOLZ` heißt in der Oberfläche „Brennmaterial" (`KATEGORIE_LABEL`, E11 Label seit Nr. 23) — Chips, Abschnitte und Filter nehmen das Label, nie ein eigenes Wort.
- **Eine fehlende L2 ist kein Fehler.** Bestandsprodukte dürfen ohne bleiben; das Formular zeigt nur einen Hinweis. Einzige Ausnahme: Futter-Kategorien mit Sorten (Heu & Stroh, Getreide & Körner).
- **Siegel sind orthogonal zur Kategorie.** `labels` ist eine Menge (BIO, GENTECHNIKFREI, AMA_GUETESIEGEL), mehrere je Produkt, keines Pflicht, keines doppelt. `isOrganic` ist Altlast: wird nur noch gelesen, nie mehr geschrieben; Bio ist `labels` enthält BIO.
- **Neue Produkte brauchen eine Kategorie** (`productAnlegenSchema`) — ohne landen sie im Bereich Sonstiges zwischen den Lebensmitteln. Bestandsprodukte ohne Kategorie bleiben speicherbar; die Produktliste zeigt einen Chip. Nachtragen aus der Liste nur über `setzeKategorie` (schreibt Kategorie, Unterkategorie, MwSt-Vorbelegung, nur solange die Kategorie leer ist) — nie über `updateProduct` mit Listendaten, das schriebe einen veralteten Bestand zurück.
- **Kategorie-Vorschlag ist nie eine Wahl.** `kategorieVorschlag(name)` in `taxonomie.ts` liefert nur bei genau einem eindeutigen Treffer etwas; Wörter aus `DUAL_USE` nie. Übernommen wird erst mit einem Tipp; Futtermittel nie mit einem Tipp aus der Liste (Kennzeichnung fehlt).
- **Futter-Kennzeichnung nur im Bereich Futtermittel.** Dort Pflicht (Futtermittelart passend zur Kategorie, Nettomenge, Tierarten, Zusammensetzung, analytische Bestandteile, Bestätigung), sonst verboten. Ein Kategoriewechsel aus dem Bereich heraus löscht sie in derselben Transaktion wie das Produkt-Update.
- **Pflicht-Bestätigung des Hofs (E10a, seit Nr. 23).** Wortlaut `FUTTER_BESTAETIGUNG_TEXT`, Zeitpunkt in `FutterKennzeichnung.bestaetigtAm`. Beim Anlegen verlangt das Schema den Haken (`futterKennzeichnungSchema`, Futter-Formular). Beim Bearbeiten entscheidet der Server mit dem gespeicherten Stand: `updateProduct` vergleicht, was es schreiben würde (`produktDaten`, `futterDaten`), mit genau diesen Spalten aus der Datenbank (`brauchtNeueBestaetigung` in `src/lib/futter-registrierung.ts`); ändert sich etwas außer `OHNE_NEUE_BESTAETIGUNG` (Preis, Vorrat, Sichtbarkeit, Foto) und fehlt der Haken, antwortet es mit Code `BESTAETIGUNG` und schreibt nichts. Ohne Änderung bleibt der alte `bestaetigtAm`. Der Haken wird beim Bearbeiten nie vorbelegt. Ein neuer Schreibweg auf Futter-Angaben fragt dieselbe Funktion.
- **Futter-Texte für Hof und Kundin aus EINER Quelle** (`src/lib/futter-registrierung.ts`): Haken, Kopfhinweis „zur Orientierung" samt BAES-Adresse (`BAES_FUTTERMITTEL_URL`, nur dort), Verantwortungs-Hinweis für Kundinnen (`futterVerantwortung`, im Korb `futterVerantwortungImKorb` — reine Anzeige, ändert nie die Warenkorb-Prüfung). `tests/futter-bestaetigung.test.ts` sucht die Wortlaute im Quelltext.

### Bereiche (Lebensmittel, Futtermittel, Sonstiges)

Konzept: `docs/konzepte/bereiche.md`.

- **Bereich ist abgeleitet.** `bereichVon(category)` in `taxonomie.ts` entscheidet. Nie als Spalte, nie in `localStorage`, nie `category === '…'` vergleichen, wo der Bereich gemeint ist. Im Browser nur zur Anzeige und Formularführung (dieselbe Funktion) — verbindlich prüfen Zod und die Servergrenze.
- **Angezeigt werden zwei Bereiche: „Hofladen" und „Futtermittel".** `anzeigeBereichVon` und `ANZEIGE_BEREICHE` in `taxonomie.ts` (Hofladen = Lebensmittel + Sonstiges). Das Label steht nur dort — nie „Lebensmittel" als Bereichsname in der Oberfläche, keine zweite Label-Tabelle.
- **Kaufbar heißt: sichtbar UND freier Bestand > 0** — `istKaufbar` in `src/lib/bereiche-anzeige.ts`. Chips, Suche, Facetten, Karte und Kilopreis-Sortierung fragen nur dort.
- **Verkaufsgrößen sind eine Produktfamilie (E3, seit Nr. 20).** Je Größe ein Produkt mit eigenem Preis, `stock` und eigener Kennzeichnung (Nettomenge je Gebinde); zusammengehalten von `Product.familieId` (vom Server vergeben, kein Fremdschlüssel). Angelegt wird eine Familie in EINER Transaktion über `legeFutterFamilieAn` bzw. `legeBrennmaterialFamilieAn` (`src/server/actions/produktfamilie.ts`, Schemas `src/schemas/produktfamilie.ts`); der Name je Größe ist `groessenProduktname` (Familie + Größe), bearbeitet wird je Größe im Produktdialog. Neue Futtermittel entstehen nur so — `createProduct` lehnt Futter ab, `updateProduct` den Wechsel eines Nicht-Futter-Produkts auf eine Futter-Kategorie (beide `FUTTER_NUR_UEBER_FORMULAR`); der Produktdialog bietet die Futter-Kategorien dann gar nicht an. Ein Futtermittel ohne Verpackung ist damit immer Altbestand.
- **Abholhinweise eines Futters (N23, seit Nr. 123).** `Product.abholhinweise` ist eine Liste der Aufzählung `Abholhinweis` (`ANHAENGER_NOETIG`, `FRONTLADER`, `NACH_ABSPRACHE`; NOT NULL, Standard leer). Werte, Wörter und Symbole stehen nur in `src/lib/abholhinweise.ts`, das Zod-Feld `abholhinweiseSchema` in `src/schemas/product.ts` (höchstens drei, keine Doppelten). Geschrieben wird nur über `abholhinweiseDaten` (`src/server/produkte-schreiben.ts`): im Bereich Futtermittel geordnet wie die Auswahl, sonst immer die leere Liste. Einstiege: neues Futter (`legeFutterFamilieAn`, jede Größe übernimmt die Hinweise der Familie), Bearbeiten (`updateProduct`; eine geänderte Wahl verlangt den Haken neu wie jede Produktangabe außer Preis, Vorrat, Foto, Sichtbarkeit). Gelesen von der Produktliste, der Produktseite (`OEFFENTLICHES_PRODUKT_SELECT`) und „Futter kaufen".
- **Sperre je Gebinde (E10, S7, seit Nr. 20).** Welche Registrierung ein Gebinde braucht und ob der Hof sie hat, entscheidet nur `gebindeSperre` (`src/lib/futter-registrierung.ts`): Verpackung `LOSE_BALLEN` → LFBIS (eine Nummer am Hof), `ABGEPACKT_ETIKETT` sowie Mischfutter und Ergänzungsfutter → BAES (Status Registriert/Zugelassen). Produkte ohne Verpackung (Bestand) sperrt sie nie. Durchgesetzt mit dem Stand des Hofs FRISCH aus der Datenbank (`ladeHofRegistrierung`) an allen Wegen in den Shop: beim Anlegen (gesperrte Größen entstehen als Entwurf), am Schalter „Sichtbar" (`produktSichtbarkeitSetzen`, Code `GESPERRT`), beim Bearbeiten (`updateProduct` speichert gesperrt als Entwurf, `hinweis`), nach einem Wechsel von Nummer oder Status im Hofprofil (`nimmGesperrteAusDemShop`) und vor dem Checkout im Warenkorb-Abgleich (`pruefeSitzungsWarenkorb`: gesperrt = nicht verkäuflich). Die Plattform prüft die Nummer nicht (E9).
- **Behördenkontakt BAES — einzige freigegebene Ausnahme** zu „keine echten E-Mails oder Telefonnummern im Code" (CLAUDE.md; Freigabe Lauf 7 §11, Nr. 36): E-Mail und Telefon des BAES stehen nur in `BAES_KONTAKT` in `src/lib/futter-registrierung.ts`, Links und Vorlese-Texte werden daraus gebaut; `tests/futter-bestaetigung.test.ts` zählt die Vorkommen in `src/`, Tests prüfen nur über den Import. Jede weitere Ausnahme braucht eine eigene Freigabe des Menschen.
- **Ein Produkt gehört zu genau einem Bereich.** Dual-Use (Mais als Lebensmittel und als Futter) = zwei Produkte mit zwei Beständen, ohne Verknüpfung im Schema.
- **`OrderItem.vatRate` ist ein Snapshot.** Der Checkout-Handler schreibt ihn aus `Product.vatRate` im selben `create` wie die Bestellung. Nie nachlesen, nie rückwirkend ändern. `mwstStandard` ist nur die Vorbelegung im Formular.

Fachkonzepte liegen unter docs/konzepte/. Ein Sprint verweist auf sein Konzept, statt es zu wiederholen.
