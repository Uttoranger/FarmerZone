## Messung und Grenzen
- Lasttest (echtes Postgres, Resend-Attrappe, 200 ms Abstand): 5.020 Mails in 10,2 s, 51 Stapel, ein Lauf = 494 Mails/s; Einstellen von 5.020 Aufträgen 1,9 s. Alle 20 Wichtig im ersten Stapel, keine doppelt, keine verloren.
- Grenze des Workers: 100 je Stapel × 5 Anfragen/s = 500/s, 30.000 je Minute, ~25.000 je 50-s-Lauf. Die echte Grenze ist das Kontingent (Resend Free 100/Tag).
- `batch.send` (resend 6.12.4, `index.d.cts`): `CreateBatchEmailOptions = Omit<CreateEmailOptions, 'attachments' | 'scheduledAt'>` → `headers` je Mail gehen; `CreateBatchRequestOptions extends PostOptions, IdempotentRequest` → ein `idempotencyKey` je Anfrage; `batchValidation` strict/permissive. Gewählt: strict (n-te ID = n-te Mail); 4xx auf den Stapel → einzeln.
- Vercel Pro und Cron jede Minute: Vercel-Doku (vercel.ts, „Configure cron jobs“) zeigt `* * * * *` als Beispiel; die Tarif-Tabelle (Hobby täglich, Pro minütlich) war von hier nicht abrufbar, TECH_STACK sagt nur „Vercel Pro seit 19.10.2026“. Nach dem Deploy in Vercel › Cron Jobs prüfen.

- „Nach 5 Versuchen gescheitert“ = fünf Wiederholungen (1, 5, 15, 60, 240 min); beim sechsten Fehlschlag gescheitert (`versuche` 6).
- Advisory-Lock als `pg_try_advisory_xact_lock` in einer Transaktion, die den Lauf über offen bleibt (Pooler im Transaktionsmodus); „genau einmal“ hängt an SKIP LOCKED.
- `fehlerCode` = `error.name` von Resend (`rate_limit_exceeded` …), sonst `ausnahme`/`renderer_fehler`/`kein_renderer`.
