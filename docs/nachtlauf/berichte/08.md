### Beleg: Versuche zählen in der Datenbank, über Instanzen hinweg

In `better-auth@1.6.23`, `dist/plugins/email-otp/routes.mjs`, prüft `atomicVerifyOTP` so:

```js
const consumed = await ctx.context.internalAdapter.consumeVerificationValue(identifier); // Zeile in einer Transaktion löschen
const [otpValue, attempts] = splitAtLastColon(consumed.value);                        // "<hash>:<versuche>"
if (usedAttempts >= allowedAttempts) throw APIError.from("FORBIDDEN", TOO_MANY_ATTEMPTS);
if (!await verifyStoredOTP(...)) {
  await ctx.context.internalAdapter.createVerificationValue({ value: `${otpValue}:${usedAttempts + 1}`, identifier, expiresAt: consumed.expiresAt });
  throw APIError.from("BAD_REQUEST", INVALID_OTP);
}
```

Der Zähler steht also in der Zeile `Verification.value`, nicht im Speicher. `tests/integration/anmeldecode.int.test.ts` lädt `auth` zweimal frisch (`vi.resetModules`), wie zwei Serverless-Instanzen: 3 Fehlversuche auf A und 2 auf B ergeben `…:5` in der Datenbank, danach nimmt B auch den richtigen Code nicht mehr an (`TOO_MANY_ATTEMPTS`). Die Gegenprobe: Nach 4 Fehlversuchen nimmt der richtige Code noch an, und zwar genau einmal. Eine zweite Gegenprobe: Mit `allowedAttempts = 3` werden beide Tests rot. **Keine Schema-Änderung nötig:** Das Plugin nutzt die bestehende Tabelle `Verification` (identifier, value, expiresAt).

## Was nicht gelöst wurde und warum

- **Rate-Limit-Speicher in der Datenbank** (`rateLimit.storage: 'database'`): Better Auth bräuchte dafür eine eigene Tabelle, und Schema-Änderungen sind in Gate 4 nicht freigegeben. Die IP-Bremse und die Bremse je Adresse gelten deshalb weiter je Instanz. Die Grenze über alle Instanzen sind die 5 Versuche je Code in der Datenbank. S4 verlangt genau diesen Zähler.
- **Magic-Link-Plugin ganz entfernen:** Ich habe es bewusst noch nicht gemacht. Links, die kurz vor dem Deployment verschickt wurden, sind 15 Minuten gültig und sollen noch funktionieren. Das Anfordern ist zu (404), nur `/magic-link/verify` bleibt offen. Plugin, `sendMagicLinkEmail` und `customer-magic-link.tsx` können in einem kleinen Aufräum-PR nach dem Deployment entfallen. Sonst nutzt nichts den Magic Link (geprüft per grep).
- **„Bestellungen finden"** gehört zu Nr. 14. Es kann die Code-Anmeldung so wiederverwenden: `KundeCodeFormular` mit eigenem `ziel`, dazu `zielNachAnmeldung(roh, '/<ziel>')`. Ablauf, Texte und Bremsen bleiben dieselben.
- **Keine `loading.tsx`:** `/account/login` wartet auf keine Datenbank. `/login` liest nur die Sitzung, und das geht schnell (DESIGN_SYSTEM: Ladeansicht nur dort, wo gewartet wird).
- **Zeitunterschied Hof/Kundin beim Anfordern:** Für eine Hof-Adresse wird keine Mail gerendert, die Antwort kommt deshalb etwas schneller. Den Mailversand in den Hintergrund zu verlegen (`advanced.backgroundTasks`) wäre eine eigene Infrastrukturfrage. Der Magic Link hatte dasselbe Verhalten.

## Annahmen

- **Höfe bekommen keinen Code**, auch wenn ihre Adresse in der Kundenkarte eingetippt wird. Die Seite zeigt trotzdem „Wir haben dir einen Code geschickt", damit niemand erfährt, ob hinter einer Adresse ein Hof steht. Gründe: E7 („Höfe bleiben bei E-Mail und Passwort"), und Better Auth entzieht einem noch unbestätigten Konto beim ersten Code das Passwort (`revokeUnprovenAccountAccess`). Beim Magic Link war beides noch möglich.
- **Neue Adressen bekommen beim ersten Anmelden ein Kundenkonto ohne Passwort**, genau wie bisher beim Magic Link (`disableSignUp: false`). Das ist die bestehende freiwillige Anmeldung, die E8 bestehen lässt. Neu angeboten wird nichts, es gibt weder „Konto anlegen" noch einen Konto-Satz.
- **Code nicht im Betreff:** `sendRaw` schreibt den Betreff auch in Produktion ins Vercel-Log, und der Sperrbildschirm zeigt Betreff und Vorschautext jedem, der danebensteht. Der Code steht deshalb nur im Text, und das Telefon setzt ihn über `one-time-code` trotzdem ein.
- **Kein Link in der Code-Mail.** Grund: Ein Link aus einer Mail ändert nie einen Zustand (ARCHITECTURE §5).
- **Ungenutzte Plugin-Pfade gesperrt:** Gesperrt sind Passwort-Zurücksetzen per Code, E-Mail-Bestätigung und E-Mail-Wechsel per Code; Anfordern nimmt nur `sign-in` an. Sonst gäbe es einen zweiten Weg, das Passwort eines Hofs zu ändern.
- **Ein falscher Code leert das Feld**, der Fehlertext bleibt stehen. Das Feld nimmt nur 6 Ziffern, ohne Leeren müsste man erst löschen.
- **Die Anmeldung startet automatisch bei der sechsten Ziffer**, also auch, wenn das Telefon den Code einsetzt. Der Knopf „Anmelden" bleibt trotzdem da.
- **„Code erneut senden" wartet 60 s**, so lange wie das Fenster der IP-Bremse (3 je Minute).
- **Die Bremse je Adresse** (5 Codes in 15 Minuten) gibt es zusätzlich zum Auftrag. Sie schützt Postfächer, die von vielen IPs aus mit Codes zugeschüttet werden; wie alle Speicher-Grenzen gilt sie nur in Produktion.
- `/account/login` leitet eine schon angemeldete Kundin nicht um, wie bisher (siehe Kommentar in `kunden-navigation.ts`).

## Wie der Mensch es testet

Lokal ohne `RESEND_API_KEY` (dann steht der Code im Terminal), App wie im Rahmen gestartet:

1. `http://localhost:3000/account/login` am Laptop (≥ 1024 px): zwei Karten, links „Ich kaufe ein", rechts „Ich habe einen Hof". Eine erfundene Adresse eintippen und „Code schicken" drücken. Im Terminal steht `[DEV] Anmeldecode für …: 123456`. Die Karte zeigt jetzt sechs Kästchen, „Er gilt 10 Minuten." und „Code erneut senden (59 s)", das herunterzählt.
2. `000000` eintippen: Inline steht „Der Code stimmt nicht …", das Feld wird geleert. In der Datenbank endet `Verification.value` jetzt auf `:1`.
3. Fünfmal falsch, dann den richtigen Code: „Du hast den Code zu oft falsch eingegeben …".
4. „Code erneut senden" (nach 60 s), dann den neuen Code eintippen: Die Seite leitet auf `/account/profile` weiter, oben steht „Mein Konto".
5. Abgelaufen: einen Code anfordern, dann in der Test-DB `update "Verification" set "expiresAt" = now() - interval '1 minute' where identifier = 'sign-in-otp-<adresse>'` und den Code eintippen. Es erscheint „Der Code ist abgelaufen – er gilt 10 Minuten …".
6. Ziel-Sicherheit: `http://localhost:3000/account/login?ziel=//example.com` und anmelden → Weiterleitung nach `/account/profile`, nicht zu example.com.
7. Hof: `http://localhost:3000/login` am Handy (390 px). Oben steht der Umschalter mit „Ich habe einen Hof" aktiv. `bauer-01@example.com` mit falschem Passwort ergibt „E-Mail oder Passwort falsch …", mit dem Seed-Passwort geht es nach `/dashboard`. Ein erneuter Aufruf von `/login` leitet nach `/dashboard`.
8. Hof-Adresse in der Kundenkarte: Die Seite zeigt den Code-Schritt, im Terminal steht aber KEIN Code.
9. Am echten Handy (Produktion/Preview mit Resend): Code anfordern, Mail öffnen. Der Betreff ist ohne Code; beim Antippen des Code-Felds schlägt die Tastatur den Code vor.
10. Beide Themes über den Schalter oben prüfen.

Geprüft im Nachtlauf (agent-browser, lokal): alle Schritte oben außer 9. Axe hatte 0 Verstöße auf beiden Routen, bei 390 und 1440 px, hell und dunkel, im E-Mail-, Code- und Fehlerzustand. Im Tastatur-Durchlauf (Sprunglink, Kopf, Feld, Knopf, Hof-Felder, Links) hat jedes Ziel einen sichtbaren Rahmen (`outline: solid 2px`). Screenshots unter `.nachtlauf/screens/08/` (390, 1024, 1440, hell und dunkel, Kunde E-Mail/Code, Hof, Fehler, abgelaufen; nicht committet).
