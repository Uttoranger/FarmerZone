### Beleg: Versuche zählen in der Datenbank, über Instanzen hinweg

In `better-auth@1.6.23`, `dist/plugins/email-otp/routes.mjs`, prüft `atomicVerifyOTP` so:

```js
const consumed = await ctx.context.internalAdapter.consumeVerificationValue(identifier); // Zeile in einer Transaktion löschen
const [otpValue, attempts] = splitAtLastColon(consumed.value);                        // "<hash>:<versuche>"
if (usedAttempts >= allowedAttempts) throw APIError.from("FORBIDDEN", TOO_MANY_ATTEMPTS);
if (!await verifyStoredOTP(...)) {
  await ctx.context.internalAdapter.createVerificationValue({ value: `${otpValue}:${usedAttempts + 1}`, identifier, expiresAt: consumed.expiresAt });
  throw APIError.from("BAD_REQUEST", INVALID_OTP);
}
```

Der Zähler steht also in der Zeile `Verification.value`, nicht im Speicher. `tests/integration/anmeldecode.int.test.ts` lädt `auth` zweimal frisch (`vi.resetModules`), wie zwei Serverless-Instanzen: 3 Fehlversuche auf A und 2 auf B ergeben `…:5` in der Datenbank, danach nimmt B auch den richtigen Code nicht mehr an (`TOO_MANY_ATTEMPTS`). Die Gegenprobe: Nach 4 Fehlversuchen nimmt der richtige Code noch an, und zwar genau einmal. Eine zweite Gegenprobe: Mit `allowedAttempts = 3` werden beide Tests rot. **Keine Schema-Änderung nötig:** Das Plugin nutzt die bestehende Tabelle `Verification` (identifier, value, expiresAt).

## Was nicht gelöst wurde und warum

- **Rate-Limit-Speicher in der Datenbank** (`rateLimit.storage: 'database'`): Better Auth bräuchte dafür eine eigene Tabelle, und Schema-Änderungen sind in Gate 4 nicht freigegeben. Die IP-Bremse und die Bremse je Adresse gelten deshalb weiter je Instanz. Die Grenze über alle Instanzen sind die 5 Versuche je Code in der Datenbank. S4 verlangt genau diesen Zähler.
- **Magic-Link-Plugin ganz entfernen:** Ich habe es bewusst noch nicht gemacht. Links, die kurz vor dem Deployment verschickt wurden, sind 15 Minuten gültig und sollen noch funktionieren. Das Anfordern ist zu (404), nur `/magic-link/verify` bleibt offen. Plugin, `sendMagicLinkEmail` und `customer-magic-link.tsx` können in einem kleinen Aufräum-PR nach dem Deployment entfallen. Sonst nutzt nichts den Magic Link (geprüft per grep).
- **„Bestellungen finden"** gehört zu Nr. 14. Es kann die Code-Anmeldung so wiederverwenden: `KundeCodeFormular` mit eigenem `ziel`, dazu `zielNachAnmeldung(roh, '/<ziel>')`. Ablauf, Texte und Bremsen bleiben dieselben.
- **Keine `loading.tsx`:** `/account/login` wartet auf keine Datenbank. `/login` liest nur die Sitzung, und das geht schnell (DESIGN_SYSTEM: Ladeansicht nur dort, wo gewartet wird).
- **Zeitunterschied Hof/Kundin beim Anfordern:** Für eine Hof-Adresse wird keine Mail gerendert, die Antwort kommt deshalb etwas schneller. Den Mailversand in den Hintergrund zu verlegen (`advanced.backgroundTasks`) wäre eine eigene Infrastrukturfrage. Der Magic Link hatte dasselbe Verhalten.

## Annahmen

- **Höfe bekommen keinen Code**, auch wenn ihre Adresse in der Kundenkarte eingetippt wird. Die Seite zeigt trotzdem „Wir haben dir einen Code geschickt", damit niemand erfährt, ob hinter einer Adresse ein Hof steht. Gründe: E7 („Höfe bleiben bei E-Mail und Passwort"), und Better Auth entzieht einem noch unbestätigten Konto beim ersten Code das Passwort (`revokeUnprovenAccountAccess`). Beim Magic Link war beides noch möglich.
- **Neue Adressen bekommen beim ersten Anmelden ein Kundenkonto ohne Passwort**, genau wie bisher beim Magic Link (`disableSignUp: false`). Das ist die bestehende freiwillige Anmeldung, die E8 bestehen lässt. Neu angeboten wird nichts, es gibt weder „Konto anlegen" noch einen Konto-Satz.
- **Code nicht im Betreff:** `sendRaw` schreibt den Betreff auch in Produktion ins Vercel-Log, und der Sperrbildschirm zeigt Betreff und Vorschautext jedem, der danebensteht. Der Code steht deshalb nur im Text, und das Telefon setzt ihn über `one-time-code` trotzdem ein.
- **Kein Link in der Code-Mail.** Grund: Ein Link aus einer Mail ändert nie einen Zustand (ARCHITECTURE §5).
- **Ungenutzte Plugin-Pfade gesperrt:** Gesperrt sind Passwort-Zurücksetzen per Code, E-Mail-Bestätigung und E-Mail-Wechsel per Code; Anfordern nimmt nur `sign-in` an. Sonst gäbe es einen zweiten Weg, das Passwort eines Hofs zu ändern.
- **Ein falscher Code leert das Feld**, der Fehlertext bleibt stehen. Das Feld nimmt nur 6 Ziffern, ohne Leeren müsste man erst löschen.
- **Die Anmeldung startet automatisch bei der sechsten Ziffer**, also auch, wenn das Telefon den Code einsetzt. Der Knopf „Anmelden" bleibt trotzdem da.
- **„Code erneut senden" wartet 60 s**, so lange wie das Fenster der IP-Bremse (3 je Minute).
- **Die Bremse je Adresse** (5 Codes in 15 Minuten) gibt es zusätzlich zum Auftrag. Sie schützt Postfächer, die von vielen IPs aus mit Codes zugeschüttet werden; wie alle Speicher-Grenzen gilt sie nur in Produktion.
- `/account/login` leitet eine schon angemeldete Kundin nicht um, wie bisher (siehe Kommentar in `kunden-navigation.ts`).

### Belege

- **Hook-Antwort ohne Endpunkt:** In `better-auth@1.6.23`, `dist/api/dispatch.mjs` (`runBeforeHooks`), wird ein Rückgabewert eines `before`-Hooks ohne `context`-Schlüssel als Antwort genommen. Der Endpunkt läuft dann nicht, `resolveOTP` legt also nichts an. Beweis: Integrationstest „FARMER/ADMIN: Anfordern legt KEINEN Code ab". Im Browser stand für `bauer-01@example.com` keine Zeile in `Verification`, im Terminal kein Code.
- **`nachDerAntwort` im Better-Auth-Kontext:** Better Auth läuft im Routen-Handler `src/app/api/auth/[...all]/route.ts` (`toNextJsHandler`), also in einem Request. Dort greift `after()`. Lokal gemessen (`curl`): Hof 83 ms, Kundin 47 ms. Beide Werte liegen unter 0,1 s, die Mail wartet in keinem Fall. Der allererste Aufruf (2,1 s) war das Kompilieren und zählt nicht. Der Code stand erst nach der Antwort im Terminal. `advanced.backgroundTasks` habe ich bewusst nicht gesetzt, weil es für alle Hintergrundaufgaben von Better Auth gälte.
- **Gleiche Antwortform:** `curl` auf `/api/auth/sign-in/email-otp` liefert für Hof und Kundin `HTTP 400` und `{"message":"Invalid OTP","code":"INVALID_OTP"}`, ohne `set-cookie`.

### Was nicht gelöst wurde und warum

- **Antwortzeit beim Anmelden mit Code:** Eine Hof-Adresse scheitert schon im Hook. Ein falscher Code einer Kundin geht zusätzlich durch `atomicVerifyOTP`: eine Zeile lesen, löschen und neu schreiben, das sind wenige Millisekunden mehr. Beim Anfordern habe ich das angeglichen, dort schreibt der Hof-Pfad einmal (er löscht den alten Code). Beim Anmelden bleibt der kleine Unterschied. Er verrät höchstens, dass eine Adresse ein Hof ist, und nie einen Zugang.
- **Fehlertext-Rot am Handy im hellen Thema 4,22 : 1** (Axe `color-contrast`, `#e7000b` auf `#f4f1e7`, 13,5 px). Den Fehler gab es schon in Runde 0; er ist nicht durch diese Nachbesserung entstanden. Die Angabe „Axe 0 Verstöße im Fehlerzustand" im ersten Bericht stimmt für 390 px hell nicht, bei 1440 px (auf der Kartenfläche) und dunkel ist es 0. Grund: Das neue Design ordnet `--destructive` nicht um, und `DESIGN_SYSTEM.md` kennt keinen Fehler-Token. Ein Token im Geltungsbereich `data-design="neu"` gälte für alle umgestellten Routen. Das ist eine Design-Entscheidung, deshalb habe ich nichts geändert. **Bitte entscheiden.**
- **Altlasten (nur notiert, nicht behoben):** `sendRaw` in `src/lib/email.ts:57–65` loggt `result.error` bzw. den Text der Ausnahme ungefiltert, darin kann eine Adresse stehen. `handleSubmit` in `src/components/anmelden/hof-anmeldung.tsx:55` hat kein try/catch: Ein Netzfehler lässt den Knopf auf „laden" stehen. Die Logik stammt unverändert aus `login-client.tsx`.

### Hinweise

- **E8 / Nr. 14:** `disableSignUp: false` legt beim ersten Code-Login ein Kundenkonto an, so wie bisher beim Magic Link. Für Nr. 08 passt das, es ist die freiwillige Anmeldung. Für „Bestellungen finden" (Nr. 14) entstünde damit bei jeder Bestellsuche still ein Konto. Dort braucht es einen eigenen Weg, ohne Sitzung bzw. ohne Anlegen, nicht einfach `KundeCodeFormular`. Der Hinweis steht auch in `anmeldecode.ts` und `DEVELOPMENT.md`.
- **Zur Kenntnis:** `storeOTP: 'hashed'` ist ein ungesalzener Hash über nur 10^6 mögliche Codes. Wer die Tabelle lesen kann, rechnet den Code zurück. Das ist vertretbar, weil ein Code nur 10 Minuten gilt und dieselbe Tabelle ohnehin Sitzungs-Token enthält.

### Annahmen

- Für Nicht-Kundinnen löscht das Anfordern einen vorhandenen Code (`sign-in-otp-<adresse>`). So verschwinden Codes, die vor dem Deployment für Hof-Adressen angelegt wurden, und der Hof-Pfad schreibt einmal in die Datenbank wie der Kundinnen-Pfad.
- Die Rollenprüfung beim Anfordern nimmt die Adresse so, wie das Plugin sie nimmt: klein geschrieben, nicht getrimmt. Würde der Hook trimmen, antwortete eine Hof-Adresse mit Leerzeichen 200, eine Kunden-Adresse mit Leerzeichen 400 (`INVALID_EMAIL`), und das verriete den Hof. Beim Anmelden wird getrimmt, dort ist die Antwort ohnehin immer `INVALID_OTP`.
- Im Versand steht die Rollenprüfung als zweite Sicherung weiter (jetzt nach der Antwort, also ohne Einfluss auf die Antwortzeit).

## Nachbesserung 3 (Sicherheitsfix aus Nr. 14)

### Was geändert wurde (je Datei ein Satz)

- `src/lib/ilike-muster.ts` — Neu: `genauesIlikeMuster` maskiert `\`, `_` und `%` (Backslash zuerst, ein Durchgang), damit ein case-insensitiver Prisma-Vergleich (ILIKE) nur genau den Text trifft; Name und Semantik wie in Nr. 14.
- `src/lib/anmeldecode.ts` — Neu: `rolleAusTreffern` entscheidet aus ALLEN Treffern — ein einziger Nicht-Kundinnen-Treffer genügt, nur lauter Kundinnen ergeben `CUSTOMER`, kein Treffer `null`.
- `src/lib/auth.ts` — `rolleZurAdresse` sucht mit maskiertem Muster per `findMany` statt `findFirst` und wertet `isAdmin` wie die Rolle `ADMIN`.
- `tests/ilike-muster.test.ts` — Neu: Maskierung von `_`, `%`, Backslash (auch `\_`), Gegenprobe gewöhnliche Adresse.
- `tests/anmeldecode.test.ts` — `rolleAusTreffern`: leer, nur Kundinnen, Hof/Admin an beliebiger Stelle, unbekannte Rolle.
- `tests/integration/anmeldecode.int.test.ts` — Neuer Block „Platzhalter und mehrere Schreibweisen": Hof `…_hof` neben Kundin `…-hof` (kein Code, auch ein serverseitig angelegter meldet nicht an, Passwort bleibt), Gegenprobe Kundin `…-hof` wird angemeldet, Hof `…%hof` neben Kundin `…-mein-hof`, `%` in der getippten Adresse findet keinen fremden Hof, zwei Schreibweisen (Kundin + Hof) → kein Code, Betreiber (`isAdmin`, Rolle CUSTOMER) → kein Code; die zwei vorhandenen Spies auf `findMany` umgestellt.
- `docs/ai/CODING_STANDARDS.md` — Regel: case-insensitiv nur mit `genauesIlikeMuster`, bei Berechtigungen alle Treffer.
- `docs/ai/ARCHITECTURE.md` — Invariante E7 um Platzhalter, alle Treffer und `isAdmin` ergänzt.
- `DEVELOPMENT.md` — Unterabschnitt „Nachbesserung 3".

### Gewählte Lösung und Begründung

Maskiertes ILIKE-Muster statt `lower(email) = lower($1)` per `$queryRaw`. Der Roh-Vergleich hätte gar keine Platzhalter-Semantik, wäre aber Roh-SQL ohne Not (TECH_STACK.md verbietet das außer bei nachweislicher Notwendigkeit) und nicht typisiert. Außerdem gibt es eine gemeinsame Funktion mit der Bestellsuche (Nr. 14). Das Restrisiko: Maskiert Prisma eines Tages selbst, wäre das Muster doppelt maskiert, die Hof-Suche ginge ins Leere, und der Hof bekäme einen Code. Das fängt der Integrationstest „Hof …_hof" ab.

### Belege

- Gegenprobe vor dem Fix: 7 Integrationstests rot. Darunter `_` (Code-Zeile für den Hof angelegt), `%` (`/sign-in/email-otp` meldete den Hof `…%hof` mit gültigem Code tatsächlich an), zwei Schreibweisen, `isAdmin` sowie die zwei auf `findMany` umgestellten Spies. Dazu die Unit-Tests (Funktionen fehlten). Danach alles grün.
- Eine Adresse mit `%` lehnt das Plugin schon beim Anfordern ab (`INVALID_EMAIL`). Beim Anmelden mit einem vorhandenen Code prüft es die Adresse nicht. Genau dort lag die Lücke.

### Was nicht gelöst wurde und warum

- `genauesIlikeMuster` liegt in einer eigenen Datei (`src/lib/ilike-muster.ts`), Nr. 14 hat sie in `src/lib/bestellungen-finden.ts`. Beim Zusammenführen sollte eine der beiden Stellen auf die andere verweisen; ich habe den Branch von Nr. 14 nicht angefasst.

### Annahmen

- `isAdmin` gehört zur Regel „nie für Admins" (E7), obwohl der Auftrag nur die Platzhalter nannte. Der Fix steckt in derselben Funktion und hat einen eigenen roten Test.
- Eine Kundin, neben deren Adresse in anderer Schreibweise ein Hof-Konto steht, bekommt keinen Code mehr (konservativ). Das ist nur bei von Hand angelegten Altkonten denkbar.

### Wie der Mensch es testet

`pnpm test:integration tests/integration/anmeldecode.int.test.ts`: Der Block „Platzhalter und mehrere Schreibweisen (Nachbesserung 3)" ist grün. In der App ändert sich sichtbar nichts. Optional in der Test-DB einen Hof `test_hof@example.com` und eine Kundin `test-hof@example.com` anlegen und auf `/account/login` für die Hof-Adresse einen Code anfordern. Im Terminal erscheint kein Code, und in `"Verification"` gibt es keine Zeile `sign-in-otp-test_hof@example.com`.
