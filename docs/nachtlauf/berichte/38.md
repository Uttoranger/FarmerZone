# Nr. 38 – S11 Double-Opt-in für werbliche Mails

Enthält Migration: **ja** – nur Expand, zwei nullable Spalten am Abo.

```sql
-- prisma/migrations/20261007180000_double_opt_in/migration.sql
SET lock_timeout = '5s';
ALTER TABLE "CustomerFarmSubscription" ADD COLUMN IF NOT EXISTS "emailOptInAngefragtAm" TIMESTAMP(3);
ALTER TABLE "CustomerFarmSubscription" ADD COLUMN IF NOT EXISTS "emailOptInBestaetigtAm" TIMESTAMP(3);
```

**Begründung:** Für den Double-Opt-in müssen wir pro Abo speichern, wann die Bestätigung angefragt und wann sie erteilt wurde. Der Bestätigungszeitpunkt ist auch der Nachweis der Einwilligung. Die Migration ist erzeugt nach Regel 3 (`prisma migrate diff` gegen `origin/main`) und um `IF NOT EXISTS`, `lock_timeout` und eine Anweisung je Spalte ergänzt.

- Die Spalten haben keinen Default und kein NOT NULL. Es gibt kein UPDATE und keine Datenmigration.
- Jedes bestehende Abo hat danach null/null und gilt damit als **Bestand**. Es bleibt unverändert und bekommt weiter Mails wie bisher (S11).
- Die Migration ist eine reine Katalog-Änderung, die Tabelle wird nicht umgeschrieben. Es entsteht keine neue Tabelle, deshalb ist keine RLS nötig.
- Geprüft wird sie mit der Datei-Wache `tests/migration-double-opt-in.test.ts` und mit `tests/integration/double-opt-in.int.test.ts` (Spaltentyp, Deploy-Fenster per rohem INSERT, zweiter Lauf).

**Deploy-Fenster:** Abos, die der alte Code zwischen Migration und neuem Code anlegt, haben null/null. Sie zählen deshalb als Bestand, also als einfaches Opt-in wie bisher. Umgekehrt setzt der neue Code `optInEmail` erst mit der Bestätigung. Der alte Code, der nur nach `optInEmail` filtert, schickt einer unbestätigten Anmeldung daher keine Werbung. Setzt der alte Checkout den Haken auf einer angefragten Anmeldung, schließt der neue Filter sie trotzdem aus (Integrationstest).

Branch `nacht/2026-10-07/38-double-opt-in`, Basis `origin/main` 2f1ecb8. Freigabe: `freigabe.md` §11 „38", Register S11 (Fassung Lauf 7).

## Bestehende Abonnenten

Auf die Produktion habe ich keinen Zugriff und habe ihn auch nicht versucht. Die Zahl ermittelst du mit diesen Abfragen (nur lesend):

```sql
-- Nach dem Deploy: bestehende E-Mail-Abonnenten mit einfachem Opt-in (nie angefragt)
SELECT count(*) AS abos, count(DISTINCT lower("customerEmail")) AS adressen
FROM "CustomerFarmSubscription"
WHERE "optInEmail" = true AND "emailOptInAngefragtAm" IS NULL;

-- je Hof

FROM "CustomerFarmSubscription" s
JOIN "Farm" f ON f.id = s."farmId"
WHERE s."optInEmail" = true AND s."emailOptInAngefragtAm" IS NULL
GROUP BY f.slug, f.name
ORDER BY abos DESC;

-- davon im Deploy-Fenster vom alten Code angelegt (Merge-Zeitpunkt in UTC einsetzen)
SELECT count(*) FROM "CustomerFarmSubscription"
WHERE "optInEmail" = true AND "emailOptInAngefragtAm" IS NULL
  AND "createdAt" >= TIMESTAMP '2026-10-08 00:00:00';  -- Beispielwert

-- Vor dem Deploy (die Spalten gibt es noch nicht): alle E-Mail-Abos sind Bestand
SELECT count(*) AS abos, count(DISTINCT lower("customerEmail")) AS adressen
FROM "CustomerFarmSubscription" WHERE "optInEmail" = true;
```

Wie mit dem Bestand umgegangen wird, entscheidest du. Möglich wären etwa eine einmalige Bitte um Bestätigung oder eine Stichtagsregel. Gebaut ist dafür nichts.

## Was nicht gelöst wurde und warum

- **WhatsApp-Opt-in** ist nicht angefasst, weil S11 nur von „werblichen Mails" spricht. Er bleibt einfaches Opt-in. Offen für dich.
- **Umgang mit den bestehenden Abonnenten:** Laut S11 entscheidest das du (siehe SQL oben).
- **`List-Unsubscribe`-Kopf:** nicht gebaut.
  - `sendRaw` kennt keine Kopfzeilen.
  - Ein Ein-Klick-Abmelden nach RFC 8058 bräuchte eine eigene POST-Route.
  - Der Abmeldelink in jeder werblichen Mail besteht weiter (signiert, ohne Ablauf, Abmelden per Knopf).
- **Datenschutzerklärung (§ 9):** Ein Satz zum Double-Opt-in und zu den gespeicherten Zeitpunkten fehlt. Das ist eine Rechtstext-Änderung, die nicht freigegeben ist, deshalb habe ich nichts geändert.
- **Hof-Kundenliste** (`customers.ts`): Sie zeigt „E-Mail-Neuigkeiten an/aus" nach `optInEmail`. Eine unbestätigte Anmeldung steht dort als „aus", das ist richtig. Den Zustand „wartet" zeigt sie nicht.
- **O3-Rest** („Nochmal bestellen" in der Abholbereit-Mail Werbung?): Das ist nicht entschieden, deshalb nicht angefasst.
- Subagenten `tester` und `pruefer` waren in dieser Umgebung nicht aufrufbar. Ersatz: eigene Prüfung des Diffs, Gegenprobe gegen den alten Code und der Browser-Durchlauf. Dabei habe ich einen Fehler gefunden und behoben (siehe unten).

## Annahmen

- **Gültigkeit 7 Tage, Bremse 10 Minuten je Abo.** Die Bremse steht in der Datenbank (`emailOptInAngefragtAm`) und gilt damit über alle Instanzen. Der frühere Link bleibt bis zu seinem Ablauf gültig.
- **Auch `/account` verlangt den Bestätigungslink**, obwohl die Kundin dort mit Code angemeldet ist und die Adresse damit bewiesen hat. Die Freigabe verlangt den Klick auf den Link für jede neue Anmeldung, deshalb habe ich konservativ entschieden. Soll die Code-Anmeldung als Bestätigung reichen, ist das eine kleine Änderung in `updateSubscription`.
- **Wer sich abgemeldet hat** (auch nach einer Bestätigung), bestätigt bei erneuter Anmeldung neu. Sonst könnte jeder, der die Adresse kennt, sie im Checkout wieder anmelden. „Bereits bestätigt → keine neue Bestätigung" gilt nur für ein aktives bestätigtes Abo.
- **Ein noch gültiger alter Link** meldet nach einer Abmeldung wieder an. Das ist ein ausdrücklicher Knopfdruck des Postfachinhabers.
- **`optInEmail` wird erst mit der Bestätigung gesetzt.** Grund ist der Schutz im Deploy-Fenster gegen den alten Code.
- **Werblich sind heute nur die Beitragsmails** (`publishStatusPost`). Andere Mails an Abonnentinnen gibt es nicht; die Vorlage `newsletter.tsx` wird nirgends verwendet.

## Wie der Mensch es testet (Vorschau)

1. **Neue Anmeldung:** Auf einer Hofseite einkaufen, in der Kasse „Per E-Mail … informiert werden" anhaken, mit einer neuen Adresse bar bestellen.
   - Erwartung: Die Bestellung geht durch wie immer.
   - Es kommt eine Mail „Bitte bestätige deine Anmeldung · FarmerZone" mit dem Hofnamen.
2. **Noch keine Werbung:** Als dieser Hof unter `/status/new` einen Beitrag „per E-Mail" vorbereiten.
   - Erwartung: Der Zähler enthält die neue Adresse noch nicht.
   - Veröffentlichen schickt ihr keine Mail.
3. **Link öffnen:** Den Link aus der Mail öffnen.
   - Erwartung: Seite „Anmeldung bestätigen" mit Hofname und Knopf. Neu laden ändert nichts.
   - Ein Tipp auf „Anmeldung bestätigen" zeigt „Danke, du bist angemeldet".
4. **Mails kommen an:** Einen weiteren Beitrag per Mail schicken.
   - Achtung: 1 Mail je Hof in 7 Tagen, am besten mit einem zweiten Testhof.
   - Erwartung: Die Mail kommt an, unten mit „Abmelden" und „Benachrichtigungen verwalten".
   - „Abmelden" → Knopf „Ja, abmelden" → danach keine Mails mehr.
5. **Ungültiger Link:** Den Link mit verändertem Token öffnen (ein Zeichen ändern).
   - Erwartung: „Das hat nicht geklappt" mit Ausweg „Zu ‚Mein Konto‘".
6. **Mein Konto:** `/account/login` mit derselben Adresse und Code, dann `/account/profile`.
   - Erwartung: Eine wartende Anmeldung zeigt „Wartet auf deine Bestätigung".
   - Aus- und wieder Einschalten schickt höchstens alle 10 Minuten einen neuen Link.
7. **Bestand:** Ein Abo aus der Zeit vor dem Deploy bekommt weiter Beitragsmails, ohne etwas zu tun.
