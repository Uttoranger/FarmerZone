## 3. Annahmen

- **`Farm.tarif` nullable ohne Default.** Kein Wert entspricht dem heutigen Zustand: HOFTOR brächte Grenzen (3 Produkte, 1 Abholzeit), HOFLADEN 19 €/Monat. null = bisheriges Modell, unverändert; kein UPDATE auf Bestandszeilen. Der Integrationstest zeigt: ein Hof, den alter Code anlegt, hat danach `tarif = null`.
- **`Order.erstattetCents` mit Default 0** statt nullable: Bestandsbestellungen haben nichts teilweise erstattet; 0 ist wahr und erspart überall eine Null-Prüfung. In PostgreSQL 11+ ein reiner Katalog-Schritt ohne Umschreiben der Tabelle.
- **Geld in ganzen Cent (Int)** für `erstattetCents`, `serviceFeeMinCentsApplied` und die Beträge der `Monatsabrechnung`: so in der Freigabe benannt, und alles rechnet gegen `serviceFeeCents`/Stripe-Beträge in Cent. **Widerspricht** der Altlast-Zeile in `ARCHITECTURE.md` §6 („Neue Geldfelder: Decimal(10,2)") — nicht heimlich, siehe offene Punkte.
- **Teilstorno minimal:** `OrderItem.fehltSeit`, `Order.erstattetCents`, Snapshot `Order.serviceFeeMinCentsApplied` (die Neuberechnung nach E14 braucht die Mindestgebühr zur Bestellzeit, sonst läse sie die heutige Hofeinstellung). Die bestehenden Snapshots bleiben unangetastet. Ob Gate 5 danach `totalAmount`/`serviceFeeCents` überschreibt oder eine aktuelle Gebühr daneben führt, bleibt Gate 5.
- **Enum-Werte:** `TeilenKanal` aus den Link-Kürzeln in Gate 7 (`?k=wa, wa-status, fb, ig, mail, qr, link`); `Trocknung` aus dem Formular-Mockup; `Tarif` aus E6.
- **Brennmaterial:** `holzart` Freitext, Wassergehalt/Körnung als Zahl der Klasse (W20 → 20, P31 → 31) — beides, weil Enum-Werte endgültig sind und die Listen offen; `restfeuchteMax` ganze Prozent; `gelagertSeit` als Datum (die Anzeige rechnet „seit 2 Jahren"); `ueberdacht` Default false. Welche Angabe je Art Pflicht ist, entscheidet später Zod.
- **`TeilenAufruf` ohne createdAt/updatedAt:** nur Aggregate, nichts über einzelne Aufrufe.
- **`Monatsabrechnung`** nach dem Mockup der Auswertung; kein Status-Enum, keine Stripe-ID (Lastschriftweg noch nicht gebaut, additiv nachrüstbar). RESTRICT zum Hof wegen Aufbewahrungspflicht.
- **`Product.familieId` ohne Fremdschlüssel/Tabelle**, wie in der Vorlage: Die Familie hat keine eigenen Daten.
- **Vorbereitete Unterkategorien außerhalb von `TAXONOMIE`:** Der Abgleich-Test erzwang die Werte in `taxonomie.ts`. In `TAXONOMIE.BRENNHOLZ` hätten sie sofort den Hinweis „Unterkategorie ergänzen" an jedem Brennholz-Produkt und eine Auswahl im Formular ausgelöst. So lehnt Zod sie ab, und nichts ändert sich. Ein bestehender Test wurde dafür eingeengt (nicht gelöscht): „jede Unterkategorie gehört zu genau einer Kategorie" gilt jetzt für die zugeordneten; der neue Test daneben prüft, dass die vorbereiteten zu keiner gehören.
- **Neue Einheiten:** keine Code-Änderung nötig — `PRODUCT_UNIT_VALUES` und `UNIT_OPTIONS` kennen sie nicht, das Formular bietet sie nicht an, Zod lehnt sie ab (Test).

**Deploy-Fenster:** Kein Code liest die neuen Strukturen. Alle neuen Spalten an Bestandstabellen sind nullable oder haben einen Default (Migrationswache grün, eigener Test zusätzlich); der alte Code schreibt weiter (Integrationstest mit rohem SQL nur aus alten Spalten).

**Rückroll-Risiko:** Die fünf neuen Werte an `ProductUnit`/`ProductSubcategory` und die vier neuen Enum-Typen sind endgültig (kein `DROP VALUE`). Solange keine Zeile einen neuen Wert trägt — bis Gate 6 schreibt keiner einen —, ist ein Rückrollen des Codes gefahrlos. Danach würde Code von vor diesem Schritt beim Lesen solcher Produkte werfen (wie bei `VERMUTLICH_WUNSCH`); das UPDATE dafür steht in `DEVELOPMENT.md`.

## Offene Punkte

- **Bitte entscheiden, vor dem Einspielen: Int-Cent oder `Decimal(10,2)` für die neuen Geldfelder.** Die Regelzeile in `docs/ai/ARCHITECTURE.md` §6 (Tabelle, Zeile „Geld teils `Decimal`, teils `Int` in Cent") sagt „Neue Geldfelder: `Decimal(10,2)`" — die Migration weicht davon ab. Zwei Wege, beide sauber:
  - **(A) Int-Cent behalten — Empfehlung des Prüfers.** Gilt für die Familie Servicegebühr/Erstattung/Monatsabrechnung: `erstattetCents`, `serviceFeeMinCentsApplied`, `grundgebuehrCents`, `servicegebuehrBarCents`, `servicegebuehrOnlineCents`, `summeCents`. Begründung: Die Werte stammen aus `serviceFeeCents` (Int), Stripe rechnet in Cent, und die Fachregeln rechnen ohnehin in Cent (`CODING_STANDARDS.md` §2 „Geld"). Dann gehört die Ausnahme in dieselbe Regelzeile von `ARCHITECTURE.md`, z. B.: „Ausnahme: Servicegebühr, Erstattungen und Monatsabrechnung in `Int`-Cent wie `serviceFeeCents`." Migration bleibt, wie sie ist. **`ARCHITECTURE.md` habe ich nicht geändert — das entscheidest du.**
  - **(B) Vor dem Einspielen auf `Decimal(10,2)` umstellen:** `erstattetCents`, `grundgebuehrCents`, `servicegebuehrBarCents`, `servicegebuehrOnlineCents`, `summeCents` (mit Umbenennung ohne `Cents`). `serviceFeeMinCentsApplied` bleibt `Int`, weil es ein Snapshot von `Farm.serviceFeeMinCents` (Int) ist. Geht nur, solange die Migration nirgends eingespielt ist; danach wäre es eine destruktive Typänderung.
- **Hinweis zu `docs/nachtlauf.md` Regel 3 (nur Vorschlag, nicht geändert):** Der dort vorgeschriebene Befehl `prisma migrate dev --create-only` ist praktisch nicht ausführbar — die Shadow-Datenbank scheitert an `20260804091431_enable_rls` (P3006), für jede Migration. An jener Migration lässt sich nichts ändern (Prüfsumme). Sicherer Weg für den Nachtlauf: `pnpm exec prisma migrate diff --from-schema <altes schema.prisma> --to-schema prisma/schema.prisma --script` — erzeugt das SQL rein aus zwei Schema-Dateien, **ohne jede Datenbank**, also auch ohne Risiko, die falsche zu treffen. Das alte Schema käme z. B. aus `git show main:prisma/schema.prisma` in eine Datei im Scratchpad.
- Gate 5: Rückfall für `serviceFeeMinCentsApplied = null` festlegen; Vollstorno nach Teilstorno muss `erstattetCents` abziehen; Checkout schreibt den Snapshot.

```sql
-- Schema-Expand Redesign (Gate 3, Aufgabe 5 aus docs/umsetzungsprompt.md,
-- Abschnitt 5). Nur die Punkte, die docs/nachtlauf/freigabe.md (Abschnitt 2)
-- freigibt: Produktfamilie (E3), Verpackung (E10), Brennmaterial (E11),
-- Teilen-Wirkung (S8), Tarife und Monatsabrechnung (E6), Teilstorno (E14).
-- NICHT enthalten: Farm.betriebsnummerGeprueftAm (E9: keine Prüfung),
-- Merkliste (E8: kein Kundenkonto), RueckrufAnfrage (nicht besprochen).
--
-- NUR ADDITIV (Expand, ARCHITECTURE §5): neue Enum-Werte, neue Enums, neue
-- Tabellen, an bestehenden Tabellen nur Spalten, die nullable sind oder einen
-- Default haben, und ein Index. Kein DROP, kein ALTER COLUMN, kein UPDATE auf
-- Bestandszeilen. DEPLOY-FENSTER: Kein Code liest oder schreibt eine dieser
-- Strukturen; alter Code schreibt weiter, ohne sie zu kennen.
--
-- NEUE ENUM-WERTE an bestehenden Typen (ProductUnit, ProductSubcategory) werden
-- hier NUR angelegt, nie benutzt — PostgreSQL erlaubt die Nutzung erst nach dem
-- Commit. ENDGÜLTIG: PostgreSQL kennt kein DROP VALUE. Solange keine Zeile
-- einen der neuen Werte trägt, kann alter Code gefahrlos zurückgerollt werden;
-- danach siehe DEVELOPMENT.md → „Schema-Expand Redesign" (Rückrollen).
--
-- VON HAND GESCHRIEBEN: `prisma migrate dev --create-only` scheitert an der
-- Shadow-Datenbank (P3006 bei 20260804091431_enable_rls, weil dort
-- "_prisma_migrations" noch nicht existiert) — dasselbe Hindernis wie bei den
-- früheren handgeschriebenen Migrationen. Geprüft mit `prisma migrate diff
-- --from-config-datasource --to-schema` gegen die lokale Testdatenbank.
--
-- WIEDERHOLBAR wie die übrigen Migrationen (IF NOT EXISTS, DO-Blöcke): Prisma
-- fährt eine Migration nicht in einer Transaktion.
--
-- RLS: Die drei neuen Tabellen bekommen RLS wie alle Tabellen im public-Schema
-- (20260804091431_enable_rls) — ohne Policies, ohne FORCE.
SET lock_timeout = '5s';

-- 1. Neue Werte an bestehenden Enums (E11). Nur angelegt: Zod kennt sie noch
--    nicht, kein Formular bietet sie an (Gate 6 schaltet sie frei).
ALTER TYPE "ProductUnit" ADD VALUE IF NOT EXISTS 'RAUMMETER';
ALTER TYPE "ProductUnit" ADD VALUE IF NOT EXISTS 'SCHUETTRAUMMETER';

ALTER TYPE "ProductSubcategory" ADD VALUE IF NOT EXISTS 'BRENNHOLZ_SCHEIT';
ALTER TYPE "ProductSubcategory" ADD VALUE IF NOT EXISTS 'ANZUENDHOLZ';
ALTER TYPE "ProductSubcategory" ADD VALUE IF NOT EXISTS 'HACKSCHNITZEL';

-- 2. Neue Enums
DO $$ BEGIN
  CREATE TYPE "Verpackung" AS ENUM ('LOSE_BALLEN', 'ABGEPACKT_ETIKETT');
EXCEPTION WHEN duplicate_object THEN NULL; END $$;

DO $$ BEGIN
  CREATE TYPE "Trocknung" AS ENUM ('OFENFERTIG', 'LUFTTROCKEN', 'FRISCH');
EXCEPTION WHEN duplicate_object THEN NULL; END $$;

DO $$ BEGIN
  CREATE TYPE "TeilenKanal" AS ENUM (
    'WHATSAPP', 'WHATSAPP_STATUS', 'FACEBOOK', 'INSTAGRAM', 'EMAIL', 'QR', 'LINK'
  );
EXCEPTION WHEN duplicate_object THEN NULL; END $$;

DO $$ BEGIN
  CREATE TYPE "Tarif" AS ENUM ('HOFTOR', 'HOFLADEN');
EXCEPTION WHEN duplicate_object THEN NULL; END $$;

-- 3. Farm: Tarif und SEPA-Mandat (E6). Beide nullable, OHNE Default und ohne
--    Backfill: null = bisheriges Modell (keine Grundgebühr, keine Grenzen).
--    Jeder Default würde Bestandshöfen einen Tarif unterstellen, den sie nie
--    gewählt haben.
ALTER TABLE "Farm" ADD COLUMN IF NOT EXISTS "tarif" "Tarif";
ALTER TABLE "Farm" ADD COLUMN IF NOT EXISTS "sepaMandatAm" TIMESTAMP(3);

-- 4. Product: Produktfamilie (E3) und Verpackung (E10), beide nullable.
--    null = Einzelprodukt bzw. keine Angabe — so stehen alle Bestandsprodukte.
ALTER TABLE "Product" ADD COLUMN IF NOT EXISTS "familieId" TEXT;
ALTER TABLE "Product" ADD COLUMN IF NOT EXISTS "verpackung" "Verpackung";
CREATE INDEX IF NOT EXISTS "Product_familieId_idx" ON "Product"("familieId");

-- 5. Order: Teilstorno (E14) und Teilen-Kanal (S8).
--    erstattetCents mit Default 0: Bestandsbestellungen haben nichts teilweise
--    erstattet; der Default schreibt das in einem Katalog-Schritt fest (PG 11+,
--    kein Umschreiben der Tabelle). Die beiden anderen nullable.
ALTER TABLE "Order" ADD COLUMN IF NOT EXISTS "serviceFeeMinCentsApplied" INTEGER;
```
