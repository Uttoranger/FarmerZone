# Bericht Nr. 40 — R1 Rate-Limit über die Datenbank

**Enthält Migration: ja.** Ordner `prisma/migrations/20261007200000_rate_limit_db`, nur Expand:

```sql
SET lock_timeout = '5s';

CREATE TABLE IF NOT EXISTS "RateLimitZaehler" (
    "schluessel" TEXT NOT NULL,
    "fensterStart" TIMESTAMP(3) NOT NULL,
    "zaehler" INTEGER NOT NULL DEFAULT 0,
    "ablauf" TIMESTAMP(3) NOT NULL,

    CONSTRAINT "RateLimitZaehler_pkey" PRIMARY KEY ("schluessel","fensterStart")
);

CREATE INDEX IF NOT EXISTS "RateLimitZaehler_ablauf_idx" ON "RateLimitZaehler"("ablauf");

ALTER TABLE "public"."RateLimitZaehler" ENABLE ROW LEVEL SECURITY;
```

**Begründung:** Register R1 verlangt „eine Tabelle in der Datenbank (Schlüssel, Fenster, Zähler)", Migration nur Expand (freigabe.md §11 „40").

**Wie erzeugt:** nach Regel 3. Zuerst `git show origin/main:prisma/schema.prisma > …/schema-main-40.prisma`, dann `pnpm exec prisma migrate diff --from-schema …/schema-main-40.prisma --to-schema prisma/schema.prisma --script`. Die Ausgabe war genau `CREATE TABLE` und `CREATE INDEX` wie oben. Ergänzt habe ich nur `IF NOT EXISTS`, `lock_timeout` und RLS ohne Policies (wie bei allen Tabellen im public-Schema, Muster `20261005120000_schema_expand_redesign`).

**Was die Migration berührt:** Keine bestehende Tabelle wird angefasst. Es gibt keine Daten-Migration und keine Spalte für IP, Adresse oder Sitzung. Der Schlüssel ist Zweck + HMAC.

**Deploy-Fenster:** Alter Code kennt die Tabelle nicht und läuft unverändert weiter.

**Wo angewandt:** nur über `pnpm test:integration` (global-setup → `migrate deploy` gegen die lokale Test-DB, unter `flock`). Nie über `migrate dev`, `db:*` oder `.env.local`. Der Zeitstempel liegt nach `20261007180000_double_opt_in` (Nr. 38).

## Annahmen

- **Fail-open:** Ist die Datenbank nicht erreichbar, wirft sie einen Fehler oder braucht die Zählung länger als 1,5 s, lässt Stufe 2 durch. Dann geht eine Sentry-Meldung „Bremse über alle Instanzen nicht erreichbar" ab, Level warning. Sie enthält nur die Fehlerart (`name`), den Grund (`datenbank`/`zeitlimit`) und die Zwecke, nie Schlüssel, IP, Adresse oder den Fehlertext. Stufe 1 wirkt weiter. So scheitert eine gültige Bestellung nie an der Bremse.
- **Registrierung bekommt eine erste Stufe:** Bisher bremste dort nichts. Das Better-Auth-Limit gilt nur für seinen HTTP-Router, `registerFarmer` ruft `auth.api.signUpEmail` direkt (geprüft in `better-auth/dist/api/index.mjs`, `onRequestRateLimit` nur in `router.onRequest`). „Die bestehende Bremse je Instanz bleibt als erste Stufe" habe ich deshalb so gelesen: eine Speicher-Bremse mit der Zahl des bestehenden Auth-Limits (10/min je IP), dann die Datenbank.
  - Gezählt wird nach Honigtopf, Zeitschranke und Zod: Ein Bot, der still abgewiesen wird, kostet nichts.
  - Die Antwort über der Grenze ist sichtbar: „Das waren gerade zu viele Versuche. Warte eine Minute und probier es dann noch einmal." Die stille Erfolgsmeldung ist bewusst nicht gewählt: Ein Mensch hielte sein Konto sonst für angelegt.
- **Feste Fenster statt gleitender:** Der Auftrag sagt, ein fester Fenster-Zähler genügt. An der Fenstergrenze sind kurz bis zu 2× Grenze möglich; die gleitende Stufe 1 fängt das je Instanz ab.
- **Anmeldecode ohne Anfrage-Header** (Aufruf über `auth.api` vom Server): Dann zählt nur die Adresse, keine IP. Sonst teilten sich alle Server-Aufrufe den Schlüssel „unknown". Auch Better Auths Stufe 1 gilt dort nicht.
- **Adressen** zählen klein und ohne Rand, wie in Stufe 1.
- **Datenschutz, bitte gegenlesen:** Die Formulare „Problem melden" sagen „Keine IP-Adresse, keine Cookies". Die Meldung selbst enthält weiterhin keine IP.
  - Der Zähler für Meldungen ohne Hof-Sitzung speichert aber einen HMAC der IP, höchstens bis zum nächsten Cron-Lauf, also rund 1–25 Stunden. Er ist nicht mit der Meldung verknüpft.
  - Ich halte das für gedeckt durch „Server-Logs (IP-Adresse, Zeitstempel) für Betrieb und Sicherheit" in `/datenschutz`. Texte habe ich nicht geändert (Rechtstexte, O4).
  - Wenn du es anders siehst: Der Satz in den Formularen bzw. in der Datenschutzerklärung wäre anzupassen.
- **Geheimnis:** Der HMAC nutzt `BETTER_AUTH_SECRET` mit Präfix `bremse:`, wie die übrigen Signaturen. Ein Wechsel des Geheimnisses setzt nur die laufenden Fenster zurück.
- **Kein `server-only`** in `src/server/bremse-datenbank.ts`, weil `auth.ts`, die Checkout-Route und die Actions in vielen Unit-Tests ohne Mock dafür geladen werden. Die Datei liegt unter `src/server` und wird nur serverseitig importiert.

## Wie der Mensch es testet

Die Bremse wirkt nur in Produktion. Deshalb lokal als Produktions-Build gegen die Test-DB:

1. Server mit diesem Befehl starten:
   ```
   DATABASE_URL=postgresql://postgres:postgres@localhost:5432/farmerzone_test DIRECT_URL=$DATABASE_URL BETTER_AUTH_SECRET=$(openssl rand -hex 32) STRIPE_SECRET_KEY=sk_test_platzhalter STRIPE_WEBHOOK_SECRET=whsec_platzhalter NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY=pk_test_platzhalter NEXT_PUBLIC_APP_URL=http://localhost:3000 pnpm build && <dieselben Variablen> pnpm start
   ```
   Das Geheimnis für beide Befehle einmal festlegen. Die Test-DB muss die Migration haben (`pnpm test:integration` spielt sie ein).
2. Vier Codes von derselben IP anfordern, mit vier verschiedenen erfundenen Adressen:
   ```
   curl -s -o /dev/null -w '%{http_code}\n' -X POST http://localhost:3000/api/auth/email-otp/send-verification-otp -H 'content-type: application/json' -H 'origin: http://localhost:3000' -H 'x-forwarded-for: 192.0.2.5' -d '{"email":"test-1@example.com","type":"sign-in"}'
   ```
   Erwartung: 200, 200, 200, 429.
3. In der Datenbank nachsehen: `psql postgresql://postgres:postgres@localhost:5432/farmerzone_test -c 'SELECT * FROM "RateLimitZaehler"'`. Erwartung: eine Zeile `anmeldecode-anfordern-ip:<32 Hex>` mit Zähler 3, je Adresse eine `anmeldecode-adresse:<Hex>` mit 1. Nirgends steht „192.0.2.5" oder eine Adresse.
4. **Über alle Instanzen:** Den Server beenden und neu starten. Das ist eine frische Instanz mit leerem Speicher. Innerhalb derselben Minute noch einmal von `192.0.2.5` anfordern. Erwartung: 429. Diesmal kommt es aus der Datenbank, Better Auths Speicher ist leer. Mit `x-forwarded-for: 192.0.2.6` kommt 200.
5. **Fail-open:** Mit `DATABASE_URL` auf eine nicht erreichbare Datenbank greift Stufe 2 nicht. Weil dann auch die Anmeldung selbst die Datenbank braucht, prüfen das die Unit-Tests (`tests/bremse-datenbank.test.ts`, „FAIL-OPEN …").
6. **Aufräumen:** Nach mindestens einer Minute den Cron aufrufen: `CRON_SECRET=x` beim Start setzen, dann `curl -H 'authorization: Bearer x' http://localhost:3000/api/cron/cleanup-reservations`. Erwartung: `{"deleted":…,"bremsZaehler":N,…}`, und die abgelaufenen Zeilen sind weg.
7. Zum Schluss Testzeilen löschen: `DELETE FROM "RateLimitZaehler";` und die Codes in `"Verification"` mit `identifier LIKE 'sign-in-otp-test-%'`.
